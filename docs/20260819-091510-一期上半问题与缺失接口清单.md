## 2. 当前结论

当前一期上半更准确的阶段描述是：

> 管理身份、会话安全基础、后台角色基础和调用系统基础配置已完成；Catalog 已确认归入一期下半，不影响一期上半完成判断。管理操作级鉴权和若干管理安全闭环仍需整改。

当前不能直接将一期上半标记为“完整完成”，原因包括：

1. 管理操作码已经定义和分配，但管理 API 尚未统一接入后端操作级鉴权。
2. 首个超级管理员初始化和最后一个超级管理员保护没有形成完整可执行闭环。
3. 传统账密验证码登录尚未形成完整链路，调用系统工具范围和运行 API 范围尚未形成完整接口。
4. 管理审计在一期目标、一期下半安排和二期目标之间尚未统一。
5. 一期要求的迁移、初始化、网关和基础验收交付物尚未完整形成。

## 4. 逐项问题与处理建议

### H01：Catalog 管理尚未实现，已确认归入一期下半

**优先级：P0**  
**状态：已关闭**（Catalog 实现仍属一期下半交付项，跟踪见 5.4 节）

#### 当前设计

- 当前代码没有 `api/admin/catalog`、Provider、Tool、ToolVersion、Capability 等正式管理模型和路由。
- [一期开发完成情况.md](./功能架构梳理/一期开发完成情况.md) 已说明 Catalog 核心配置尚未实现。
- 已确认 Catalog 属于一期下半，与工具发现、执行、Provider 和检索链路在同一阶段完成，不作为一期上半完成判定。

#### 问题

Catalog 虽然不属于一期上半，但它是 Discover、Execute、Provider 执行和工具检索的配置前提。如果一期下半只开发运行 API 而没有先完成 Catalog，运行链路将没有已审核、已发布的工具定义和固定执行映射可用。

#### 确认结论

- Catalog 归入一期下半，不纳入一期上半完成判定，但继续在本时间戳清单中跟踪。
- 一期下半应先冻结并实现 Catalog 核心模型、状态机、管理 API 和管理页面，再接入 Discover、Execute、Provider 和检索链路。
- Catalog 仍属于一期最终目标，不能因其阶段调整而延期到二期或从一期交付范围删除。

#### 最终方案

- 一期下半实现范围至少包括 Provider、能力包、工具、工具版本、执行绑定、审核、发布、启停、归档及相应管理页面和 API。
- Catalog 归入一期下半，与工具发现、执行、Provider 和检索链路在同一阶段完成；不作为一期上半完成判定。
- Catalog 仍属于一期最终目标，不能因阶段调整而延期到二期或从一期交付范围删除。
- 本清单继续保留 Catalog 管理接口（见 5.4 节），作为一期下半交付项跟踪。

**已解决**：2026-08-20，完成文档口径统一并核实：
- [一期目标.md](./功能架构梳理/一期目标.md) 已从一期上半目标表移除“Catalog 管理”，并在一期下半目标表新增“Catalog 管理（配置前提）”行；同步调整了上下半交付顺序和范围边界表述。
- [一期开发完成情况.md](./功能架构梳理/一期开发完成情况.md) 已将 2.2 节改为明确“Catalog 归入一期下半实现，不作为一期上半目标或完成判定”。
- 核实确认：代码仍无 `api/admin/catalog`、Provider、Tool、ToolVersion、Capability 等 ORM 模型、迁移、状态枚举或 API，与“Catalog 属于一期下半、尚未实现”一致；实际开发按 A05 流程在一期下半先冻结实体关系、状态机、接口契约后再编码。

### H02：管理操作级鉴权未接入所有管理 API

**优先级：P0**  
**状态：已关闭**（后端操作级鉴权已接入；前端按操作项控制见 H12）

#### 当前设计

- 一期目标要求默认拒绝、角色与操作项关联，以及页面/API 操作级控制。
- 总体架构要求后端 API 必须独立执行操作码校验，不能只依赖前端隐藏按钮。
- 当前管理路由普遍只依赖 `_get_current_user`，没有统一的 `require_operation` 依赖。
- 架构问题清单的最新处理记录仍将“操作项接口校验统一接入”列为待后续事项。

#### 问题

登录成功只证明账号身份，不代表账号拥有当前接口的操作权限。若没有后端操作码校验，普通管理账号可能调用账号、角色、调用系统等写接口，默认拒绝原则实际上没有落地。

#### 处理建议

1. 增加统一的 `require_operation(operation_code)` 依赖或等价授权组件。
2. 为每个管理接口建立“接口 → 操作码”映射。
3. 未授权统一返回 403，并区分未认证 401。
4. 超级管理员走实时授权，不在 Session 中保存授权快照。
5. 前端通过 `/api/admin/auth/me/operation-items` 控制菜单和按钮，但不能替代后端校验。

**已解决**：2026-08-20，已完成后端操作级鉴权接入：
- 新增 `require_operation(operation_code)` 依赖（`toolhive/api/admin/deps.py`），基于 `RoleService.check_operation` 实时计算权限；超级管理员自动全量，不缓存、不保存授权快照。
- 管理 API 全部接入操作码校验：账号（`admin_account:*`）、角色与操作项（`role:*`）、调用系统（`caller_system:*`）、系统任务（`system_task:*`）；自身会话类接口（`/auth/me`、`/session`、`/csrf-token`、`/change-password`、`/mfa/bind`、`/login/verify-mfa`）仅校验身份，不加操作码。
- 未登录/会话失效返回 401，已登录但缺操作码返回 403（`缺少操作项: xxx`）。
- `caller_system:allow_any_ip` 落地：新增 IP 规则值为 `*` 时需额外持有该操作码，否则 403。
- 新增 `tests/api/test_admin_authz.py`（放行、403、401、会话版本失效 4 个用例）；全量测试 93 项通过，改动文件通过 ruff 检查。
- 前端按 `/auth/me/operation-items` 控制菜单和按钮仍属 H12，本轮未改动前端。

### H03：超级管理员初始化和最后超管保护未闭环

**优先级：P0**  
**状态：待实现**

#### 当前设计

- 一期目标要求首个超级管理员初始化和超级管理员保护。
- 当前服务中存在 `init_super_admin` 方法，但没有明确可执行的初始化命令或一次性 HTTP 接口。
- 当前 CLI 已有 Chroma 重建命令，但没有 `init-admin` 子命令。
- 账号服务中的 `_check_last_super_admin` 目前仍为空实现。

#### 问题

- 新环境没有明确、可审计、可重复验证的首个管理员初始化入口。
- 禁用、离职或其他状态操作可能绕过最后一个超级管理员保护。
- 文档要求的安全边界没有转化为可验收的接口和错误语义。

#### 处理建议

补充以下其中一种初始化方式，并明确只能执行一次：

- `toolhive init-admin` CLI；或
- 受网络和一次性初始化令牌保护的 `POST /api/admin/bootstrap`。

同时补齐：初始化状态查询、最后一个超管保护、超管角色保护、初始化操作审计和明确的冲突错误码。

**已解决记录（2026-08-20）**：完成初始化闭环与最后超管保护，原文保持不动，补充如下：

- 新增 `toolhive init-admin --username <名称>` CLI 命令：仅当无任何管理账号时可执行；密码优先读环境变量 `TOOLHIVE_INIT_ADMIN_PASSWORD`（CLI `--help` 与 `toolhive.example.yaml` 已写明用法），未设置时交互式输入两次；已存在账号时拒绝执行并返回非零退出码，不覆盖任何数据。
- `init_super_admin` 修复：创建账号后自动确保内置超管角色存在并建立“账号 → 超管角色”关联（此前只建账号、未授角色，初始化出的“超管”实际无权限）。
- `_check_last_super_admin` 由空实现补全：启用状态超管账号且启用超管数 ≤ 1 时，禁用/离职操作返回 `ValidationError`（“不能停用或离职最后一个超级管理员”），覆盖 `disable_account` 与 `offboard_account`；超管角色自身的保护（不可改/禁、只有超管可授予/移除、不可移除最后一个超管角色）沿用现有 `role_service` 逻辑。
- 新增公开接口 `GET /api/admin/bootstrap/status`：返回 `{"initialized": true|false}`，仅判断是否存在账号，不泄露账号敏感信息。
- 初始化操作审计：因 H07 尚未确认管理审计归属一期还是二期，本轮仅输出结构化 INFO 日志（用户名、来源 CLI、时间），不建审计表；待 H07 定口径后统一补审计记录。
- 测试：新增账号服务、CLI、bootstrap 状态共 13 个用例；全量测试 106 项通过；改动文件通过 ruff 检查。
- 超管权限说明：超级管理员通过内置超管角色自动获得全部有效管理操作项（实时计算），新增接口只需在 `OperationCode` 枚举中增加操作码，应用启动时自动同步，无需为超管逐项手动授权。

### H04：传统图形验证码登录链路未完成

**优先级：P1**  
**状态：已确认，待实现**

#### 当前设计

- 已确认一期管理后台采用账号、密码和图形验证码登录。
- 登录服务在达到阈值后返回 `captcha_required`，并注释说明后续请求应携带 `captcha_token`。
- 登录请求 Schema 当前只有用户名和密码，没有验证码标识和验证码内容。
- 当前没有图形验证码生成、刷新、展示和一次性校验接口。

#### 问题

当前实现仍是登录失败达到阈值后才返回 `captcha_required`，而且前端收到后只能提示用户重试。现有实现既不符合已确认的传统账密图形验证码登录方案，也没有可执行的验证码链路。

#### 处理建议

- 由 ToolHive 提供图形验证码生成和校验能力；验证码答案等临时状态保存在 Redis，不写入数据库。
- 登录页加载或手动刷新时申请验证码，返回短期有效的验证码标识和图形内容。
- 登录请求提交账号、密码、验证码标识和验证码内容；验证码必须短期有效、一次性消费，成功或失败后均不可重放。
- 删除现有仅在失败阈值后返回 `captcha_required`、但无法继续验证的半成品流程；登录失败限制继续独立生效。

**已解决记录（2026-08-20）**：完成传统图形验证码登录链路，原文保持不动，补充如下：

- 新增 `toolhive/services/security/captcha.py`：使用 `captcha`（lepture）+ Pillow 生成 PNG 图形验证码；随机码去除易混淆字符（0/O、1/I/l、2/Z、5/S、8/B 等）；答案写入 Redis（`captcha:<id>`），TTL 默认 300 秒。
- 一次性消费：校验时在 Redis 管道中原子读取并删除答案，无论答案正确或错误均不可重放；答案比较使用 `hmac.compare_digest` 常量时间比较。
- 新增公开接口 `POST /api/admin/auth/captcha/challenge`（已加入 CSRF 白名单，无需会话与 CSRF）：返回 `{captcha_id, image（base64 PNG data URI）, expires_in_seconds}`。
- `LoginRequest` 新增必填 `captcha_id`、`captcha_code`；登录服务先校验图形验证码再进入账号流程，验证码错误/过期返回 401 `验证码错误或已过期，请刷新后重试`。
- 删除半成品逻辑：`check_captcha_required`、`captcha_required` 错误分支、`captcha_trigger_failures`、`captcha_trigger_window_minutes` 全部移除；登录失败限制继续独立生效。
- 配置调整：`captcha_trigger_window_minutes` 更名为 `login_failure_window_minutes`（仅承担登录失败统计窗口）；新增 `captcha_ttl_seconds`（默认 300）、`captcha_code_length`（默认 4）；`toolhive.example.yaml` 与 `.env.example` 已同步。
- 前端登录页：支持验证码展示、点击刷新与提交；验证码错误/过期时自动刷新并提示。MFA 步骤暂时保留，待 H05 移除。
- 依赖：`pyproject.toml` 新增 `captcha>=0.7.1,<0.8` 与 `pillow>=10.0.0`。
- 测试：新增验证码服务与 API 链路共 7 个用例；全量测试 113 项通过；本次改动文件通过 ruff 检查。

### H05：管理登录方案改为传统账密验证码，不使用 MFA

**优先级：P1**  
**状态：已确认，待整改**

#### 确认结论

一期管理后台使用传统的账号、密码和图形验证码登录，不使用 MFA、TOTP 动态码或恢复码，也不依赖手机端或第三方验证器应用。

```text
管理人员输入账号、密码和图形验证码
  → 服务端校验图形验证码
  → 校验账号状态、登录限制和密码
  → 校验成功后创建管理 Session
```

图形验证码用于防止自动化尝试和暴力登录，不属于第二认证因素。短信验证码、邮件验证码、TOTP 和恢复码均不纳入一期管理登录方案。工具运行侧仍使用调用系统公钥验签，与本项管理登录方案无关。

#### 当前偏差

- 当前后端和前端已经存在 MFA 绑定、TOTP 验证、恢复码登录及 MFA 设置页面，与确认后的登录方案不一致。
- 当前图形验证码仅存在触发标记，尚无可执行的挑战、展示和登录校验链路，具体缺口继续由 H04 跟踪。
- 原计划中的 MFA 重置、重新绑定和恢复码轮换接口不再需要实现。

#### 整改要求

- 调整登录流程为账号、密码和图形验证码校验通过后直接创建管理 Session。
- 删除或停用 MFA 绑定、TOTP 验证、恢复码登录及 MFA 设置页面，不再新增 MFA 生命周期接口。
- 清理不再使用的 MFA 配置、数据模型和安全配置前，先确认现有环境是否已有相关数据，并制定兼容或迁移处理方式。
- 图形验证码的生成、刷新、有效期、一次性消费、错误次数和登录请求字段统一在 H04 中冻结。

**已解决记录（2026-08-20）**：已完成管理登录方案整改（移除 MFA），原文保持不动，补充如下：

## 5. 一期上半缺失接口清单

以下接口名称是用于冻结业务契约的建议，不要求必须使用完全相同的 URL；正式开发前应统一命名、请求 Schema、响应 Schema、错误码和操作码。

### 5.1 管理身份与账号

| 业务 | 建议接口 | 说明 |
|------|----------|------|
| 首次初始化 | `toolhive init-admin` 或 `POST /api/admin/bootstrap` | 仅在无账号时可用，初始化后关闭 |
| 初始化状态 | `GET /api/admin/bootstrap/status` | 不泄露账号敏感信息 |
| 账号资料 | `PATCH /api/admin/accounts/{account_id}` | 修改外部用户 ID、展示资料等非敏感字段 |
| 账号离职 | `POST /api/admin/accounts/{account_id}/offboard` | 禁用、撤销会话并保留历史记录 |
| 人工锁定 | `POST /api/admin/accounts/{account_id}/lock` | 如果业务要求管理员主动锁定 |
| 传统账密验证码登录 | `POST /api/admin/auth/login` | 提交账号、密码和图形验证码；校验成功后创建管理 Session |
| 图形验证码 | `POST /api/admin/auth/captcha/challenge` | 返回短期有效的验证码标识和图形内容，支持刷新 |

### 5.2 RBAC 与管理安全

| 业务 | 建议接口或机制 | 说明 |
|------|----------------|------|
| 操作项查询 | `GET /api/admin/auth/me/operation-items` | 当前已有，但前端需要实际使用 |
| 接口授权 | `require_operation(operation_code)` | 已接入（H02），对所有管理 API 强制校验，不是可选项 |
| 操作项错误 | 统一 401/403 语义 | 已落地（H02）：未登录 401，已登录但无权限 403 |
| 会话撤销 | 复用账号强制下线或补充会话管理接口 | 明确单会话互斥和撤销范围 |
