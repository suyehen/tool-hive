# ToolHive 二期目标

> 文档版本：v1.3  
> 更新日期：2026-08-18  
> 文档目的：说明在一期 HTTP 工具调用闭环稳定后，ToolHive 的二期及后续建设方向。

## 1. 二期启动前提

二期不以功能清单齐全为唯一条件，而应建立在一期核心闭环已经稳定的基础上：

- 管理配置、调用系统认证、工具发现、工具调用控制、HTTP Provider 执行和基础 Trace 已形成可验收闭环；
- 已确认一期的权限、审计、外部 API 和基础设施规则，且能够稳定部署和维护；
- 首批调用系统和外部 HTTP 工具经过实际运行验证；
- 需要新增的协议、规模或治理能力有明确业务场景和容量依据。

二期具体范围和排期应在启动前重新确认；以下内容是能力方向，不代表无条件同时启动。

## 2. 身份与企业集成

| 目标 | 二期能力 |
|------|----------|
| SSO 实接入 | 按企业身份系统实际协议实现适配器，例如 OIDC、SAML 或企业自有协议。 |
| 统一登录扩展 | 在保留本地超级管理员应急入口的前提下，使外部身份与内部管理账号安全匹配。 |
| 高风险调用方认证 | 按实际风险增加请求签名与 mTLS 的组合认证，或接入企业 OAuth2/身份中心适配器。 |

SSO 和企业身份集成只确认管理人员或调用系统的身份来源，不能绕过 ToolHive 内部的账号状态、管理操作项、调用系统状态和工具调用控制。

## 3. 协议与 Provider 扩展

| 方向 | 二期能力 |
|------|----------|
| MCP Provider | 连接经过批准的 MCP Server，将可执行工具规范化为 Catalog 候选版本。 |
| MCP Registry | 将 Registry 作为候选发现来源，而非可信工具源；所有 Server 必须经过来源校验、审批、凭据配置和健康检查。 |
| 平台 MCP 网关 | 在确有跨 Agent 生态需求时，对外暴露经过 ToolHive Policy 允许的工具能力。 |
| gRPC Provider | 为内部高频、强类型或低延迟服务提供 gRPC 适配，并统一映射 Schema、错误、审计和版本。 |
| 其他协议 | 按实际业务需要增加新的 Provider 适配器，而不重建与现有标准重复的外部协议。 |

无论接入何种协议，Provider 都必须遵循 Catalog 审核、凭据隔离、受控出站、权限判断和 Trace 记录的统一治理规则。

## 4. 宿主工具与高风险能力治理

对于文件、Shell、Wiki、记忆、渠道等依赖 Agent 主机环境、进程上下文或本地工作区的能力，二期应设计受控的宿主 Provider 或独立 Agent：

- 明确网络可达性、调用与回调方向、服务身份和断连语义；
- 对参数、目录、命令、文件类型、工作空间和资源上限进行最小权限控制；
- 将高风险工具的确认、审计和结果脱敏纳入统一运行链路；
- 明确哪些能力仍应保留在调用方本地，不迁入平台。

计算、JSON、字符串等无副作用的纯函数工具可以长期保留在调用方本地，不以迁移数量作为二期目标。

## 5. 发布、执行与检索治理增强

| 方向 | 二期能力 |
|------|----------|
| 发布治理 | 高级灰度发布、自动回滚、版本兼容窗口和更精细的默认版本切换策略。 |
| 执行治理 | Provider 配额、熔断、细粒度限流、异步任务、取消、回调和死信处理。 |
| 检索治理 | 离线召回评测、在线质量指标、候选预算优化和更精细的检索降级策略。 |
| 权限治理 | 大规模账号—工具 ACL、复杂租户范围、细粒度数据范围和专用权限检索优化。 |
| 成本治理 | 模型、Provider 和工具调用的成本统计、配额分析和质量成本评估。 |

## 6. 可观测性、运营与合规

二期应将一期基础 Trace 发展为可运营能力：

- 监控看板、系统健康指标、服务告警和关键安全事件通知；
- 管理操作、授权决策、检索和执行链路的查询、导出和审计报表；
- 数据脱敏、留存周期、访问权限、合规审计和安全事件调查流程；
- 在线质量、失败类型、Provider 可用性和调用成本的持续分析。

### 6.1 管理操作审计记录

一期每张业务表仅保留最后操作人（`create_id`/`update_id`/`create_name`/`update_name`），不保留变更历史。二期建设追加式、不可修改的管理操作审计记录，用于安全追责、还原现场和合规留痕：

- 审计记录至少包含操作人（`actor_account_id`/`actor_system_id`）、对象类型与对象 ID、动作、变更前/后摘要、原因、结果、`trace_id`、来源 IP 和发生时间；
- 成功的业务变更与对应审计在同一数据库事务中提交；失败尝试单独记录失败审计，不能把已回滚的变更记为成功；
- 覆盖关键安全事件：账号创建/启停/锁定/密码重置/强制下线/离职、角色与操作项变更、账号角色关联、调用系统生命周期、公钥与 IP 规则变更、授权决策和工具执行；
- 密码、TOTP 密钥、恢复码、私钥等敏感字段只保存脱敏摘要，不写入审计正文；
- 审计为长期追责数据，保留时间长于 Trace，清理前必须经过明确的留存策略；
- 与二期可观测性中的查询、导出、报表和合规审计流程统一设计。

一期不实现管理操作审计记录，该能力不纳入一期完成判定。

## 7. 规模化与可用性

| 方向 | 二期能力 |
|------|----------|
| 检索基础设施 | 向量检索服务化、专业搜索引擎、分片/多副本、热点目录优化和分布式缓存。 |
| Chroma 服务化 | 将一期嵌入式 Chroma 改造为独立共享服务，支持多个完整 ToolHive 实例访问同一索引。 |
| 应用部署 | 单一 ToolHive 应用的多实例部署、滚动发布兼容规则，以及按管理与工具调用负载进行容量治理的能力。 |
| 数据保护 | 备份恢复演练、容量治理、更高等级的 RPO/RTO 和跨区域容灾。 |
| 网络安全 | 公网运行接口接入 API 网关、WAF、更加严格的调用方准入和持续安全检查。 |

### 7.1 嵌入式 Chroma 的服务化改造

一期使用位于 `/vdb/tool-hive/chroma` 的嵌入式 Chroma，并因此限制为单 ToolHive 应用实例和单应用 Worker。二期需要根据实际容量和可用性需求处理以下风险：

- 本地索引与具体服务器绑定，服务器迁移时需要重新构建或迁移索引。
- 多个 ToolHive 实例无法安全共享同一个本地 Chroma 持久化目录。
- 多实例分别维护本地索引会产生索引版本和检索结果不一致。
- 多进程同时读写同一个持久化目录存在并发和数据可靠性风险。
- 本地磁盘损坏或目录丢失后，只能以 PostgreSQL 为事实来源全量重建。
- 单机磁盘、内存和计算资源会限制索引容量、查询并发和独立扩容能力。
- 嵌入式模式难以独立实施高可用、备份、监控和运维隔离。

二期改造方向为：

- 将 `VectorIndex` 的嵌入式实现替换为独立共享的 Chroma 服务实现，业务代码不直接依赖部署模式。
- 支持多个完整 ToolHive 实例访问同一索引，并明确服务认证、网络边界、超时和故障降级规则。
- 设计 PostgreSQL 全量导入、增量追平、双写验证、索引数量和内容校验流程。
- 在切换前验证新旧索引的召回结果和数据版本，制定流量切换、失败回滚和旧索引清理方案。
- 服务化完成并通过验收前，不启用依赖共享索引的 ToolHive 多实例部署。

是否进入这些建设项应以实际 QPS、并发、延迟、可用性、数据规模和业务风险为依据，避免在一期规模下过度设计。

### 7.2 外部目标系统凭据与 Secret Store 评估

一期不代持目标业务系统凭据。二期只有在首批工具确实需要通过 ToolHive 访问带认证的外部系统时，才评估是否建设 Secret Store。

可能涉及的凭据包括：

- 外部业务系统 API Key；
- Basic Auth 用户名和密码；
- OAuth2 Client Secret；
- 外部系统 mTLS 客户端证书和私钥；
- 其他不能由调用系统直接提供的服务凭据。

二期评估必须先确认：

- 哪些工具和目标系统确实需要平台代持凭据；
- 是否已有 Vault、云密钥管理服务或企业 Secret Manager；
- SecretStore 接口、环境/Provider 隔离路径、精确读取权限和轮换机制；
- 管理侧写入与执行侧读取的权限边界；
- 凭据访问审计、失效、备份恢复和 Secret Store 不可用时的拒绝策略；
- 是否需要把 Provider 执行器拆为独立进程或服务；
- 凭据注入与出站 allowlist、DNS/TLS/SSRF 防护的联动方式。

调用系统公钥不属于 Secret Store 范围，仍由 ToolHive 作为调用系统认证数据保存和管理。

在二期方案确认前，不得在一期 Catalog、配置文件或数据库中预留并实际使用目标系统密码、API Key、OAuth Secret 或客户端私钥字段。
