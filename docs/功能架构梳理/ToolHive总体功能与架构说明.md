# ToolHive 总体功能与架构说明

> 文档版本：v1.3  
> 更新日期：2026-08-16  
> 文档目的：说明 ToolHive 的产品定位、功能边界和目标总体架构。本文件不区分具体迭代交付范围，迭代目标见 [一期目标](./一期目标.md) 与 [二期目标](./二期目标.md)。
>
> 部署约束：ToolHive 是一个应用、一个发布单元和一个生命周期单元。管理模块与工具应用模块位于同一个 ToolHive 后端中，必须统一部署、启动、停止和升级；路由与访问控制的隔离不代表拆分为两套可独立运行的后端系统。

## 1. 产品定位

ToolHive 是面向 Agent、业务系统和其他服务调用方的统一工具平台。平台作为一个统一部署和运行的应用，将外部系统的可调用能力以受控工具的形式登记、审核、授权、发现和执行，避免调用方或 LLM 直接决定目标地址、认证凭据和执行权限。

ToolHive 解决以下核心问题：

1. **统一管理**：管理员在一个管理后台维护调用系统、工具 Provider、工具、版本、授权配置和运行状态。
2. **安全调用**：调用系统通过来源网络限制、身份认证、请求签名和防重放访问运行接口；LLM 不接触外部系统凭据。
3. **按需发现与执行**：平台根据调用主体和业务上下文判断可见工具，再对实际调用参数执行二次校验和受控转发。
4. **可追溯治理**：管理操作、授权决策、工具检索和执行结果都应具备 Trace 或审计记录，支持问题定位和安全追责。

ToolHive 不替代外部业务系统的业务权限和数据校验。外部系统仍负责确认业务数据是否可访问、写操作是否合法，以及返回稳定的业务结果和错误码。

## 2. 参与方与职责边界

| 参与方 | 在平台中的角色 | 主要职责 |
|--------|----------------|----------|
| 管理员 | 管理侧使用者 | 维护账号、后台角色、调用系统、工具目录及运行配置。 |
| 调用系统 | 工具应用模块的调用者 | 使用登记后的 `system_id` 和认证凭据请求工具发现或工具执行。调用系统可以是 Agent、业务系统或其他服务调用方。 |
| 最终业务身份 | 运行请求携带的业务上下文 | 表示用户、租户、角色、渠道等业务事实，供工具调用控制判断。 |
| ToolHive | 管理与运行控制平面 | 保存受控配置、校验调用方、执行授权判断、路由 Provider、记录 Trace。 |
| Provider | 外部能力适配层 | 将已审核工具定义转换为对外部 HTTP、MCP、gRPC 或其他协议的受控调用。 |
| 外部业务系统 | 实际能力提供者 | 提供订单、工单、项目等业务能力，并在自身系统内完成最终业务校验。 |
| LLM / Agent | 工具使用者 | 只能使用平台下发且当前请求允许的工具 Schema；不能直接构造 URL、Header、凭据或未下发工具。 |

### 2.1 管理模块与工具应用模块的访问隔离

ToolHive 的管理能力与工具调用能力位于同一个应用中，但采用两套独立的访问和控制体系。它们共享发布、部署、启动和停止生命周期，不作为独立后端服务运行：

| 对比项 | 管理模块 | 工具应用模块（运行 API） |
|--------|--------|--------|
| 使用主体 | 管理账号 | 调用系统及其业务上下文 |
| 访问对象 | 管理页面、管理 API、配置数据 | 工具发现、授权判断、工具执行 API |
| 身份凭据 | 管理登录会话 | `system_id`、调用系统公钥签名及来源网络信息 |
| 控制模型 | 后台角色 + 管理操作项 | 调用系统范围 + 工具调用控制 |
| 结果 | 管理员可以做哪些配置动作 | 当前请求可以发现或执行哪些工具 |

拥有超级管理员角色只代表能够管理 ToolHive，不代表可以绕过工具应用模块的认证或直接调用业务工具。调用系统凭据也不能访问管理页面或管理 API。

### 2.2 哪些能力进入 ToolHive

无网络访问、无外部凭据、无数据库或文件写入、没有业务副作用的轻量纯函数工具，例如计算、JSON 转换、字符串处理和简单规则判断，可以继续由调用方本地执行。这类工具不需要登记到 ToolHive Catalog，也不应为了统一形式而增加跨服务调用。

一旦工具需要访问外部业务系统、使用平台管理的凭据、读取租户业务数据或产生业务副作用，就应作为 ToolHive 管理的外部工具接入并接受平台治理。

## 4. 架构分层说明

### 4.1 接入与网关层

Nginx 是生产环境的统一入口，负责：

- 使用路径区分同一 ToolHive 应用中的管理前端、管理 API 与工具应用 API：`/admin/**`、`/api/admin/**`、`/api/runtime/v1/**`。
- 为管理模块提供公网 HTTPS 入口；仅允许明确配置的内网来源访问工具应用模块。
- 处理 TLS、HTTP 到 HTTPS 跳转、浏览器安全 Header 和基础登录限流。
- 清理或覆盖不可信的代理 Header；存在可信代理时，传递经过解析的真实来源信息。

网关只承担边界控制，不能取代应用层认证、授权、签名校验和工具调用控制。

### 4.2 管理模块

管理侧提供可视化管理前端和 `/api/admin/**` API，负责：

- 管理账号初始化、创建、启用、禁用、锁定、密码重置和强制下线；
- 本地登录（账号 + 密码 + 图形验证码）、会话、CSRF 和密码安全控制；
- 后台角色、管理操作项及其分配；
- 调用系统、调用系统公钥和来源 IP 规则管理；
- 能力包、Provider、工具、工具版本、审核、发布、启停等 Catalog 管理。

管理侧的授权单位是稳定的管理操作码，例如 `admin_account:view`、`role:assign`、`tool:review` 和 `tool:publish`。操作码由代码维护，前端控制展示，后端必须执行同一操作码的强制校验。

### 4.3 工具应用模块（运行 API）

工具应用模块通过 `/api/runtime/v1/**` 向调用系统提供工具相关能力。它与管理模块同属一个 ToolHive 应用，只是使用独立的调用身份和控制链。完整调用链为：

```text
调用系统请求
  → 网络来源校验
  → 调用系统状态、IP 规则和签名校验
  → Nonce 防重放
  → 运行 API 范围校验
  → 工具发现或工具执行的策略判断
  → 读取已发布的工具定义
  → Provider 受控调用
  → 返回标准化结果并记录 Trace
```

工具应用模块包含两个核心阶段：

- **发现（Discover / Resolve）**：依据调用主体和业务上下文，筛选可向调用方或 LLM 展示的工具候选及 Schema。
- **执行（Execute）**：对调用主体、真实参数、目标资源、风险等级和确认状态再次校验；工具可见不等于工具一定允许执行。

### 4.4 领域与 Provider 层

ToolHive 的领域核心是 Catalog 与工具调用控制：

```text
调用系统 + 业务上下文
        │
        ▼
工具调用控制 / Policy
        │
        ├── 工具发现范围
        └── 工具执行许可
                 │
                 ▼
Catalog：Provider → Tool → Tool Version → 执行配置
                 │
                 ▼
Provider：固定映射、受控出站、超时、错误转换、结果清洗；一期不代持目标系统凭据
                 │
                 ▼
外部业务系统
```

Provider 只允许调用管理员预先定义并审核过的目标服务、HTTP 方法、路径模板、参数映射和凭据引用；不能接收由 LLM 生成的任意 URL、任意方法、任意 Header 或未声明参数。

> **补充（2026-08-20，H08）**：上句中“凭据引用”属二期能力；一期不引入 `credential_ref`、不代持目标系统凭据（见一期目标 3.3 与 A11 当前结论），一期 Provider 仅允许调用不需要平台代持凭据的固定映射。

### 4.5 数据与基础设施层

| 组件 | 在总体架构中的职责 |
|------|--------------------|
| PostgreSQL | 管理账号、角色、调用系统、Catalog、策略、审计和运行事实的核心数据源。 |
| Redis 或其他共享存储 | 管理会话、互斥登录索引、登录限制、Nonce 防重放及后续共享缓存。安全敏感校验依赖的共享存储不可用时应拒绝请求。 |
| Chroma | 工具检索的派生索引，不作为工具定义、权限或版本状态的事实来源。 |
| Secret Store | 二期候选能力：保存目标系统凭据等敏感信息；一期不部署、不保存目标系统凭据。 |
| Embedding / 模型服务 | 为工具检索提供向量化能力；模型 Key 仅由 ToolHive 后端持有。 |

## 5. 核心领域对象

| 领域 | 主要对象 | 作用 |
|------|----------|------|
| 管理身份 | 管理账号、后台角色、管理操作项、管理会话 | 控制谁能维护平台及其可执行的管理动作。 |
| 调用方身份 | 调用系统、调用系统公钥、来源 IP 规则 | 控制哪个外部系统可以访问运行 API。 |
| 工具目录 | Provider、工具、工具版本、执行绑定、能力包 | 描述外部能力、可调用版本和实际执行配置。 |
| 工具调用控制 | ToolContext、能力、策略绑定、确认令牌 | 基于调用方和业务身份决定工具发现与执行范围。 |
| 可观测性 | Trace、审计记录、工具调用记录 | 追踪管理操作和运行链路，支持安全审计与问题定位。 |

Catalog 和工具调用控制的详细字段、状态机及关联规则需要在一期目标范围内单独冻结；本表仅定义领域职责，不将候选字段或状态提前视为最终设计。

## 6. 核心业务流程

### 6.1 管理配置流程

```text
管理员登录
  → 建立管理会话
  → 校验管理操作项
  → 维护调用系统 / Catalog 配置
  → 审核和发布可运行工具
  → 配置变更生效并写入审计记录
```

管理操作采用默认拒绝原则。前端菜单和按钮可据操作项隐藏，但后端 API 必须独立完成同一操作码的授权校验。

### 6.2 运行工具调用流程

```text
调用系统发起运行请求
  → Nginx 内网来源限制
  → ToolHive 校验调用系统状态、来源 IP、公钥签名和 Nonce
  → 校验运行 API 范围与工具调用控制
  → Resolve 返回允许发现的工具，或 Execute 请求具体工具
  → Provider 按已审核映射调用外部系统
  → 清洗并标准化结果，写入 Trace / 审计后返回
```

发现阶段不能泄露未授权工具的完整 Schema；执行阶段必须重新校验真实参数和高风险操作的确认状态。

## 7. 全局安全原则

- **凭据分区**：管理安全密钥、调用系统公钥和模型 Key 按用途分别保存；调用系统私钥不上传到 ToolHive，一期不保存目标系统凭据。
- **默认拒绝**：未登录、未授权、未配置来源规则、认证失败或安全依赖不可用时，默认拒绝请求。
- **固定执行映射**：LLM 只能传入满足 Schema 的业务参数，不能决定 URL、方法、认证 Header 或执行目标。
- **双层网络控制**：Nginx 控制整体网络边界，应用按调用系统进行来源 IP、签名和授权校验。
- **实时生效**：账号禁用、角色/操作项变化、调用系统停用和密钥撤销应在后续请求立即影响校验结果。
- **脱敏可追溯**：密码、会话 ID、私钥和敏感业务字段不得进入普通日志；Trace 和审计应保存必要的脱敏信息。

### 7.1 单进程安全边界

ToolHive 一期是一个应用进程和一个 Linux 服务账号。管理模块与工具应用模块通过路由、认证链、配置对象、模块依赖和凭据访问接口进行逻辑隔离，但共享同一个操作系统身份、进程内存和主机出站权限。

一期的逻辑隔离用于防止普通代码误用、接口越权和凭据原文被管理查询接口读取，不等同于进程级强隔离。如果同一进程发生任意代码执行漏洞，平台不能保证攻击代码无法读取其他模块持有的密钥或使用该进程的出站能力。

所有业务 HTTP 出站统一经过 `ProviderGateway`，但一期不读取或注入目标系统凭据。若二期引入需要凭据的 Provider，再配套建设 Secret Store、独立凭据权限和必要的执行器隔离。

### 7.2 代理信任与来源 IP 边界

一期的部署前提是 Nginx 与 ToolHive 位于同一台 Linux 服务器。ToolHive 只监听本机回环地址，Nginx 是唯一可以访问应用端口的代理；管理入口和运行入口通过不同 Nginx 路由转发到同一个 ToolHive 端口。

Nginx 必须清除调用方提交的 `Forwarded`、`X-Forwarded-For`、`X-Real-IP` 和内部入口 Header，再根据实际连接重写 `X-ToolHive-Ingress` 与 `X-ToolHive-Client-IP`。ToolHive 只有在 TCP 对端属于明确配置的可信代理范围时，才使用这些 Header 判断入口和来源 IP。

一期运行入口先由 Nginx 限制内网来源，应用再按 `system_id` 的来源 IP 规则进行校验。调用系统规则中的 `*` 只在已通过运行入口限制的范围内生效。若后续将 Nginx、WAF 或 Gateway 部署到其他服务器，必须重新配置代理链、可信 CIDR、专用私网和防火墙，不能直接沿用同机回环地址前提。
