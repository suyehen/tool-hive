# ToolHive 二期 · MCP 接入需求

> 文档版本：v0.1（首版草案，待评审）
> 更新日期：2026-09-07
> 文档状态：方向性问题已全部确认（见《待确认问题清单》），本文按确认结论整理为首版需求草案
> 关联文档：《待确认问题清单》、[《待后续实现功能》](../../待后续实现功能/待后续实现功能.md)

## 1. 背景与目标

ToolHive 二期第一个功能是 MCP 接入：让平台作为 **MCP Server**，把已发布的 Catalog 工具对外暴露给支持 MCP 的客户端（Claude Desktop、Cursor、自研 Agent 等）通过 **Streamable HTTP** 发现和调用。工具仍只定义一次、审核一次、执行一次，HTTP 与 MCP 只是两个调用入口。

目标不是"把现有 HTTP 链路复制一套"，而是给"同一批 Catalog 工具资产"增加第二个受控入口：

- 外部 MCP 客户端可发现、调用平台授权的工具；
- 调用全程经过与 HTTP 同级的调用控制、Schema 校验、Provider 执行与 Trace（风险确认实现延后，见 5.6）；
- MCP 拥有独立的管理菜单、客户端身份与授权模型，不与 HTTP 运行链路混放；
- 第一批仅交付同步执行；异步与流式执行列入待后续实现功能。

## 2. 前置基线

以下基线是本文全部需求的前提（源自《待确认问题清单》"固定基线"）：

1. **无历史数据包袱**：当前系统无业务数据，任何情况允许删表、删库重建；设计不为此前数据结构做兼容或数据迁移。
2. **工具单一事实源**：一个工具在 Catalog 中定义一次、实现一次、审核一次；实际执行只定义一处，修改执行只改一处。
3. **多协议默认支持**：新接入 Catalog 的工具同时支持 HTTP 与 MCP 两个入口，不按协议复制工具或执行逻辑；默认全开，可分别停用（见 5.9）。
4. **链路隔离**：HTTP 与 MCP 是两条独立链路，管理菜单、运行入口不混在一起；共享的只有 Catalog 工具资产与治理服务（调用控制、确认、检索、Trace、审计）。

## 3. 范围

### 3.1 本批做

- ToolHive 作为 MCP Server，通过官方 Python SDK v2 以 Streamable HTTP 对外暴露工具（方向 A）。
- MCP 客户端独立建模与管理：一客户端一 Bearer Token，客户端可启用/停用、来源限制可配置（默认仅内网）。
- MCP 客户端显式授权（默认拒绝），粒度与 HTTP 侧一致：命名空间 / 能力包 / 工具三级 + 能力包→客户端授权入口（A2）。
- MCP 工具发现与调用复用 Catalog 与现有 execute 决策链；识别需确认（高风险/写操作）工具，确认流程落地前在 MCP 侧明确拒绝、不执行（见 5.6）。
- 独立"MCP 接入"管理一级菜单，五个页面：接入配置（含运行状态摘要）、客户端与授权、暴露工具（只读）、调用记录、测试调试。
- 调用记录落地：运行 Trace 增加渠道维度（HTTP / MCP）与 MCP 客户端维度，管理端提供 MCP 渠道查询入口。
- 工具协议开关：工具支持全局启停 + 协议维度开关（http_enabled / mcp_enabled，默认全开）。
- 协议版本跟随官方 SDK v2 做握手协商，不做人为单版本锁定；提供协议版本支持范围的展示/约束配置。

### 3.2 本批明确不做

- ToolHive 作为 MCP Client 收编外部 MCP Server（方向 B）及双向模式（C）。
- OAuth2 / mTLS 等 MCP 客户端认证形态（沿用 Bearer Token 最小形态，留后续候选）。
- 异步执行、流式执行、取消、回调与死信治理（已登记《待后续实现功能》）。
- MCP 风险确认流程（协议表达与确认交互，D1 待确认）：延后至 MCP 接入代码开发完成后实现与调整；第一批对需确认工具在 MCP 侧明确拒绝、不执行。
- MCP resources / prompts 服务端能力（本批只暴露 tools；不声明相应能力）。
- 通用 MCP Client 实验室或外部 MCP 连接调试（管理端测试调试仅回环测试本平台 Server）。
- 管理端完整可观测看板、告警与审计报表（沿用二期整体规划，本批只交付 MCP 渠道调用记录查询）。

### 3.3 完成口径

本批完成以"接入、执行、可观测"三侧闭环齐备为标准，与 HTTP 链路同等完整：

- 接入侧：管理员可配置 MCP Server 与客户端授权，工具发布后可被授权客户端发现；
- 执行侧：调用经过调用控制、Schema 校验、Provider 执行，返回标准化结果；
- 可观测侧：调用落 Trace，管理端可查 MCP 渠道调用记录；关键管理变更落审计。

## 4. 总体形态

### 4.1 两条链路

```text
HTTP 链路（既有）                 MCP 链路（本期新增）
─────────────────────             ─────────────────────────────
管理：工具目录 / 调用系统 / ...    管理：MCP 接入（五个页面，独立一级菜单）
运行：/api/runtime/v1/**          运行：MCP 端点（Streamable HTTP，独立路径）
身份：CallerSystem + 请求签名     身份：MCP Client + Bearer Token
授权：调用系统工具范围            授权：MCP 客户端工具范围（A2，对齐 HTTP）
──────────────────────────────────────────────────────────────
共享：Catalog 工具资产（工具/版本/审核/发布/能力包/Provider）
共享：调用控制 · 确认 · Schema 校验 · ProviderGateway · Trace · 审计
```

MCP 运行端点与管理链路分开，并遵守现有部署约束：默认仅内网开放，来源限制可配置；对外域名需显式配置 Host/来源白名单。

### 4.2 运行请求链路

```text
MCP 客户端
  → Streamable HTTP（Authorization: Bearer <token>）
  → MCP Server 端点（官方 SDK v2 挂载于现有 FastAPI 应用）
  → Token 校验（客户端状态/Token 有效性/来源限制）
  → MCP 适配层（tools/list、tools/call 协议翻译）
  → 调用控制（授权范围 × Catalog 实时状态 × mcp_enabled）
  → 需确认工具检查（本批明确拒绝、不执行；确认流程延后）→ Schema 校验
  → ProviderGateway → 结果标准化 → Trace
```

## 5. 功能需求

### 5.1 MCP 接入配置

管理页面提供 MCP Server 级配置与运行摘要：

- 全局启停：MCP 链路整体启用/停用开关；停用后所有 MCP 请求被拒绝；
- Server 信息：名称、描述、对外端点路径、接入地址展示；
- 网络与传输安全：来源限制（默认仅内网）、对外 Host 白名单/传输安全配置、会话与请求限制；
- 协议版本：展示当前 SDK 支持的协议版本范围，默认取 SDK 能力全集；保留约束配置位；
- 连接示例：为不同客户端形态提供接入配置示例（复制即用）；
- 运行摘要：Server 运行状态、当前会话/调用概况、最近错误，作为轻量"运行状态"页签内容，不单独建立空页面。

### 5.2 MCP 客户端与认证

- MCP 客户端独立建模，不复用调用系统（CallerSystem）身份；
- 一客户端一 Bearer Token：管理端签发时明文只展示一次，数据库只保存单向哈希（沿用现有密码哈希做法）；
- Token 支持重置/吊销，重置或吊销后后续请求立即失效；客户端启用/停用同样实时生效；
- 客户端可配置来源限制，默认仅内网；
- Token 等价于密码管理：泄露后的止血手段为吊销/重置 + 来源 IP 白名单 + HTTPS；管理页需给出相应提示；
- Token 校验在协议解析前完成（官方 SDK v2 资源服务器校验接口），未携带或校验失败返回标准 401，不执行任何工具也不泄露工具存在性；
- 校验通过后请求身份携带 client_id，供授权、执行、Trace 使用。

### 5.3 客户端授权（A2）

- 授权模型：**显式授权 + 默认拒绝**，与 HTTP 调用系统一致；
- 粒度：命名空间 / 能力包 / 工具三级范围，另支持能力包→客户端授权入口；任一命中即放行；
- 范围编码保存时做 Catalog 真实引用校验（编码不存在、已归档等拒绝保存或返回失效提示）；
- 授权主体为 MCP 客户端（client_id），管理入口位于 MCP 菜单"客户端与授权"；
- 授权不写进 Token：Token 只回答"是谁"，范围由服务端授权记录决定，每次调用实时判定。

### 5.4 工具暴露与生命周期

- 工具定义、版本、Schema、审核、发布、启停完全复用 Catalog 流程，不另设 MCP 独立生命周期；
- MCP 工具名直接映射为 Catalog 完整编码（namespace.tool_code），不做二次改名；每级命名由 Catalog 唯一性约束与提交查重保证；
- MCP 侧可发现集合（tools/list）= 客户端授权内 ∩ 工具启用 ∩ `mcp_enabled=true` ∩ 可发现 ∩ 存在已发布默认版本且 Provider 可用；
- 不在授权内或不可用工具不出现在 tools/list，也不在 tools/call 中泄露存在性；
- 工具停用/撤回、协议开关变更、客户端授权变更后，后续调用立即生效；已受理在途请求允许自然完成；
- 本批 Server 只声明 tools 能力，不暴露 resources / prompts；
- 工具协议开关属于工具定义属性（见 5.9），MCP 菜单"暴露工具"为只读视图，编辑入口留在共享工具目录。

### 5.5 调用执行

- `tools/call` 完全复用现有 execute 决策链：授权判定 → 需确认工具检查（本批明确拒绝、不执行）→ JSON Schema 参数校验 → ProviderGateway → 结果标准化 → Trace；
- 每次调用实时重新判定，不信任客户端缓存的 tools/list 快照；
- 版本选择沿用 Catalog 默认版本语义（已发布默认版本；显式版本不在本批 MCP 调用契约内，除非设计阶段确认需要）；
- 本批同步执行：调用等待执行结果返回；异步/流式另行列后续；
- Provider 返回按声明的 output_schema 校验，契约漂移按 Provider 错误处理；
- 错误映射：协议层错误转换为 MCP 标准错误语义，不返回堆栈、内部地址或未授权信息。

### 5.6 风险确认

- 方向已确认：MCP 无 HTTP method 语义，确认需求以**工具风险等级 + 写操作绑定**驱动（复用 Catalog 风险等级），与调用方是否来自 MCP 无关；
- 实现延后（D1 待确认）：MCP 侧确认流程（协议表达、确认凭据形态、确认交互）本批不实现，待 MCP 接入代码开发完成后实现与调整；候选方案见《设计冻结》第 8 节；
- 第一批兜底：识别为需确认（高风险/写操作）的工具在 MCP 渠道明确拒绝并返回暂不支持/不可用语义，**不静默放行**；
- 协议级调试台的确认分支随 D1 落地后补充（见 5.8）。

### 5.7 Trace 与调用记录

- `runtime_trace_log` 增加渠道（channel：http / mcp）与 MCP 客户端（mcp_client_id）维度及相应索引（允许删库重建，不做兼容迁移）；
- MCP 请求全链路 Trace：认证、授权、执行、Provider、请求完成等事件均落库（确认事件随 D1 落地后补充）；
- 管理端"MCP 接入 → 调用记录"提供按时间、客户端、工具、结果过滤的列表与事件链详情；
- 查询服务做渠道通用化设计，本批先开放 MCP 渠道入口，HTTP 侧查询入口留后续批次复用；
- Trace 敏感信息口径沿用现有明文记录 + 脱敏 TODO 约定，本批不单独扩大记录范围。

### 5.8 协议级测试调试

- MCP 菜单提供协议级调试台（区别于 Catalog 既有"工具测试"）：
  - 以专用内置测试客户端身份，通过 SDK 的 MCP 客户端对本平台实际挂载的 MCP 端点发起真实会话（initialize → tools/list → tools/call）；
  - 输入：选择工具、参数 JSON（高风险确认开关与确认分支随 D1 延后落地，第一批测试"需确认工具被拒绝"语义）；
  - 输出：协议层消息摘要、标准化结果、trace_id；Trace 标注 `source=mcp-console-test`，与真实调用区分；
- 调试台只回环测试本平台 Server，不做成通用 MCP Client 实验室；
- Catalog 既有"工具测试"（执行级）继续复用，本批不在 MCP 菜单重复建设。

### 5.9 工具协议开关

- 工具增加两层启停：
  - 工具维度全局启停：停用则 HTTP 与 MCP 全部不可用（沿用现有工具启停）；
  - 协议维度开关：`http_enabled` / `mcp_enabled`，默认全开，关闭仅影响对应协议入口；
- 两层独立叠加，执行逻辑仍只有一份，开关是入口调用控制前的检查项；
- 新增工具默认两协议都开启；存量工具在可删库重建前提下按默认全开落地；
- 开关位于工具定义上，由共享工具目录管理；MCP 菜单展示只读状态。

## 6. 数据与接口变化（初版清单，以设计冻结为准）

### 6.1 领域对象

| 对象 | 变化方向 |
|------|----------|
| Catalog 工具 | 新增 `http_enabled` / `mcp_enabled` 协议开关字段 |
| MCP Server 配置 | 新增：全局启停、端点路径、Server 信息、来源/传输安全、协议版本范围 |
| MCP 客户端 | 新增：客户端编码、名称、状态、来源限制、Token（仅哈希）、Token 重置/吊销 |
| MCP 客户端授权 | 新增：命名空间 / 能力包 / 工具范围 + 能力包→客户端授权（对齐 HTTP 授权语义） |
| 运行 Trace | `runtime_trace_log` 新增 `channel`、`mcp_client_id` 维度与索引 |
| 管理操作码 | 新增 MCP 域操作码（如 MCP Server 查看/配置、客户端管理、授权、调用记录、调试执行），映射到菜单与后端校验 |

### 6.2 依赖变化

- 引入官方 MCP Python SDK：`mcp>=2,<3`（Python 3.10+，现有 `>=3.11.6,<3.12` 满足）；
- 随 SDK 提升依赖下限并新增硬依赖：pydantic>=2.12（现有 >=2.10 需上调）、anyio>=4.9、sse-starlette>=3.0、opentelemetry-api>=1.28、mcp-types、typing-extensions>=4.13；
- SDK v2 以 httpx2 取代 httpx：项目 HTTP Provider 仍在用 httpx，需显式保留 httpx 依赖并审计异常分支（httpx 与 httpx2 类型不可互换）；
- 部署形态不变：SDK 以 Starlette 子应用形式挂载进现有 FastAPI 应用，同一进程运行；宿主应用 lifespan 需自行管理 MCP 会话管理器。

## 7. 验收标准

1. 管理员可在 MCP 菜单完成 Server 配置、客户端创建与 Token 签发、客户端授权配置；客户端与授权变更实时生效。
2. 已发布且 mcp_enabled 的工具可被授权客户端通过 tools/list 发现，工具名等于 Catalog 完整编码，Schema 与 Catalog 一致。
3. 授权客户端可调用已发布默认版本，经 Schema 校验后正确返回结果；未授权/停用/关闭协议的调用被拒绝且不泄露工具信息。
4. 需确认（高风险/写操作）工具在 MCP 渠道被明确拒绝、不执行（确认流程延后，不静默放行）。
5. 调用全过程（认证、授权、执行、Provider、完成）落 Trace；管理端"MCP 调用记录"可按客户端/工具/时间查询到该调用。
6. 工具全局停用、协议开关关闭、客户端停用/Token 吊销后，后续 MCP 调用立即被拒，在途请求自然完成。
7. 协议版本按 SDK 协商工作：官方 MCP Inspector 与 SDK 客户端实连必测通过；Cursor / Claude Desktop 按其支持性抽测并记录兼容矩阵，受限项登记《待后续实现功能》。
8. HTTP 既有闭环不受影响：协议开关默认全开情况下 HTTP 行为保持；HTTP 工具仍可独立配置关闭 MCP 暴露。
