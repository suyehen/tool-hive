## 固定基线（所有设计决策的前提）

1. **无历史数据包袱**：当前系统无业务数据，任何情况下都允许删表、删库重建；设计上不为此前的数据结构做兼容或数据迁移，直接按目标结构落地。
2. **工具单一事实源**：一个工具在 Catalog 中定义一次、实现一次、审核一次；工具的实际执行只定义一处（Provider 执行），修改执行只需改这一处。
3. **多协议默认支持**：新接入 Catalog 的工具同时支持 HTTP 与 MCP 两个调用入口，不按协议复制工具或执行逻辑。
4. **链路隔离原则**：HTTP 与 MCP 是两条独立链路，管理菜单、运行入口不混在一起；共享的只有 Catalog 工具资产与治理服务。

## 第 1 组 · 确认留痕

**结论（2026-09-06）：**

- 方向选 A：ToolHive 作为 MCP Server，把平台已发布的工具对外暴露给 MCP 客户端调用；第一批不做 B（接入外部 MCP Server）与 C（双向）。
- 隔离尺度：Catalog 工具资产域共用，链路域隔离。HTTP 与 MCP 各自拥有独立的接入主体、认证方式、授权、运行策略、入口与菜单；共享的只有工具定义、版本审核、Schema、Provider 执行与治理服务（调用控制 / 检索 / 确认 / Trace）。
- 完成口径：与 HTTP 工具同等完整闭环，即管理侧可配置 MCP Server 与客户端授权、工具发布后可被发现并调用、调用经过调用控制与风险确认、执行落 Trace、管理端可查调用记录。
- 取消的两个边界问题（因“可删表重建 + 工具默认双协议”而不再存在）：① 不需要为 MCP 单独设计执行绑定，Catalog 执行定义统一、双入口共用；② 不按 builtin/http 二选一限制暴露范围，Provider 类型由 Catalog 决定。
- 保留的独立配置：MCP Server 对外暴露哪些工具、允许哪些客户端调用，仍属 MCP 接入侧授权配置，不复制工具本身。

## 第 2 组 · 确认留痕

**结论（2026-09-06）：**

- #4：MCP 工具复用 Catalog 的“版本 → 送审 → 审核 → 发布”流程，不另设 MCP 独立流程。
- #5：MCP 工具的 input_schema / output_schema 直接复用 Catalog 定义，不独立维护。
- #6：工具启停/撤回/协议开关关闭后，对后续 MCP 调用立即生效；已发出的在途请求允许自然完成，不主动中断。MCP 客户端即使缓存 tools/list 旧结果，tools/call 仍按 Catalog 实时状态校验并拒绝。
- #7：MCP 工具名直接取 Catalog 完整编码（namespace.tool_code）。namespace、tool_code 每级命名由用户手填，提交时做重复校验——Catalog 已通过唯一约束 + 创建查重实现，重名直接拒绝提交，不会出现映射后 MCP 工具名重复的情况。因此 MCP 适配层不做第二次查重、不提供改名或手工指定机制，仅校验协议对工具名的长度与字符合法性要求。

**新增结论（2026-09-06）：**

- 工具启停模型为两层：**工具维度**（全局启停，停用则 HTTP、MCP 全部不可用）与**协议维度**（http_enabled / mcp_enabled 各自独立，默认全开，关闭只影响对应协议入口）。两层独立叠加。
- 协议开关位于工具定义上，属工具级属性，不按调用方区分：关闭某协议后，该协议下所有调用方均不可用该工具。
- 执行逻辑仍只有一份；协议开关是入口调用控制前的检查项，不影响“执行只改一处”原则。
- 该需求确认于第 2 组讨论中，已并入工具与生命周期设计。

## 第 4 组 · 确认留痕

**结论（2026-09-07）：**

- #11：采用官方 Python SDK（当前稳定行为 v2，`mcp>=2,<3`）。基于官方文档与代码核实的事实如下：
  - SDK v2 要求 Python 3.10+；项目当前约束 `>=3.11.6,<3.12` 已满足，无需为接入 MCP 放宽；后续若 SDK 或依赖要求变化，可按需调整本地 Python 版本约束（用户已确认允许调整）。
  - SDK v2 提升了部分依赖下限并新增硬依赖：pydantic>=2.12（项目现为 >=2.10.0，需上调）、anyio>=4.9、sse-starlette>=3.0、opentelemetry-api>=1.28、mcp-types（与 mcp 精确锁定）、typing-extensions>=4.13；`httpx` 与 `httpx-sse` 被 `httpx2` 取代，SDK 不再安装 httpx。
  - 项目 HTTP Provider 执行器直接使用 httpx（`http_executor.py`）；升级依赖后需显式保留项目自身对 httpx 的依赖声明，并审计 `except httpx.*` 异常分支——SDK 侧抛的是 httpx2 类型，两者运行时类型不可互换，不能混用。
  - 部署形态：SDK 以 `streamable_http_app()` 返回 Starlette 子应用，可直接挂载进现有 FastAPI 应用（同一 uvicorn 进程），不需要独立部署一个 MCP 服务进程；不改变现有部署拓扑。
  - 挂载注意点（官方 v2 文档"Add to an existing app"）：被挂载子应用的 lifespan 不会由 FastAPI 自动执行，宿主应用 lifespan 必须手动进入 `mcp.session_manager.run()`，否则首个请求报 `RuntimeError: Task group is not initialized`；`streamable_http_path`、`transport_security` 等传输参数在 `streamable_http_app()` 上配置（v2 已从 MCPServer 构造器移出）。
  - 传输安全默认值：SDK 默认只接受发往 localhost 的请求（DNS rebinding 防护），对外提供真实域名/入口时需显式配置 `transport_security` 的 Host 白名单——与 #10“来源限制可配置、默认仅内网”一致。
  - ToolHive 的工具集合来自 Catalog、随版本发布动态变化，与 SDK 面向静态装饰器注册的示例不同；具体采用 MCPServer 动态注册或低层 Server 的 on_* 处理器，在设计阶段确认，不构成选型阻塞。
- #12：传输采用 Streamable HTTP。理由：它是 MCP 规范的现行标准 HTTP 传输，替代已进入维护状态的 SSE；SDK v2 对它有第一等支持；stdio 适合本地子进程形态，与 ToolHive“平台内运行入口”的定位不符；SSE/stdio 不作为第一批入口。目标客户端为支持 Streamable HTTP 的 MCP 客户端（Claude Desktop / Cursor / 自研 Agent 等），具体实连验收范围见管理与验收组 #20。
- #13：MCP 调用完全复用现有 execute 决策链（调用控制 → 确认 → 参数校验 → ProviderGateway → Trace），不新增独立执行路径。MCP 适配层只做协议翻译：工具发现（tools/list 映射 Catalog 工具）与调用转换（tools/call 解包 → 进入决策链 → 结果回包）。
- #14：MCP 无 HTTP method 语义，确认改为以工具风险等级驱动：高风险工具需要调用方确认后才执行，规则复用 Catalog 的风险等级定义；与调用方是否来自 MCP 无关。**补充（2026-09-07）**：MCP 侧确认流程实现延后（D1 待确认），不阻塞第一批代码开发；第一批对需确认工具在 MCP 渠道明确拒绝、不执行，不静默放行。
- #15：第一批只支持同步执行（调用等待执行结果返回，与 HTTP 同步语义一致）。异步执行与流式执行列入《待后续实现功能》文档，进入二期后续批次候选，启动前单独确认需求与验收。

## 第 5 组 · 确认留痕

**结论（2026-09-07）：**

- #18：MCP 管理区采用独立一级菜单（如“MCP 接入”），下设五个页面，不在 HTTP/共享 Catalog 菜单中混放：
  1. **接入配置（含运行状态摘要）**：MCP Server 全局启停、Server 名称/描述、对外端点路径、协议版本支持方式、来源限制（默认仅内网）与 transport security Host 白名单、会话与请求限制；展示接入地址及各类客户端连接配置示例。页面顶部提供轻量“运行摘要”（运行状态、会话数、最近错误），不单独开“运行状态”空页面，二期可观测性基建到位后再拆。
  2. **客户端与授权**：MCP 客户端 CRUD、Bearer Token 签发/重置/吊销（只显示一次）、客户端启停、来源限制；客户端详情中配置该客户端可调用的工具范围（范围模型未定，见派生项 #21）。
  3. **暴露工具（只读）**：展示当前从 MCP 侧 tools/list 可见的工具（full_code、schema、风险、状态、mcp_enabled），可跳转共享 Catalog 详情；不做编辑，mcp_enabled 与工具定义、版本、审核、发布一律在共享“工具目录”维护，避免同一字段两个入口。
  4. **调用记录**：MCP 渠道过滤的 Trace 列表（时间、客户端、工具、结果、trace_id）与事件链详情；查询服务做通用化并按渠道（HTTP/MCP）过滤，本批次先给 MCP 建入口，HTTP 侧后续复用（见派生项 #22）。
  5. **测试调试**：见 #19。
  - 明确不进 MCP 菜单：Provider 配置、能力包、工具审核、发布历史等 Catalog 领域内容。
- #19：测试分两层，职责分离：
  - **执行测试（复用，不重复建设）**：共享 Catalog 现有的管理端“工具测试”（test-execute，走统一 ProviderGateway + 参数校验 + 审计 + Trace），与协议无关，MCP 工具同样适用；一期仅放行 builtin 的范围限制随二期执行绑定能力放开另行评估。
  - **协议级调试台（MCP 菜单新增，第一批交付）**：用专用内置测试客户端身份，通过 SDK 的 MCP 客户端对本平台实际挂载的 MCP 端点发起真实会话（initialize → tools/list → tools/call），输入为工具、参数 JSON、高风险确认开关，输出为协议层原始消息摘要、标准化结果与 trace_id；Trace 标记 source=mcp-console-test，与真实调用区分。只回环测试自身 Server，不做成通用 MCP Client 实验室（不滑向已移除的方向 B）。
- #20：两个子问题的口径：
  - **协议版本**：跟随官方 SDK v2 支持的协议版本做握手协商，不人为锁定单版本；接入配置中保留“协议版本支持范围”的展示/约束项，默认取 SDK 能力全集。理由：SDK 已完成协商，兼容成本趋近于零；平台没有模拟特定旧版本协议的业务理由。
  - **验收实连**：分层进行。必测：官方 MCP Inspector + SDK 自带/参考客户端（覆盖协议细节与确定性断言）；抽测：Cursor、Claude Desktop 等真实客户端按其支持性实测。远程 HTTP MCP 客户端接入方式存在差异（部分生态倾向 OAuth），与 #9 Bearer Token 可能产生兼容边界，不把“所有客户端都能连”当验收标准；以兼容矩阵记录必测通过项与已知受限项，受限项记入《待后续实现功能》。

**派生确认项结论：**

- #21 ✅（2026-09-07）：MCP 客户端采用**显式授权 + 默认拒绝**，粒度对齐 HTTP 侧 A2 模型——命名空间 / 能力包 / 工具三级范围 + 能力包→客户端授权入口；任一命中即放行，无授权默认拒绝。授权主体为 MCP 客户端（client_id），不沿用调用系统表；范围编码保存时复用 Catalog 引用校验。关联口径：
  - **Token 认证**：静态 Bearer Token 等价于密码，一客户端一 Token；签发时明文只显示一次，数据库只存单向哈希（沿用现有密码哈希方式）；校验经官方 SDK v2 资源服务器接口（TokenVerifier + AuthSettings）在协议解析前完成，并复核客户端启用状态、Token 是否被重置/吊销、来源 IP（默认仅内网）；校验通过后请求身份挂 client_id，供授权、执行与 Trace 使用。Token 泄露的缓解以管理端重置/吊销（后续请求立即失效）+ 来源 IP 白名单 + HTTPS + 哈希存储 + Trace 追溯为主；OAuth client credentials / mTLS 保持后续候选，不改变第一批 Bearer 形态。
  - **范围判定**：Token 只回答“是谁”，不携带工具授权；可发现集合 = 客户端授权内 ∩ 工具启用 ∩ mcp_enabled ∩ 可发现 ∩ 已发布默认版本且 Provider 可用；tools/call 每次实时重判，不信任客户端缓存的 tools/list 快照。
- #22 ✅（2026-09-07）：Trace 渠道维度：`runtime_trace_log` 新增 `channel`（http/mcp）与 `mcp_client_id` 维度及索引（允许删库重建，不做兼容迁移）；管理端 Trace 查询服务通用化，本批次仅开放 MCP 渠道入口，HTTP 侧查询入口留后续批次。
- #23 ✅（2026-09-07）：真实客户端兼容矩阵：必测 Inspector + SDK 客户端；抽测 Cursor / Claude Desktop；逐客户端记录接入方式、协议版本协商结果、认证兼容性与已知限制；受限项登记《待后续实现功能》。
