# ToolHive 二期 · MCP 接入开发计划

> 文档版本：v0.1
> 更新日期：2026-09-07
> 文档目的：将 MCP 接入功能拆解为可执行的功能清单与实施顺序，作为任务拆分、开发执行和阶段验收的依据。
> 范围说明：正式交付范围与边界以《需求》《设计冻结》为准；D1（MCP 风险确认流程）延后，不阻塞本计划。

## 1. 阶段目标

MCP 接入形成最小、可控的 MCP 工具调用闭环：

```text
管理员配置 MCP Server 与客户端
  → 客户端 Bearer Token 认证
  → MCP 客户端授权（A2）与工具暴露判定（tools/list）
  → tools/call 复用 Catalog execute 决策链
  → Provider 执行返回标准化结果
  → Trace 落库，管理端可查 MCP 调用记录
```

HTTP 与 MCP 两条链路隔离，共享 Catalog 工具资产与治理服务；本批只做 MCP Server（方向 A），同步执行，风险确认流程延后（D1）。

## 2. 实施前置：已冻结设计

实现依据《需求》与《设计冻结》。关键前置如下：

| # | 主题 | 冻结/状态 |
|---|------|-----------|
| 1 | SDK 与部署 | 官方 SDK v2（mcp>=2,<3），`streamable_http_app()` 挂载进现有 FastAPI；宿主 lifespan 进入 `session_manager.run()` |
| 2 | 端点与能力 | 独立 `/mcp` 路径（可配置），仅声明 tools，协议版本跟 SDK 协商 |
| 3 | 认证 | Bearer Token 一客户端一 Token；只存哈希；SDK TokenVerifier 校验；来源限制默认内网 |
| 4 | 授权 | 显式授权 + 默认拒绝；A2（命名空间/能力包/工具 + 能力包→客户端授权）；范围保存做 Catalog 引用校验；实时判定 |
| 5 | 执行 | tools/call 完全复用 execute 决策链；同步；默认已发布版本；需确认工具明确拒绝、不执行（D1 兜底） |
| 6 | 管理 | 独立"MCP 接入"一级菜单五个页面：接入配置、客户端与授权、暴露工具（只读）、调用记录、测试调试 |
| 7 | Trace | `runtime_trace_log` 增加 `channel` / `mcp_client_id` 维度，管理端开放 MCP 渠道查询 |
| 8 | D1 风险确认 | 延后待确认（记录于《待确认问题清单》《设计冻结》《待后续实现功能》）；开发完成后实现与调整 |
| 9 | D2/D3 技术细节 | SDK 鉴权接线与挂载/生命周期细节在阶段 0 技术预研中实证；如与冻结草案结论不一致，追加补充记录后再进入建模 |

## 3. 功能拆解

### 3.1 依赖与基础设施

- pyproject 引入 `mcp>=2,<3`；pydantic 升到 >=2.12，anyio、sse-starlette、opentelemetry-api、mcp-types、typing-extensions 对齐 SDK v2 下限；
- 显式保留 httpx 依赖（HTTP Provider 在用），审计 httpx/httpx2 异常分支；
- 技术预研 Spike：现有 FastAPI 上完成最小可运行 MCP 端点（initialize → tools/list → tools/call），验证挂载、lifespan、传输安全默认行为与 TokenVerifier 接线；
- 全量测试与 ruff 保持通过，作为依赖升级后的回归基线。

### 3.2 数据模型（可直接改基线，不做迁移）

- `catalog_tool` 增加 `http_enabled` / `mcp_enabled`（默认 true）；
- 新增 MCP Server 配置（全局启停、端点路径、来源/传输安全、协议版本范围）；
- 新增 MCP 客户端（编码、名称、状态、来源限制、Token 哈希、Token 重置/吊销状态）；
- 新增 MCP 客户端授权范围（命名空间 / 能力包 / 工具三级 + 能力包→客户端授权）；
- `runtime_trace_log` 增加 `channel` / `mcp_client_id` 及索引；
- 管理操作码增加 MCP 域操作码并纳入启动同步与角色分配。

### 3.3 认证链路

- Token 签发（明文仅显示一次）、哈希入库、重置/吊销、客户端启停；
- SDK 资源服务器校验接入：TokenVerifier 完成哈希比对 + 客户端状态 + Token 有效性 + 来源限制；
- 未认证/无效 Token 在协议解析前 401，不执行、不泄露工具信息。

### 3.4 授权与工具暴露

- 将 HTTP 调用系统范围判定抽象为"授权主体 × 授权范围"通用计算，HTTP/MCP 共用语义，避免口径漂移；
- MCP A2 授权解析：命名空间 / 能力包 / 工具 + 能力包→客户端授权，默认拒绝；
- tools/list 构建：客户端授权内 ∩ 工具启用 ∩ mcp_enabled ∩ 可发现 ∩ 已发布默认版本且 Provider 可用；
- 工具名直接映射 Catalog 完整编码，schema/描述复用 Catalog；
- HTTP 侧回归：调用控制接入 `http_enabled` 过滤，默认全开行为不变。

### 3.5 tools/call 执行闭环

- MCP 适配层解包 → 授权与实时状态重判 → 需确认工具拒绝（D1 兜底）→ JSON Schema 校验 → ProviderGateway → output_schema 校验 → 结果标准化为 MCP 响应；
- 错误映射：401、未授权/不可用、参数错误、Provider 错误、内部错误分别映射 MCP 错误语义；
- 同步执行，默认已发布版本；显式版本不进入本批契约；
- 事件落 Trace：认证、授权、执行、Provider、请求完成，带 channel 与 client_id。

### 3.6 管理端（MCP 一级菜单）

- 接入配置：全局启停、Server 信息、端点路径、来源/传输安全、协议版本范围、连接示例、运行摘要；
- 客户端与授权：客户端 CRUD、Token 签发/重置/吊销、来源限制、A2 授权配置；
- 暴露工具：只读展示 MCP 可发现集合，跳转共享 Catalog；
- 调用记录：MCP 渠道 Trace 列表与事件链详情；
- 测试调试：协议级调试台（见 3.7）；
- 前端菜单与按钮按新操作码控制，后端 API 独立鉴权。

### 3.7 协议级测试调试

- 专用内置测试客户端；以 SDK MCP 客户端对实际挂载端点发起 initialize → tools/list → tools/call；
- 输出协议层消息摘要、标准化结果、trace_id；Trace 标注 `source=mcp-console-test`；
- 高风险确认分支随 D1 延后；第一批验证"需确认工具被明确拒绝、不执行"；
- 只回环测试本平台 Server。

### 3.8 部署交付与验收

- MCP 运行入口网络边界：来源限制默认仅内网；对外域名需配置 Host/来源白名单；
- Nginx 路由/Header 清洗与配置示例、verify 脚本更新；
- 端到端验收：客户端创建 → Token 签发 → 授权 → tools/list → tools/call → Trace 查询；
- 兼容矩阵实测：Inspector + SDK 客户端必测；Cursor / Claude Desktop 抽测并记录；
- HTTP 既有闭环回归；文档对齐（需求/设计/开发完成情况/待后续功能）。

## 4. 可复用现状

| 资产 | 说明 |
|------|------|
| Catalog / 工具版本 / 审核发布 / 能力包 / Provider | 直接复用，不新建工具生命周期 |
| execute 决策链（调用控制、Schema 校验、ProviderGateway、结果标准化） | tools/call 直接复用 |
| TraceService / runtime_trace_log | 增加渠道维度后复用 |
| AuditService / management_audit_log | 管理操作接入 |
| 管理操作码体系与前端按钮/菜单控制 | 新增 MCP 域操作码后复用 |
| CallerToolScope 授权模型与判定逻辑 | 抽象为通用主体后为 MCP 复用 |
| 前端布局、测试基础设施、部署交付物 | 沿用 |

## 5. 工程约定

- 数据库结构变更直接修改 `sql/init.sql`，不保留历史迁移（无历史数据，可删库重建）；
- 状态约束使用代码层枚举，数据库不加 CHECK；
- 管理操作码集中声明于 `core/operation_codes.py`，启动同步；
- 关键管理操作接入 `AuditService`；敏感凭据只存哈希，不进入日志/Trace/审计；
- 后端只注入所需配置分区，不依赖完整 Settings；
- 测试与实现同步编写，每阶段跑通全量测试、ruff，前端改动跑通 tsc；
- SDK 版本固定 `mcp>=2,<3`，升级需全量回归并追加补充记录。

## 6. 实施顺序

| 阶段 | 内容 | 依赖 | 完成标志 |
|------|------|------|----------|
| 0 | 技术预研与依赖基线：SDK 挂载/鉴权 Spike、依赖升级、HTTP 回归 | 无 | 最小 MCP 端点跑通 initialize/tools/list/call；测试与 ruff 全绿；D2/D3 结论落档 |
| 1 | 数据模型与基础服务：协议开关、MCP Server/客户端/Token/授权表、Trace 渠道维度、操作码 | 阶段 0 | 表结构与枚举就绪；Token 签发/重置/吊销服务可用；引用校验生效 |
| 2 | 认证链路：TokenVerifier 接入、401 语义、来源限制 | 阶段 1 | 有效 Token 通过、无效/停用/吊销/来源不符被拒并留 Trace |
| 3 | 授权与暴露：主体抽象、A2 范围解析、tools/list、mcp_enabled、HTTP 回归 | 阶段 1、2 | 可发现集合正确；HTTP 既有行为回归通过 |
| 4 | tools/call 执行闭环：决策链复用、需确认拒绝、错误映射、Trace | 阶段 3 | 授权客户端可端到端同步调用低风险工具；需确认工具被拒绝且不执行 |
| 5 | 管理端：五个页面 + 管理 API + 操作码控制 | 阶段 1–4 | 管理员可在 MCP 菜单完成配置、客户端授权、调用记录查询 |
| 6 | 协议级调试台与兼容矩阵：内置测试客户端、Inspector/SDK 必测、Cursor/Claude 抽测 | 阶段 4、5 | 调试台可用；兼容矩阵落档，受限项登记待后续功能 |
| 7 | 部署交付与端到端验收：入口网络、verify、HTTP 回归、文档 | 全部 | MCP 接入完成判定全过 |

顺序说明：

- 阶段 0 必须先做：SDK v2 挂载/鉴权接线是后续模型与契约的前提，实证结论不一致时以补充记录修正设计冻结后再建模；
- 阶段 1 与阶段 2 可部分并行（认证依赖模型），建议按上表串行推进保证可验收；
- D1 风险确认不进入阶段 0–7：阶段 4 只落地"需确认工具拒绝"兜底；代码开发完成后作为后续迭代实现与调整，避免阻塞主线；
- 每阶段内部按"模型 → 服务 → API → 前端 → 测试 → 文档"推进。

## 7. 完成判定

以《需求》第 7 节验收标准为准：

1. 管理员可在 MCP 菜单完成 Server 配置、客户端创建与 Token 签发、客户端授权；变更实时生效。
2. 已发布且 mcp_enabled 的工具可被授权客户端 tools/list 发现，工具名等于 Catalog 完整编码，Schema 与 Catalog 一致。
3. 授权客户端可调用已发布默认版本，经 Schema 校验后正确返回结果；未授权/停用/关闭协议被拒且不泄露工具信息。
4. 需确认（高风险/写操作）工具在 MCP 渠道被明确拒绝、不执行（D1 兜底）。
5. MCP 调用全过程落 Trace；管理端"MCP 调用记录"可查询。
6. 工具全局停用、协议开关关闭、客户端停用/Token 吊销后，后续 MCP 调用立即被拒，在途请求自然完成。
7. Inspector + SDK 客户端实连必测通过；Cursor/Claude Desktop 抽测并记录兼容矩阵，受限项登记《待后续实现功能》。
8. HTTP 既有闭环不受影响；协议开关默认全开下 HTTP 行为保持。

## 8. 本批明确不做

- 方向 B/C（收编外部 MCP Server、双向模式）；
- MCP 风险确认流程（D1 延后：开发完成后实现与调整；第一批需确认工具拒绝、不执行）；
- OAuth2 / mTLS 客户端认证；
- 异步/流式执行、取消、回调、死信；
- resources / prompts 服务端能力；
- 显式工具版本经 MCP 调用（如需支持另行确认）；
- 通用 MCP Client 实验室；
- 管理端完整可观测看板/告警/审计报表。
