## 1. 冻结范围

本文冻结 MCP 接入第一批的技术设计。需求层面已确认事项（方向 A、链路隔离、Catalog 单一事实源、A2 授权、Bearer Token、Streamable HTTP、同步执行、五个管理页面、协议版本跟 SDK 协商等）以《待确认问题清单》与《需求》为权威来源，本文只补充实现层设计。

## 2. SDK 与部署形态

### 2.1 选型

- 官方 MCP Python SDK v2（`mcp>=2,<3`），Streamable HTTP 传输；
- 嵌入现有 FastAPI 应用：`MCPServer`（v2 中 FastMCP 的继承者）→ `mcp.streamable_http_app()` 返回 Starlette 子应用 → 挂载到宿主 FastAPI 的独立 MCP 路径（默认 `/mcp`，路径可配置）；
- 不新增独立 MCP 进程/容器，沿用同一 uvicorn 部署形态；
- 宿主应用 lifespan 必须显式进入 `mcp.session_manager.run()`（挂载子应用的 lifespan 不会自动运行），否则首个 MCP 请求报 `Task group is not initialized`；
- `streamable_http_path`、`transport_security` 等传输参数在 `streamable_http_app()` 上配置；
- 传输安全默认只接受发往 localhost 的请求（SDK DNS rebinding 防护）；对外真实域名必须配置 Host 白名单，与"默认仅内网、可配置来源"的部署约束一致。

### 2.2 依赖变化

- Python 3.10+（项目当前 `>=3.11.6,<3.12` 满足）；
- 依赖下限上调/新增：pydantic>=2.12、anyio>=4.9、sse-starlette>=3.0、opentelemetry-api>=1.28、mcp-types（与 mcp 精确锁定）、typing-extensions>=4.13；
- SDK v2 以 httpx2 取代 httpx；项目 HTTP Provider 仍直接使用 httpx，需**显式保留 httpx 依赖**，并审计 `except httpx.*` 分支（httpx 与 httpx2 类型不可互换，SDK 侧抛 httpx2 异常）；
- 本批为可删库重建前提下的改造，依赖升级不兼容旧库不受影响。

## 3. MCP 端点契约

### 3.1 端点与能力

- 对外端点：独立路径（默认 `/mcp`），不与其他运行 API（`/api/runtime/**`）混用；
- 能力声明：仅 tools；不暴露 resources / prompts；
- 会话：由 SDK `session_manager` 管理 Streamable HTTP 会话，宿主只负责在其 lifespan 中启动/停止；
- 请求体限制遵循 SDK（默认 4 MiB，可配置上限）。

### 3.2 协议版本

- 协议版本跟随 SDK v2 支持范围做握手协商，不人为锁定单版本；
- 接入配置展示"协议版本支持范围"，默认取 SDK 能力全集；约束配置位保留但不默认启用。

## 4. 认证（Token 校验）

### 4.1 设计

- 认证形态：一客户端一 Bearer Token（不引入 OAuth/mTLS，留后续候选）；
- Token 存储：签发时明文只展示一次，数据库只存单向哈希（沿用 argon2 密码哈希做法）；
- 校验接入点（D2，冻结建议）：采用 SDK v2 原生资源服务器接口——`TokenVerifier` + `AuthSettings`；`verify_token` 内完成：哈希比对 → 客户端启用状态 → Token 未重置/吊销 → （可配置）来源 IP 限制；
- 校验失败在协议解析前返回标准 401，不执行工具、不泄露工具存在性；
- 校验通过后请求上下文携带 `AccessToken`（含 `client_id`），适配层据此做授权与 Trace。

### 4.2 待设计注意点（D2 附属）

- SDK 的 AuthSettings 会发布 `.well-known/oauth-protected-resource` 元数据并向未认证请求返回标准 401 头；第一版用自有静态 Token，是否借 SDK 原生发布元数据（对自动发现客户端的副作用）在设计评审时最终确认；备选为宿主侧 Bearer 中间件 + 关闭 SDK 原生鉴权。

## 5. 授权判定（A2）

### 5.1 主体抽象（D4）

- 将现有"调用系统 × 工具范围"判定抽象为"授权主体 × 授权范围"的通用计算：
  - HTTP 主体：调用系统（现有 `CallerToolScope` 等）；
  - MCP 主体：MCP 客户端（新授权表）；
- 判定语义两渠道一致：显式授权、默认拒绝、任一命中放行；范围粒度 = 命名空间 / 能力包 / 工具 + 能力包→客户端授权；
- 范围编码保存时复用 Catalog 引用校验；
- 实时状态在每次调用判定时读取，不信任缓存或 tools/list 快照。

### 5.2 MCP 侧可发现集合

`tools/list` = 客户端授权内 ∩ 工具启用 ∩ `mcp_enabled=true` ∩ 可发现 ∩ 存在已发布默认版本且 Provider 可用。

不在授权/不可用的工具不出现在列表中，也不在 tools/call 中泄露存在性。

## 6. 工具暴露

- MCP 工具名 = Catalog 完整编码 `namespace.tool_code`，直接映射，不做改名/二次查重；
- description、input_schema、output_schema 直接复用 Catalog 定义；Schema 需按 MCP 格式要求做合法化转换（长度/结构合法校验），不改内容语义；
- 工具协议开关（http_enabled / mcp_enabled）落在工具定义上，由共享工具目录维护，MCP 菜单"暴露工具"只读展示；
- 存量工具在可删库重建前提下默认两协议全开落地（D7）。

## 7. 调用执行与错误映射

### 7.1 决策链复用

`tools/call` 流程：

```text
Token 校验 → MCP 适配层解包
  → 授权判定（主体 × 范围 × Catalog 实时状态 × mcp_enabled）
  → 需确认工具检查（第一批明确拒绝、不执行；确认流程见 D1）
  → JSON Schema 参数校验
  → ProviderGateway（默认已发布版本）
  → output_schema 校验 → 结果标准化 → MCP 响应
  → Trace（runtime.control / confirmation / execute / provider / request）
```

- 本批同步执行；异步/流式不进入第一批；
- 版本选择沿用默认已发布版本；显式版本本批不进入 MCP 调用契约（如需支持另行确认）。

### 7.2 MCP 错误语义

| MCP 场景 | 行为 |
|----------|------|
| 未认证 / Token 无效 | 401（协议解析前） |
| 未授权 / 工具不可用 | 标准 MCP 错误（tool 不可用），不泄露存在性差异 |
| 参数不符合 Schema | isError + 参数错误语义 |
| Provider 失败 / 结果契约漂移 | isError + Provider 错误语义（映射现有 RUNTIME_*） |
| 需确认工具（第一批） | 明确返回不可用/暂不支持语义，不执行（确认流程 D1 延后） |

内部错误统一走 MCP 错误模型，不返回堆栈、内部地址或敏感信息。

## 8. 风险确认（D1：延后，不阻塞第一批）

### 8.1 现状口径

现有 HTTP 确认语义（已核实代码）：高风险/写操作执行前，调用系统先申请一次性确认令牌（申请即发、PENDING），Execute 时携带 confirmation_id + token 原子消费后放行；无平台管理员审批环节，实际"人是否确认"由调用方宿主流程负责。

### 8.2 后续决策参考候选（当前未选择）

| 方案 | 描述 | 影响 |
|------|------|------|
| C1 | MCP 高风险工具调用同样需要一次性确认令牌：适配层把"需确认"转成 MCP 错误/结果提示，客户端宿主通过 MCP 渠道确认端点（Bearer 认证）申请令牌后再带令牌 tools/call | 与 HTTP 语义完全同构；自研 Agent 可完整闭环；第三方宿主（Cursor/Claude Desktop）需其自行支持确认流程，否则高风险工具实连受限，记入兼容矩阵 |
| C2 | 平台在 MCP 渠道默认不强制二次确认，由 MCP 客户端宿主（其工具调用权限体系）承担确认职责 | 第三方客户端即插即用；平台侧治理弱化，需管理端显式声明风险敞口，与"默认拒绝/与 HTTP 同等"原则有张力 |
| C3 | 需要确认（高风险）的工具默认不在 MCP 渠道暴露，管理员显式白名单后才暴露且仍须令牌 | 安全最稳；首批 MCP 可用工具集合受限于低风险工具，能力最窄 |

### 8.3 用户决定（2026-09-07）

- D1（MCP 风险确认流程：协议表达、确认凭据形态与确认交互）**先不处理，记录为待确认项**；在 MCP 接入代码开发完成后再进行实现和调整。
- 方向性结论（#14：以工具风险等级驱动确认）保留，不因延后撤销。
- 第一批兜底行为：识别为需确认（高风险/写操作）的工具在 MCP 渠道**明确拒绝、不执行，不静默放行**；HTTP 侧既有确认流程不受影响。
- C1 / C2 / C3 保留为本节决策参考，供代码开发完成后重新决策使用。

## 9. 数据与接口变化草案（D5）

### 9.1 表结构草案

| 表/字段 | 说明 |
|---------|------|
| `catalog_tool.http_enabled` / `mcp_enabled` | 协议开关，默认 true |
| MCP Server 配置 | 全局启停、端点路径、来源/传输安全、协议版本范围（单实例配置） |
| MCP 客户端 | 客户端编码、名称、状态、来源限制 |
| MCP 客户端 Token | 仅存哈希、签发时间、重置/吊销状态（一客户端一 Token，轮换时旧 Token 失效） |
| MCP 客户端授权范围 | 授权主体=client_id；scope_type=namespace/capability/tool + 能力包→客户端授权 |
| `runtime_trace_log.channel` / `mcp_client_id` | 渠道与 MCP 客户端维度 + 索引 |

### 9.2 管理操作码草案

- `mcp_server:view` / `mcp_server:config`：接入配置；
- `mcp_client:view` / `mcp_client:manage`：客户端与 Token；
- `mcp_auth:view` / `mcp_auth:manage`：授权范围；
- `mcp_trace:view`：调用记录；
- `mcp_test:run`：测试调试。

以上命名与是否并入既有角色分配，在设计评审时确认。

## 10. Trace 与调用记录

- MCP 全链路事件与 HTTP 共用 `runtime_trace_log`，以 `channel=mcp` + `mcp_client_id` 区分；
- 认证事件记录 client_id 与 Token key 信息（不记录 Token 原文）；授权、确认、执行、Provider、完成事件沿用现有事件模型；
- 管理端"调用记录"查询接口按渠道过滤，本批只暴露 MCP 入口；查询服务预留 HTTP 复用。

### 2026-09-07（阶段 0 实证补充）

- 挂载与生命周期（D3）实证：`MCPServer` + `streamable_http_app(streamable_http_path="/")` 挂载到 `/mcp` 前缀，公开端点为 `/mcp/`（SDK 对无尾斜杠请求返回 307）；宿主 lifespan 手动进入 `session_manager.run()` 后 initialize / tools/list / tools/call 跑通。
- 鉴权接线（D2）实证：采用 SDK 原生 `TokenVerifier` + `AuthSettings` 可行，无 Token 401、有效 Token 放行；AuthSettings 需同时提供 `issuer_url` 与 `resource_server_url`。SDK 发布 OAuth 资源元数据为标准行为，阶段 2 接入真实 Token 存储时复核是否保持 SDK 原生或切换宿主侧 Bearer 中间件。
- 依赖基线实证：mcp 2.1.1 与项目现有 pydantic 2.13.4 / starlette 1.6.0 / anyio 4.14.2 无冲突；httpx 需显式保留（项目 HTTP Provider 使用）。
- 占位工具 `ping` 与开发期临时 TokenVerifier 属阶段 0 验证物，将在阶段 2–4 替换，不作为最终交付契约。

### 2026-09-07（阶段 2 认证定稿）

- D2 最终结论：**放弃 SDK 原生 TokenVerifier/AuthSettings 作为认证主路径**，改为宿主侧 MCP 鉴权中间件。原因：`TokenVerifier` 协议仅接收 token 字符串、无法获得来源 IP，阶段 1 落库的客户端来源 IP 规则无法在 SDK 原生校验中执行；宿主中间件同时顺带消除 SDK 发布的 OAuth 资源元数据副作用。MCP Server 构造不再携带 token_verifier/auth。
- 认证链路：宿主中间件（位于入口中间件之后）完成 Bearer 解析 → Server 全局启停校验 → token_key 精确定位 ACTIVE 令牌 → argon2 比对 → 客户端 enabled 校验 → 来源 IP 规则校验 → 通过后将身份写入 `request.state.mcp_identity`；认证事件落 Trace（channel=mcp、mcp_client_id、source_ip）。
- 数据补充：argon2 加盐哈希无法作为检索键，`mcp_client_token` 新增唯一列 `token_key = SHA-256(token)`（用户确认 A 方案），用于精确定位后仍以 argon2 做最终比对。
- 语义：缺失/无效/已停用/已吊销统一 401（不泄露差异）；MCP Server 全局停用与来源不符返回 403；未命中来源规则默认拒绝。

### 2026-09-07（阶段 3 工具暴露定稿）

- Server 形态定稿：改用官方 SDK v2 **低层 `Server` + `on_list_tools`** 动态暴露 Catalog 工具（高层 `MCPServer` 工具为静态注册，无法按客户端授权返回不同 tools/list）；占位 ping 移除，`on_call_tool` 属阶段 4 接入点。
- 身份传递：认证中间件将身份写入模块级 `current_mcp_identity` ContextVar，MCP 低层 handler 在同一请求上下文读取（测试实证）。
- 范围核心收敛（D4）：新增共享 `runtime/tool_control/scope_expansion.py`（`expand_scope_tool_ids` / `scope_allows_tool`），HTTP `CallControlService`、运行中间件路径预检与 MCP tools/list 共用同一"授权范围 → 允许工具"展开逻辑。
- MCP 可发现口径：tools/list = 客户端 A2 授权内 ∩ 工具启用 ∩ mcp_enabled ∩ 可发现 ∩ 存在已发布默认版本；name=full_code，Schema 取默认已发布版本（缺省回退工具级）。
- HTTP 回归：HTTP 调用控制与路径预检新增 `http_enabled` 过滤（默认开启；None 视为开启，兼容既有构建路径），协议开关全量回归通过。
