## 1. 背景与目标

当平台接入的工具达到一定规模后，Agent 无法将全部工具一次性加载给 LLM：上下文窗口装不下，工具过多也会降低 LLM 选择准确率。Agent 需要根据用户对话意图，从海量工具中精准获取当前最相关的一小部分。

本批目标（来自 2026-09-07 讨论）：由**工具平台在服务端完成召回**，并且在**向量检索阶段就将权限作为过滤条件**，在有权限的工具子集内完成语义排序与 top-N 召回，避免"先全量召回、再按权限丢弃"导致无工具可用。

## 2. 已核实现状（代码依据）

- HTTP 侧已存在服务端自然语言召回接口 `Discover`（`/api/runtime/v1/tools/discover`），按调用系统返回受控候选；
- 关键词降级路径已是"权限先行"：先计算可发现工具集合，再在集合内做关键词查询（`runtime/retrieval/keyword.py`）；
- 向量路径当前是"两步走"：在全量索引取 top-K（limit×3 溢出窗口），再在应用层按权限过滤（`runtime/retrieval/service.py` 的 `_vector_discover`）；授权子集窄时，真正语义相关但全局排序靠后的工具可能永不进入召回窗口；
- 当前 `VectorIndex` 接口的 `query()` 不接受过滤条件，Chroma 文档元数据只有 namespace / tool_code / name / risk_level / version，无授权维度（`infrastructure/vector_index.py`）；
- 向量库为嵌入式单实例 Chroma，写并发固定 1；多 Agent / 大规模依赖的 Chroma 服务化已登记在《待后续实现功能》7.1；
- MCP 生态无标准"按意图检索工具"方法，`tools/list` 是全量快照语义；Agent 检索通道的对外形态需单独设计。

## 3. 初步定位（待确认）

- 属于二期后续批次，与既有《待后续实现功能》"发布、执行与检索治理增强"及"Chroma 服务化"衔接；
- 服务端召回、权限边界不出平台、多 Agent 共用 Catalog 索引，是已确认方向；
- 第一批 HTTP Discover 与后续 MCP Agent 通道的检索契约统一设计，避免两套语义；
- 开发排在 01-MCP接入 之后，不阻塞 01。
