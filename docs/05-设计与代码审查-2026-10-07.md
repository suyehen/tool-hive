## 已实现代码的问题

### 1. P1：雪花序列耗尽后的异常恢复会重复发号

位置：`backend/src/toolhive/adapters/snowflake.py:189`。

序列先取模变成 0，再等待下一毫秒。若 `_spin_until()` 超时抛错，`_last_ms` 仍为原毫秒，而 `_sequence` 已变成 0；下一次在同一毫秒调用会发序列 1，与已发 ID 重复。

本地确定性复现：注入固定时钟，生成 4096 个 ID，第 4097 次抛出等待超时，再调用一次，返回值确实在前 4096 个 ID 中。此问题直接违背“绝不重复发号”的基础契约。

建议：等待成功后再提交序列和时间状态，失败时保留“序列已耗尽”的状态。加入“耗尽→等待失败→再次调用”的回归验证。

### 2. P1：worker 租约的本地有效期和释放状态不安全

位置：`backend/src/toolhive/adapters/snowflake.py:315`、`:338`、`:351`、`:180`。

获取/续租成功后才记 `time.monotonic()`，把网络响应延迟算进了新的本地有效期。服务端 TTL 从执行命令时开始；响应延迟超过安全余量时，本地守卫可能在服务端租约已到期后继续放行。另一个实例此时可以接管相同 worker。

另一个独立触发条件：成功 `release()` 后没有清空续租时间或标记不可持有，`ensure_held()` 仍放行。本地假 Redis 已复现“acquire→release→ensure_held，无异常”。生成器的 guard 又在发号锁外检查，线程等待锁或进程停顿后不会再次检查。

建议：用发送命令前的单调时间保守计算有效截止；释放时立即废止本地持有状态；在锁内且实际生成 ID 前复查。覆盖延迟响应、主动释放、线程等待和租约接管场景。

### 3. P1：HTTP deadline 没有成为整体时间上限

位置：`backend/src/toolhive/adapters/http.py:146`、`:194`。

当前只是将剩余预算分别赋给 httpx 的 connect/read/write/pool 超时，没有用整体取消作用域包围请求。这些分阶段超时不能限制阶段累计耗时，也不能限制持续有数据到达的长响应。

本地模拟传输验证：deadline=10ms、模拟响应等待 80ms，实际约 94ms 后仍返回 HTTP 200。模拟传输不验证底层 socket 超时；此复现验证的是包装层没有独立执行整体 deadline，真实分阶段/持续读取路径也没有总时长限制。

建议：用 `asyncio.timeout_at(deadline.expires_at)` 包住完整出站动作，包括读取响应体；将该作用域的超时映射为 `DeadlineExceededError`，保留单阶段超时作为附加限制。

### 4. P1：加锁读没有刷新 ORM 中已加载的旧状态

位置：`backend/src/toolhive/adapters/db/repository.py:108`。

同一个 session 已加载对象后，另一个事务更新状态，再调用 `get_for_update()`，SQL 会加锁，但 SQLAlchemy 身份映射可能返回原对象且不覆盖已加载属性。当前 session 又配置 `expire_on_commit=False`，使跨提交复用时更容易触发。

本地 SQLite 验证了对应 SQLAlchemy 身份映射行为：数据库状态已为 `published`，再次 SELECT（带 `with_for_update()` 的同一查询写法）对象状态仍为 `pending_review`；显式 refresh 才变成 `published`。SQLite 不支持 PostgreSQL 行锁，因此该验证仅证明“重新查询不等于刷新”；生产行锁行为仍需 PostgreSQL 验证。

建议：加锁查询使用 `execution_options(populate_existing=True)`，或明确执行带锁 refresh，并处理未 flush 的本地修改。否则后续“并发审批仅一次成功”的判断可能依据旧状态。

### 5. P2：推荐的 AAD 凭据绑定与 KEK 重包装接口不兼容

位置：`backend/src/toolhive/adapters/crypto.py:158`、`:244`、`:270`。

encrypt/decrypt 支持并推荐用 AAD 绑定凭据身份，但 `rewrap()` 无 AAD 参数且只用固定前缀解开 DEK。按推荐方式加密的凭据不能走重包装轮换；代码明确要求改走 decrypt+encrypt，失去了只重包装 DEK 的收益。

建议：rewrap 接收相同 AAD，两层 DEK 包装均使用相同上下文。身份建议绑定不可变 credential ID，并明确格式版本和轮换上下文契约。

### 6. P2：加密模块直接依赖未列入工程依赖

位置：`backend/src/toolhive/adapters/crypto.py:48`；`backend/pyproject.toml:16`。

代码直接 import `cryptography`，但 dependencies 未声明。当前 conda 环境已有包可以掩盖该问题；按项目声明建立干净环境时，加密模块可能无法导入。

建议：声明直接依赖，并在干净环境验证安装及加密模块导入。当前环境的静态检查通过不能证明依赖声明完整。

### 7. P2：ORM 与 DDL 的 row_version 初值已经漂移

位置：`backend/src/toolhive/adapters/db/base.py:134`；`docs/03-表结构DDL-v0.2.md:56`。

DDL 约定和多张表均使用 DEFAULT 0，Mixin 则设置 server_default/default 为 1，自检也按首版本 1 验证。通过 ORM 插入与直接按 DDL 插入的初值不同，后续自动生成迁移也会发现默认值差异。

建议：先统一一个权威初值，再同步 Mixin、DDL 和验证脚本。不要等 C2 才处理已经出现的漂移。

### 8. P2：延迟桶声明为累计桶，实际却是区间计数

位置：`backend/src/toolhive/observability/logging.py:172`、`:225`。

类说明宣称采用累计 `le_*` 桶、解析端可直接找累计比例，但 observe 只增加命中的一个桶。一次 5ms 观测只增加 le_10，le_25 等保持 0，违背累计桶语义。按声明直接计算 p95 会错误。

建议：累计桶更新所有大于等于观测值的边界，并定义总量/+Inf；或将输出明确改成区间桶并要求解析端累加。验证快照结构及分位计算，不只验证 label。

### 9. P2：部署自检会误报单活约束通过

位置：`backend/scripts/preflight.py:121`。

查询只要求 index_meta 上存在任意 UNIQUE 索引。DDL 本来就有 uq_index_meta_version，即使丢掉 uq_index_meta_single_active，检查仍会报告“单活唯一约束存在”。

建议：核对具体索引、唯一性及 `status='active'` 的部分索引谓词，避免把版本唯一约束误认为单活约束。

## 设计契约的问题

### 10. P1：幂等身份、处理中恢复及确认消费时序尚未闭合

位置：`docs/01-ToolHive平台设计-v0.2.md:771`、`:846`、`:859`。

指纹只写“工具+参数哈希”，未明确 Principal 隔离、不可变 tool ID、实际 version ID、影响执行结果的 context，以及 channel 切换后的重放规则。相同参数钉死不同版本可能错误拿到旧结果；若 key 未按 Principal 隔离，还可能跨主体冲突或错误共享结果。这里是未定义契约，业务代码尚未实现，不能断言当前已经发生泄露。

同时只定义 SET NX 认领与 24h 保留，没有明确 processing 租约、认领 token、失败释放、失联恢复，以及“上游已成功但结果/审计写入失败”的未知结果状态。进程崩溃可能留下长时间 IN_PROGRESS，盲目删除再试则可能重复写入。文档关于把认领前移一定会卡到 TTL 的论证，实际上依赖尚未定义的清理策略。

M1 又要求第 6 步先消费确认令牌，第 8 步才认领幂等键；并发请求可能先争抢消费令牌，或者消费后配额拒绝，导致未执行却失去令牌。

建议：在 D5/F1 前确定幂等状态机、所有者 token 和故障恢复表；按 Principal 隔离并定义版本/context 的身份语义。明确确认校验与消费的区别，将消费与已认领的执行身份绑定。对未知上游结果定义查询/上游幂等恢复路径。

### 11. P1：管理面禁持 KEK 与统一配置/凭据写入职责冲突

位置：`docs/01-ToolHive平台设计-v0.2.md:1180`（§10.1 部署约束）；`backend/src/toolhive/config.py:296`、`:715`；`backend/alembic/env.py:41`。

设计规定管理 CLI/admin API 不持有 KEK，但 load_settings 无条件要求 SecretSettings 的 KEKS 和 ACTIVE_KEK_ID。迁移也调用完整 load_settings，单纯数据库迁移会被要求提供运行面密钥及 embedding 配置。后续管理 CLI 若复用该加载器，就无法按禁持 KEK 的要求启动。

此外“管理面接受新凭据明文但不持 KEK”需要一条明确的运行面加密写入通道，当前文档没有把这个职责落实成接口。

建议：按执行服务、管理 CLI、索引任务、数据库迁移定义配置需求；迁移只读数据库配置。明确凭据写入由运行面完成的受控接口及明文生命周期。保留运行面 KEK 覆盖度强校验。

### 12. P1：版本快照缺少风险等执行策略字段，发布边界不明确

位置：`docs/03-表结构DDL-v0.2.md:170`、`:208`；`docs/01-ToolHive平台设计-v0.2.md:477`。

Tool 保存 risk/domain/system/tags/executable 等字段，ToolVersion 的快照只有 name/description/input_schema/output_schema；执行确认与授权却依赖前一组字段。文档未定义重导修改这些字段时，何时影响仍在 stable 上的旧已发布版本。

例如新导入版本仍是 draft，却降低 Tool.risk、修改授权标签，旧 published 版本的确认或授权行为可能随之改变，绕过“版本审核后发布”的预期。反方向则可能把原有生产版本直接禁用。

建议：区分全局紧急停用与版本级风险/执行定义，把需审核的字段纳入版本快照，并明确检索元数据如何随 stable 发布更新。对于全局授权分类变更，定义单独的治理与审计动作。

### 13. P2：Channel 没有约束版本归属同一工具

位置：`docs/03-表结构DDL-v0.2.md:233`。

tool_channel.tool_id 和 version_id 分别有外键，但允许工具 A 的 channel 指向工具 B 的合法版本。若内核按 A 授权、按 channel.version_id 执行，错误数据可造成跨工具执行。即使状态检查保证 published，也没有保证归属正确。

建议：为 tool_version 建立 (tool_id,id) 唯一键，channel 使用 (tool_id,version_id) 复合外键；服务层仍显式校验归属及 published 状态。该不变量应加入 C4 验收。

## 次要文档/工程问题

- `backend/pyproject.toml:9` 引用 README.md，但 backend 下没有该文件；CLI entry point 也指向尚未实现的 cli.main。应区分骨架可安装与实际可运行的验收，不把占位入口计为已交付。
- 设计 §4.3 的 ReviewRecord 规则表仍残留 reviewer_id/decision/created_at，与实体总览和 DDL 的 action/create_by_* 不一致；execution_binding 的可空/默认值说明也与设计表不完全一致。
- `load_settings(environ=...)` 会清空并替换整个进程 os.environ，存在多线程读取配置/启动子进程时的竞态。建议以自定义 settings source 注入映射，避免为了局部配置校验修改全局环境。
- token_bucket.lua 回退时间时不补令牌，但仍将 ts 写成较早的 now_ms；随后较晚时间请求会再次对已经处理过的时间段补令牌。应保证时间高水位不下降，并考虑分布式实例时钟差异。
- semaphore_acquire.lua 每次用本次 lease_ms*2 覆盖整个 key TTL。如果同一 key 的持有者租期不同，短租期请求可能使 key 早于长租期 holder 过期；应要求同 key 租期固定，或按最大 score 计算 TTL。
