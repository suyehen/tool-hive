# 代码功能与架构核验报告

## 1. 核验范围

- 核验对象：`tool-hive` 后端、`frontend` 前端与 `deploy` 部署配置。
- 核验维度：功能正确性、代码实现、安全边界、并发行为、运行时一致性与架构可用性。
- 明确排除：未阅读、引用或以 `docs/` 目录内任何需求、设计或问题文档作为核验依据；也不对产品需求是否合理作判断。
- 核验方式：静态代码追踪、接口与调用链比对、后端测试执行、Python 编译检查、前端生产构建检查。

## 3. 高优先级问题

### 3.1 未启用的调用方公钥可通过运行时认证

- 证据位置：`tool-hive/src/toolhive/models/caller_public_key.py:50`
- 现象：`CallerPublicKey.is_valid()` 将 `PENDING` 状态视为有效，而不是仅接受已启用状态。
- 影响：尚未完成启用流程的公钥可用于运行时请求认证，破坏密钥审批/启用的安全边界。
- 建议：认证判断只允许显式的 `ACTIVE`（或当前系统定义的已启用状态）；同时增加 `PENDING` 密钥被拒绝的回归测试。

### 3.2 已禁用的 Provider 仍可能被执行

- 证据位置：`tool-hive/src/toolhive/services/catalog_provider_service.py:185`、`tool-hive/src/toolhive/runtime/tool_control/service.py:126`
- 现象：运行时选择 Provider 的决策链没有校验 Provider 的 `status`。
- 影响：管理端禁用 Provider 后，已发布工具仍可能继续对外发起出站调用；停用动作不能可靠生效。
- 建议：在解析和执行两个边界均校验 Provider 状态，并定义禁用后缓存、已解析结果和正在执行请求的处理策略。

### 3.3 已禁用的能力包仍参与授权

- 证据位置：`tool-hive/src/toolhive/runtime/tool_control/service.py:224`、`tool-hive/src/toolhive/runtime/middleware.py:284`
- 现象：能力包筛选仅排除 `ARCHIVED`，没有排除 `DISABLED`。
- 影响：禁用能力包的工具仍可能被发现、授权或执行，导致管理状态与实际运行状态不一致。
- 建议：将能力包状态判断收敛为单一的“可运行”谓词，供 Resolve、授权和 Execute 共用；补充禁用后不可发现、不可执行的测试。

### 3.4 确认令牌没有绑定目标工具与版本

- 证据位置：`tool-hive/src/toolhive/api/runtime/v1/tools.py:206`、`tool-hive/src/toolhive/runtime/confirmations/service.py:84`
- 现象：确认令牌校验只关联 `system_id` 与令牌值，未验证当前 `tool_id`、`version_id` 是否与令牌签发时一致。
- 影响：调用方可先取得工具 A 的确认令牌，再将其用于工具 B（包括风险等级更高的工具）的执行请求。
- 建议：在确认记录中保存并校验工具、版本、调用方、请求摘要与过期时间；令牌不得跨工具或跨版本复用。

### 3.5 确认令牌存在并发双重消费竞态

- 证据位置：`tool-hive/src/toolhive/runtime/confirmations/service.py:84`
- 现象：逻辑先读取令牌状态，再更新为已使用，未使用行锁或带状态条件的原子更新。
- 影响：两个并发请求可能同时看到未使用状态，并同时通过确认校验。
- 建议：采用 `UPDATE ... WHERE status = 'PENDING'` 的条件更新并检查受影响行数，或在事务中使用行锁；增加并发测试以确保仅一个请求成功。

### 3.6 并发槽位会被未成功获取的请求错误释放

- 证据位置：`tool-hive/src/toolhive/runtime/middleware.py:160`、`tool-hive/src/toolhive/runtime/control/traffic.py:35`
- 现象：中间件的 `finally` 只要存在 `system_id` 就调用释放；但 QPS、配额或熔断检查可在并发槽成功获取前抛出异常。
- 影响：被拒绝请求会错误降低当前并发计数，实际运行中的请求数可能超过配置上限。
- 建议：将 `acquired` 标识设为成功获取后才为真，并且只在该标识为真时释放；用混合 QPS 拒绝与长请求的场景进行回归测试。

### 3.7 前端生产静态资源没有明确的托管路径

- 证据位置：`tool-hive/src/toolhive/main.py:85`、`deploy/nginx/toolhive.conf:28`
- 现象：FastAPI 只挂载 API；Nginx 对 `/admin/` 的配置直接代理到后端，没有将前端 `dist` 目录作为静态站点提供。
- 影响：按当前部署配置访问管理前端可能得到 API 响应或 404，构建产物无法被实际服务。
- 建议：由 Nginx 使用 `root`/`try_files` 托管前端产物，并单独反向代理 API；或由 FastAPI 明确挂载静态目录。部署镜像应包含构建产物。

## 4. 中优先级问题

### 4.1 幂等键在 Provider 调用前被消费

- 证据位置：`tool-hive/src/toolhive/runtime/execution/idempotency.py:16`
- 现象：幂等键在远端 Provider 调用前即记录为已使用；调用失败后没有可靠的结果查询或重试衔接。
- 影响：网络超时、Provider 5xx 等暂时性失败会让调用方无法使用同一幂等键安全重试，且无法判断远端是否已执行。
- 建议：设计明确的幂等状态机（处理中、成功、失败、未知），保存可返回结果，或至少为不确定结果提供查询与受控重试机制。

### 4.2 熔断开关未实际参与熔断判断

- 证据位置：`tool-hive/src/toolhive/runtime/control/traffic.py:35`
- 现象：运行策略中的 `circuit_breaker_enabled` 未在 `check()` 中生效；已有熔断记录仍可拒绝请求。
- 影响：管理端关闭熔断后，系统行为可能依旧被历史熔断状态影响。
- 建议：关闭开关时跳过熔断检查并明确是否清理已有状态；添加开关切换后的行为测试。

### 4.3 前端 IP 规则无法从禁用恢复到启用

- 证据位置：`frontend/src/pages/caller-systems/CallerSystemListPage.tsx:499`、`tool-hive/src/toolhive/api/admin/caller_systems/router.py:400`
- 现象：前端切换 IP 规则状态时固定提交 `reason='toggle'`；后端以 `reason` 是否存在判断状态，结果始终走禁用分支。
- 影响：已禁用的 IP 规则无法通过界面重新启用。
- 建议：接口使用显式布尔字段或明确的目标状态枚举；前端按当前状态提交目标状态，并为启用/禁用双向切换增加接口和页面测试。

### 4.4 CLI 带查询参数的签名请求会验签失败

- 证据位置：`tool-hive/src/toolhive/cli.py:139`
- 现象：`sign-request` 命令将 `--query` 纳入 canonical string 计算，但输出 URL 时未实际附加该查询字符串。
- 影响：用户按 CLI 输出发送含查询参数的请求时，服务端计算的待签名内容与客户端不一致。
- 建议：将规范化后的查询参数同时写入 URL，或调整 CLI 参数语义；添加至少一个含查询参数的端到端验签测试。

### 4.5 Resolve 响应缺少确认需求提示

- 证据位置：`tool-hive/src/toolhive/api/runtime/v1/schemas.py:28`、`tool-hive/src/toolhive/api/runtime/v1/tools.py:102`
- 现象：Resolve 响应模型没有输出 `confirmation_required`。
- 影响：客户端在执行前不能得知写操作或高风险工具是否需要确认，只能在执行阶段被动处理失败/挑战响应。
- 建议：将最终生效的确认策略和确认需求加入 Resolve 响应，并保持与 Execute 的决策逻辑共用同一来源。

### 4.6 Resolve 与 Execute 的默认版本规则不一致

- 证据位置：`tool-hive/src/toolhive/runtime/tool_control/service.py:244`
- 现象：Resolve 缺省版本时回退到最新已发布版本；Execute 缺省版本时要求存在 `default_version_id`。
- 影响：同一工具可被成功解析，却因未传版本号无法执行，或者执行与解析结果不一致。
- 建议：将版本决策抽取为单一函数，统一两条链路；缺少默认版本时采用同一回退规则或统一返回明确错误。

## 5. 架构与实现风险

### 5.1 工具契约字段未形成运行时闭环

- 涉及字段：`output_schema`、`response_handling`、`idempotent`。
- 现象：这些字段主要被存储和返回，执行完成后没有按 `output_schema` 校验响应，也未对 `response_handling` 做转换，`idempotent` 也未用于选择或限制幂等策略。
- 风险：配置在管理端看似已生效，实际运行时却缺少约束；上游客户端会收到不符合声明结构的结果，且工具声明与运行行为逐步漂移。
- 建议：明确每个字段是“可执行配置”还是“描述性元数据”。若需执行，应把校验/转换/幂等决策纳入执行管道；若只作描述，应从控制面配置中降级并在 API 上清晰标识。

### 5.2 HTTP 出站校验存在 DNS Rebinding 窗口

- 证据位置：`tool-hive/src/toolhive/runtime/execution/http_executor.py:49`
- 现象：代码先解析域名并检查 IP 是否为内网地址，之后 `httpx` 仍以原域名重新发起解析与连接。
- 风险：在两次解析之间 DNS 记录发生变化时，请求可连接到初次校验之外的地址，削弱 SSRF 防护。
- 建议：将已校验的解析结果与实际连接绑定，或使用支持自定义解析/传输的客户端实现；同时继续校验重定向链上的每一个目标。

### 5.3 并发控制为进程内状态，横向扩容后失效

- 证据位置：`tool-hive/src/toolhive/runtime/control/traffic.py:29`
- 现象：并发计数保存在进程内字典。
- 风险：多个应用实例各自维护计数，配置为 N 的并发上限实际可放大为实例数乘 N；重启也会丢失状态。
- 建议：多实例部署时迁移到 Redis 等共享原子计数机制，或在架构上明确单实例限制并由编排层保证。

### 5.4 同步 Chroma 调用位于异步请求路径

- 证据位置：`tool-hive/src/toolhive/infrastructure/vector_index.py:84`
- 现象：异步调用链中直接调用同步 Chroma API。
- 风险：向量检索或同步耗时会阻塞事件循环，导致同一进程其他请求延迟上升。
- 建议：使用异步客户端，或通过线程池隔离同步 I/O；结合指标监控索引调用耗时和事件循环阻塞。

### 5.5 前端初始加载包偏大

- 证据位置：`frontend` 的生产构建结果。
- 现象：单个 JavaScript 产物约 1.35 MB，构建工具已发出超过 500 KB 的分包告警。
- 风险：低带宽或弱性能终端的首屏加载、解析与交互延迟较高。
- 建议：按路由懒加载，拆分管理端依赖，检查大型依赖是否可按需导入，并利用构建分析工具确认主要体积来源。

## 6. 建议修复顺序

1. 收紧运行时身份与授权边界：修复待启用公钥、Provider 状态与能力包状态判断。
2. 修复高风险执行确认：令牌绑定工具/版本并采用原子一次性消费。
3. 修复流量控制正确性：确保并发槽位获取与释放严格对称，令熔断开关生效。
4. 统一运行时决策：收敛默认版本、确认策略和能力状态的决策函数，避免 Resolve 与 Execute 分叉。
5. 修正管理端与 CLI 可用性：IP 规则双向切换、带查询参数的签名 URL、确认提示。
6. 明确生产部署：将前端静态资源托管与 API 代理拆开，并验证容器/部署包包含前端产物。
7. 针对多实例与出站网络安全，完成共享并发状态和 DNS Rebinding 防护设计。

## 7. 回归测试建议

- `PENDING`、`DISABLED` 状态的公钥、Provider、能力包都必须在运行时被拒绝，并验证已缓存或已解析的路径不会绕过状态变更。
- 确认令牌必须与调用方、工具和版本绑定；多个并发请求使用同一令牌时，只允许一个执行成功。
- 被 QPS、配额或熔断拒绝的请求不能影响其他进行中请求的并发计数。
- Resolve 和 Execute 在未传版本号时必须得到完全一致的版本选择结果。
- IP 规则在管理端可完整执行“启用 → 禁用 → 启用”状态流转。
- CLI 的带查询参数请求应使用输出 URL 和签名直接通过服务端验签。
- 部署环境应以真实的 `/admin/` 访问和 API 调用验证前端资源、历史路由回退与反向代理行为。

## 8. 结论

项目的基础单元测试和前端构建能够通过，但运行时控制面与数据面之间存在多处状态不同步，且确认令牌、并发控制、部署静态资源三类问题会直接影响安全性或生产可用性。建议优先完成第 3 节问题及其回归测试，再推进多实例控制、出站连接安全和性能优化。
