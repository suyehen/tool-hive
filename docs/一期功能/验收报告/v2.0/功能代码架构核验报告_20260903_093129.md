# ToolHive 功能、代码实现与架构核验报告

**报告时间：** 2026-09-03 09:31:29（Asia/Shanghai）  
**核验范围：** 功能行为、代码实现、系统架构  
**核验方式：** 源码静态检查、关键路径行为复核、现有测试与前端构建验证  
**说明：** 本报告未参考 `docs` 目录内容。

## 一、总体结论

项目现有单元测试和前端构建均可通过，但测试主要基于 Mock，不能证明真实 PostgreSQL、Redis、Chroma 及前后端完整链路可靠。当前存在会导致索引同步失效、运行时授权不生效、并发数据覆盖、分页数据丢失和数据库完整性下降的问题，建议在正式验收前处理高优先级问题，并补充真实基础设施集成验证。

## 二、高优先级问题

### 2.1 版本变更事件无法正确同步 Chroma

- `update_version()`、`set_default()` 及 `_after_transition()` 发出的 `catalog.version.changed` 事件没有稳定携带 `tool_id`：
  - `tool-hive/src/toolhive/services/catalog_version_service.py:246`
  - `tool-hive/src/toolhive/services/catalog_version_service.py:385`
  - `tool-hive/src/toolhive/services/catalog_version_service.py:636`
- `ChromaIndexDelivery` 对版本事件只从 `event.payload["tool_id"]` 取工具 ID，缺失即抛出 `DeterministicDeliveryError`：
  - `tool-hive/src/toolhive/services/outbox/deliveries.py:79`
- 影响：版本编辑、发布默认版本、审核状态流转等操作会使 Outbox 投递重试后进入 `DEAD`，Chroma 索引保持旧内容或被遗漏同步。
- 建议：统一封装版本索引事件，始终从版本实体补齐 `tool_id`；增加状态流转和缺少 payload 的集成测试。

### 2.2 能力包调用系统授权未接入运行时鉴权

- 管理端维护能力包与调用系统关系：
  - `tool-hive/src/toolhive/services/catalog_capability_service.py:266`
- 运行时工具范围判断只查询 `CallerToolScope`，没有查询 `CatalogCapabilityPackSystem`：
  - `tool-hive/src/toolhive/runtime/tool_control/service.py:291`
- 影响：用户在能力包页面保存的“调用系统授权”不会产生实际运行时访问权限，必须额外配置调用系统的工具范围，管理界面与运行时语义不一致。
- 建议：明确唯一授权事实来源；如果保留两套关系，应在写入和运行时解析处建立明确同步规则。

## 三、中优先级问题

### 3.1 前端主列表分页不完整

- 账号、角色、调用系统固定请求第一页 50 条，主表未配置后端分页：
  - `frontend/src/pages/accounts/AccountListPage.tsx:59`
  - `frontend/src/pages/roles/RoleListPage.tsx:67`
  - `frontend/src/pages/caller-systems/CallerSystemListPage.tsx:96`
- 工具、Provider、能力包、审核、索引任务等页面固定请求 100 条，但表格分页没有触发新的 offset/limit 请求：
  - `frontend/src/pages/catalog/ToolsPage.tsx:120`
  - `frontend/src/pages/catalog/ToolsPage.tsx:499`
- 影响：数据超过固定数量后无法访问后续记录，点击分页可能显示空页面。
- 建议：统一维护分页状态，在表格 `onChange` 中重新请求后端；筛选条件变化时重置页码。

### 3.2 Provider 健康检查忽略 HTTP 状态码

- 健康检查只执行 GET，不检查响应状态码：
  - `tool-hive/src/toolhive/runtime/execution/health.py:31`
- 实测 mock `500` 响应仍返回 `healthy=True`。
- 影响：返回 404/500 的目标可能被允许启用，运行时才暴露故障。
- 建议：明确成功状态码范围并调用 `raise_for_status()` 或显式判断状态码；同时使用实际绑定路径或健康检查路径配置。

### 3.3 HTTP 绑定参数缺少 Service 层统一校验

- API Schema 对 `timeout_seconds`、`retry_max` 有范围约束：
  - `tool-hive/src/toolhive/api/admin/catalog/schemas.py:159`
- `CatalogVersionService._validate_binding_data()` 未重复校验，直接写入绑定：
  - `tool-hive/src/toolhive/services/catalog_version_service.py:542`
- HTTP 执行器对负 `retry_max` 可能得到空重试循环，并最终执行 `raise None`：
  - `tool-hive/src/toolhive/runtime/execution/http_executor.py:60`
- 建议：将约束下沉到 Service/领域模型，并增加数据库约束或启动时数据校验。

### 3.4 响应大小限制在完整读入后才执行

- `httpx` 请求返回后才读取 `response.content` 并检查大小：
  - `tool-hive/src/toolhive/runtime/execution/http_executor.py:105`
  - `tool-hive/src/toolhive/runtime/execution/http_executor.py:152`
- 影响：超大响应仍会先占用内存，限制不能真正防止资源耗尽。
- 建议：采用流式响应读取，累计读取字节数达到上限立即中止。

### 3.5 DNS 校验与实际连接存在 TOCTOU 风险

- 出站请求先解析并校验地址：
  - `tool-hive/src/toolhive/runtime/execution/outbound.py:43`
- 随后 `httpx` 按 hostname 重新解析并连接：
  - `tool-hive/src/toolhive/runtime/execution/http_executor.py:105`
- 影响：DNS 在两次解析之间发生变化时，实际连接地址可能不是已校验地址。
- 建议：固定已校验 IP 并通过自定义 transport 保持 Host/SNI，或使用具备地址绑定能力的出站网关。

### 3.6 乐观锁检查不是数据库原子更新

- 多个 Service 仅在内存中比较并自增 `row_version`，没有条件更新或行锁：
  - `tool-hive/src/toolhive/services/catalog_tool_service.py:176`
  - `tool-hive/src/toolhive/services/catalog_provider_service.py:139`
- 影响：并发请求可同时通过检查，后提交者覆盖先提交者，版本号也可能只增加一次。
- 建议：使用 `UPDATE ... WHERE row_version = expected` 并检查影响行数，或在必要场景使用 `SELECT FOR UPDATE`。

### 3.7 初始化 SQL 与 ORM 外键约束不一致

- SQL 中以下表的关联列没有定义 `REFERENCES`：
  - `tool-hive/sql/init.sql:57`（账号认证状态）
  - `tool-hive/sql/init.sql:130`（账号角色）
  - `tool-hive/sql/init.sql:233`（角色操作）
  - `tool-hive/sql/init.sql:395`（调用系统工具范围）
  - `tool-hive/sql/init.sql:421`（调用系统公钥）
  - `tool-hive/sql/init.sql:465`（调用系统 IP 规则）
- ORM 则定义了级联外键，例如：
  - `tool-hive/src/toolhive/models/account_auth_state.py:20`
  - `tool-hive/src/toolhive/models/caller_public_key.py:24`
- 影响：数据库可产生孤儿关系，删除主对象时不会按 ORM 预期级联。
- 建议：以迁移脚本为准统一 ORM 与数据库约束，并补充真实数据库 schema 校验。

### 3.8 Provider 配置模型与运行时执行模型不一致

- 配置校验允许多个域名和多个端口：
  - `tool-hive/src/toolhive/services/catalog_common.py:75`
- 运行时要求只能有一个域名，并且只取第一个端口：
  - `tool-hive/src/toolhive/runtime/execution/outbound.py:180`
- 影响：管理端可以保存运行时必然无法执行的配置。
- 建议：要么限制管理配置为单域名单端口，要么实现多目标选择和逐目标校验。

### 3.9 异常响应不会触发 Provider 熔断

- HTTP 状态码错误会记录失败，但 JSON 非法、响应超限和非对象响应均在 `_normalize_response()` 中直接抛错：
  - `tool-hive/src/toolhive/runtime/execution/http_executor.py:84`
  - `tool-hive/src/toolhive/runtime/execution/http_executor.py:146`
- 影响：Provider 持续返回坏响应时不会达到熔断阈值。
- 建议：将所有目标侧协议错误纳入失败统计，并区分可重试与不可重试错误。

### 3.10 缺少正式数据库迁移体系

- 项目依赖包含 Alembic：
  - `tool-hive/pyproject.toml:23`
- 但项目中没有 Alembic 配置、迁移目录或迁移脚本，主要依赖一次性 `sql/init.sql`。
- 影响：生产环境无法可靠演进表结构，容易出现 ORM、初始化脚本和实际数据库结构漂移。
- 建议：建立版本化迁移目录，并在 CI 中执行空库初始化及升级/回滚验证。

## 四、低优先级问题

### 4.1 非法 CIDR 可能返回 500

- `_normalize_cidr()` 只捕获 `AddressValueError`，未捕获 `NetmaskValueError`：
  - `tool-hive/src/toolhive/services/caller_system_service.py:937`
- 实测 `1.2.3.4/999` 抛出 `NetmaskValueError`，没有转换成业务校验错误。
- 建议：统一捕获 `ValueError` 并返回明确的 400 校验错误。

### 4.2 工具范围编码校验与写入未统一 trim

- 校验时调用 `.strip()`：
  - `tool-hive/src/toolhive/services/caller_system_service.py:464`
- 写入时保存原始字符串：
  - `tool-hive/src/toolhive/services/caller_system_service.py:443`
- 影响：带前后空格的编码可能验证通过，但运行时精确匹配失败。
- 建议：在进入 Service 时统一规范化并使用规范化后的值写入。

### 4.3 版本嵌套路由未统一校验父级工具

- 多数接口接收 URL 中的 `tool_id`，但只按 `version_id` 查询或更新：
  - `tool-hive/src/toolhive/api/admin/catalog/versions.py:138`
- `set-default` 是少数显式校验归属的接口。
- 影响：错误的父级资源路径仍可能访问或修改其他工具的版本。
- 建议：所有嵌套路由统一校验 `version.tool_id == tool_id`。

### 4.4 归档工具仍可创建并发布新版本

- 创建版本只校验工具存在，没有拒绝归档工具：
  - `tool-hive/src/toolhive/services/catalog_version_service.py:150`
- 发布流程也没有检查工具状态。
- 影响：目录中会出现归档工具拥有新发布版本的状态矛盾，虽然运行时仍会因工具状态不可用而拒绝执行。
- 建议：归档工具禁止创建、送审和发布新版本。

### 4.5 前端参数映射提示与后端协议不一致

- 前端提示普通字符串映射：
  - `frontend/src/pages/catalog/ToolsPage.tsx:628`
- 后端只有以 `$.` 开头的字符串才会解析为调用参数引用：
  - `tool-hive/src/toolhive/runtime/execution/outbound.py:141`
- 影响：用户按页面提示配置后，映射会被当作固定字符串。
- 建议：统一使用 `{"a":"$.input.a"}` 形式，或在保存时转换并校验映射格式。
