# ToolHive M0 任务清单（按功能模块组织）

> 上游依据：`01-ToolHive平台设计-v0.2.md`
> **组织方式**：按**功能模块**切分，每个模块 = 一块相对独立的代码 + 一组可验收的任务。
> 每个模块都标了「代码位置」与「设计依据」，实现时先打开该模块的代码位置，规则细节查对应设计章节。

---

## 0. 怎么用这份清单

| 说明 | 内容 |
|---|---|
| 模块编号 | `A` ~ `L`，为模块标识；实际依赖与推进顺序以 §1 / §3 为准 |
| 任务编号 | `<模块><序号>`，如 `C4` |
| 「产出」列 | 该任务要创建/修改的**文件或目录**——实现时打开的就是这些 |
| 「验收」列 | 可**自动或可复现**的判定，不写"完成即可" |
| 估算 | 单位**人日**，含自测，不含联调等待 |
| **引用原则** | 任务里**只写"要做什么"与契约标识**（文件路径、配置项名、函数名、错误码名、实体名）；**具体数值与规则条文一律引用设计章节**（如"按 §7.2 矩阵"），**不复制**。原因：本清单是派生物，复制来的文案会产生第二个漂移面 |
| **路径约定** | 本清单里的代码路径**一律相对 `backend/`**（§13 把仓库分成 `backend/` 与 `frontend/`）。如 `src/toolhive/core/domain/` 实指 `backend/src/toolhive/core/domain/`。因此下文不再重复 `backend/` 前缀 |
| **术语** | `protocols/` = 设计里说的「协议前端」（REST / MCP / 管理 API），**是后端代码**；`frontend/` = 浏览器里的管理台界面（M1）。两者**不是一回事**，目录原名 `frontends/` 已改名以免一词二义 |

> **关于「测试」二字的口径（重要）**：M0 **不建测试套件**——没有 pytest、没有 testcontainers、
> 没有 CI 流水线，自动化验证保留架构断言及本地异常路径回归（设计 §14.3）。因此本文档「验收」列里出现的
> 「单测覆盖 X」/「测试逐格覆盖」/「测试覆盖 X」**一律理解为「手工构造该场景，验证 X 成立」**。
> 唯二的例外是 `A6`（架构断言）与 `A5`（手动验证脚本）——它们仍然是可执行代码。

> 2026-10-07 补充：高影响异常路径保留 `scripts/regression.py` 的本地回归，
> 不依赖 pytest、Docker 或线上服务。它覆盖 ID/租约/超时/加锁刷新/加密轮换/配置/指标，
> 与架构断言共同执行；不能把“手工验收”理解为不保留缺陷复现。
>
> **已移除的任务**：`K3`（CI 门禁）、「100~200 条标注集」。**已改变性质的任务**：
> `A5`（CI 流水线 → 手动验证脚本）、`C2`（契约测试 → 人工核对）、`I4`（契约快照 → OpenAPI 导出）、
> `L1`（E2E 测试 → 手动验收清单）。**任务编号保持不变**，因为 `03` 与 `04` 文档里有交叉引用。

**建议工作方式**：按依赖推进，模块清单保留为最终交付范围。完成 C 的最小领域模型后，
先贯通一个真实工具的授权、凭据注入、受控执行与审计，再补齐各模块能力。
每次贯通都保留可复现的命令和预期结果；L 汇总并复验已有链路，不能到 L 才开始跨模块联调。

**设计补充的落地位置**：业务工具抽象、副作用/重试安全与执行配置版本边界以设计 §4.2 为准；
部署边界以 §3.4 为准；协议无关的错误语义以 §7.4 为准。新增字段须同步实现 C 的迁移与 ORM，
不能只在导入器或内核维护临时属性。本文档只引用规则，`03` 已同步字段定义。

## 1. 模块依赖图

```
A → B → C
C → D / E / G / H
C + D + E → F
F + H → I
C + D + E + G + H → J
H + I → K
A ～ K → L
```

**执行主链**：A → B → C → D/E → F；完整 REST 交付还需 H → I。
**可并行**：C 的契约确定后，D、E、G、H 可并行；共享模型变更仍需同步。
该图表示完整模块的依赖，不要求完成整个模块后才能联调其已实现的能力。

# B · 持久化与适配层

**职责**：把"数据库、缓存、密钥、出站 HTTP"四件基础设施包成后面模块可直接用的接口。
**代码位置**：`src/toolhive/adapters/` —— `db/` 与 `cache/` 是多模块子包；
`crypto.py` / `http.py` / `snowflake.py` **单文件直接放在本层**（不再各建一个空壳子包）
**设计依据**：§7.2 横切关注点、§10.1 凭据与 KEK、§10.2 出站安全、**§4.4 雪花 ID 位分配与发号规则**、§12 技术选型

**边界**：本模块**不含业务规则**——不判断权限、不算配额、不组装请求。

| # | 任务 | 产出 | 验收 |
|---|---|---|---|
| B1 | 数据库会话与事务 | `adapters/db/session.py` | `get_db()` 不自动提交；`@transactional` 支持嵌套与 `requires_new`（独立 session 提交，不受外层回滚影响）；单测覆盖三种情况 |
| B2 | 仓储基类 | `adapters/db/repository.py` | 提供按 ID 查询、`with_for_update` 加锁刷新、乐观锁 `row_version` 比对三个能力 |
| B3 | Redis 客户端与 Lua 脚本 | `adapters/cache/client.py`、`adapters/cache/scripts/` | 连接池与超时可控；Lua 脚本以文件管理（令牌桶/滑动窗口/信号量）；**原子性靠手工验证**——并发打同一个 key，观察计数不超限（**M0 不引入 testcontainers**） |
| B4 | KEK 与信封加密 | `adapters/crypto.py` | 读 `TOOLHIVE_KEKS`（JSON 多把）+ `TOOLHIVE_ACTIVE_KEK_ID`；每条凭据独立随机 DEK + AES-256-GCM；按 `kek_id` 解密；**密钥不出现在日志/异常信息里**（单测断言） |
| B5 | 出站 HTTP 客户端 | `adapters/http.py` | `verify=True`、`follow_redirects=False`、`trust_env=False`；支持整体 deadline 传播；连接池参数可配 |
| B6 | **雪花 ID 生成器** | `adapters/snowflake.py` | **位分配、纪元、发号规则全部按 §4.4**（不在此复制数值）；产出 `bigint`；`datacenter_id` / `worker_id` 来自配置；**启动时用 Redis 抢 `(dc, worker)` 租约并定期续租，抢不到即拒绝启动**（§4.4）；手工验证覆盖**10w 次无重复且趋势递增**、序列用尽阻塞、小幅回退自旋、大幅回退报错 |

## 3. 实现顺序建议

| 批次 | 模块 | 说明 |
|---|---|---|
| 第 1 批 | **A** | 基座，必须最先 |
| 第 2 批 | **B** | B 解锁所有模块 |
| 第 3 批 | **C** | 先确定模型、版本语义与状态机，提供最小可用领域服务 |
| 第 4 批 | **D**、**E**、**G**、**H** | C 契约确定后可并行；优先实现首条真实调用所需的 D/E 能力 |
| 第 5 批 | **F** 与最小协议入口 | 贯通首条真实工具链路，验证授权、SSRF、凭据保护、deadline、审计与异常资源释放；未实现能力须明确拒绝，不能绕过策略 |
| 第 6 批 | 补齐 **D/E/F/G/H**，推进 **J**、**I** | 按已具备的能力逐命令/路由接入；J 的完整交付依赖 C/D/E/G/H，I 依赖 F/H |
| 第 7 批 | **K** | 使用已贯通的检索接口验证候选质量与降级 |
| 第 8 批 | **L** | 汇总既有联调证据，复验完整验收清单 |

**两人分工建议**：
- 共同确定 A/B/C 契约；甲负责 D → F → I，乙负责 E → G/H → J → K。
- 甲乙在 D/E 的最小能力就绪时共同贯通首条链路，持续同步共享模型与任务入口契约。
- 汇合做 L；该分工仅说明责任覆盖，实际并行程度取决于人员与接口就绪情况。
