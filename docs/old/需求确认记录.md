## 一期交付拆分

- 一期拆分为上、下两部分，确认、开发和验收顺序先管理侧、后工具侧。
- 一期上半部分用于管理侧，包含管理前端、管理侧 API、管理账号、后台角色、管理操作项，以及调用系统、能力包、Provider、工具、版本、审核和发布等配置管理能力。
- 一期下半部分用于工具侧，包含工具运行侧 API、调用系统认证、工具发现、工具调用控制、Provider 调用、工具执行和基础 Trace 等运行能力，不配置独立前端。
- 上、下两部分是同一期内的交付拆分，不代表拆成两个后端项目；两部分仍由同一套 ToolHive 后端承载并共享核心数据模型。
- 已确认的工具侧问题继续有效，不因确认顺序调整而重新开放；管理侧补充问题确认完成后，再继续处理尚未确认的工具侧问题。

## 总体确认

### Q01：一期拆分、交付范围与管理页面

- 一期按照上半部分管理侧、下半部分工具侧拆分交付，并最终形成最小可闭环的 HTTP 工具调用链路。
- 管理侧一期必须包含管理员登录、退出、修改密码、管理员账号管理、后台角色管理、调用系统管理、能力包管理、Provider 管理、工具管理、工具版本管理、审核、发布、启用和停用等页面与对应 API。
- 管理侧一期还要支持后台角色对管理动作的授权和校验，但不把管理动作与工具调用能力混为一类。
- 工具运行侧一期只保留必要的查询、授权判断和执行接口，不配置独立前端。
- 一期的工具调用链路至少要覆盖配置、审核、授权、解析、执行和基础审计或追踪闭环。
- 一期交付内容不包括监控看板、报表、SSO 实接入、MCP、gRPC、异步长任务、高级发布回滚、成本与质量评估，以及多地域容灾等能力。

### Q02：系统整体形态与 API 分类

- ToolHive 是一套后端系统和一个后端项目，不拆分成相互独立的管理后端与工具执行后端。
- 同一套后端业务中包含管理侧 API 和工具运行侧 API，两类 API 共享工具目录、策略、Provider、Trace 和数据模型等核心能力。
- 管理侧 API 面向平台管理员和管理前端，采用管理账号登录、会话和后台角色校验方案。
- 管理侧需要配套 Web 前端，用于后续承载账号、后台角色、调用系统、工具和 Provider 等管理功能。
- 工具运行侧 API 面向 Agent、业务系统或其他服务调用方，不配置独立前端。
- 工具运行侧 API 包含工具检索、工具调用权限判断和工具执行等能力，采用与管理侧不同的调用系统身份认证和授权方案。
- 管理账号的登录凭据不能用于调用工具运行侧 API，调用系统的身份凭据也不能用于访问管理侧 API。
- 两类 API 是否使用不同端口、域名、网关或网络监听地址，不在本项中确定，留到生产部署和运行接口网络策略问题中单独确认。

### Q03：生产部署与环境拓扑

- 当前只保留开发和生产两个环境，不再拆分测试和预发布环境。
- 开发环境运行在 Win11 机器上。
- 生产环境运行在 Linux 系统上。
- 开发和生产接入的模型 key 使用不同值，通过各自环境的配置文件加载。
- 生产环境使用 Nginx 做入口代理和负载均衡。
- ToolHive 后端在生产 Linux 环境部署，同一后端承载管理侧 API 和工具运行侧 API。
- 管理前端由 Nginx 或同类 Web 服务承载，可与 ToolHive 后端部署在同一台服务器，也要保留后续独立部署的空间。
- ToolHive 如需调用模型服务或模型网关，例如 Embedding、工具解析、工具选择等场景，由 ToolHive 后端通过环境配置中的模型 key 统一发起访问；模型 key 不暴露给管理前端和外部调用系统。
- 运行接口内外网开放策略留到 Q09 单独确认；PostgreSQL、Chroma 和缓存等数据组件的具体部署、备份和容量要求留到 Q24 单独确认。

## 一期上半部分：管理侧已确认

### Q04：管理账号生命周期

- 首次部署时通过一次性初始化命令创建首个超级管理员；用户名和初始密码由部署人员提供，不在代码中内置固定账号或密码。
- 初始化操作仅在尚无管理账号时执行；已有管理账号时不得重复创建或覆盖首个超级管理员。
- 不开放注册入口和公开注册 API；后续管理账号只能由具备账号管理能力的管理员通过管理后台创建。
- 新建账号使用临时密码，首次登录必须修改；登录用户可以修改自己的密码。
- 管理员可以重置其他账号的密码，但不能查看原密码；重置后使用临时密码，且用户下次登录必须修改。
- 密码只保存不可逆哈希，不保存或回显明文密码。
- 管理账号支持启用、禁用和锁定，不进行物理删除；禁用或离职账号保留基本信息和历史审计关联，用户名不得重新分配给其他人员。
- 默认连续登录失败 5 次后锁定 30 分钟，失败次数和锁定时间均可配置；锁定到期后自动恢复，也可由具备账号管理能力的管理员提前解锁，登录成功后清空失败次数。
- 支持管理员对指定账号执行强制下线；账号被禁用、密码被重置或进行离职处理时，立即撤销该账号的全部有效会话。
- 系统必须始终保留至少一个启用状态的超级管理员；不允许禁用最后一个超级管理员，也不允许当前管理员停用自己的账号。
- 管理侧的本地登录与 SSO 扩展方式按照 Q05 执行，密码、MFA 和会话安全参数按照 M02 执行。

### Q05：登录方式与 SSO 扩展

- 本项只规定管理侧人员的登录认证，不涉及工具运行侧的调用系统认证。
- 一期仅支持本地用户名和密码登录，不开放注册；账号创建和维护遵循 Q04。
- 本地登录成功后建立可撤销的管理会话，以支持强制下线，以及账号禁用或密码重置后立即撤销会话；Cookie、会话存储、超时时间和互斥登录规则按照 M02 执行。
- 一期不实际接入 SSO，也不提前限定必须使用 OIDC、SAML 或企业自有认证协议；后端只预留统一的 SSO 认证接入层，待外部身份系统明确后再实现相应适配器。
- 管理账号增加一个可空且唯一的 `external_user_id` 字段，用于保存工号或外部系统中稳定、唯一且不会重复使用的账号标识；该字段由内部管理员维护。
- 当前不建立独立的外部身份表，不支持一个管理账号绑定多个外部身份，也不根据姓名或邮箱进行自动匹配。
- 后续接入 SSO 时，由适配器完成外部认证并向 ToolHive 返回唯一人员标识；ToolHive 使用该标识匹配 `external_user_id` 对应的内部管理账号。
- SSO 返回的标识找不到内部管理账号时拒绝登录，不自动创建账号或自动绑定；匹配成功后仍须检查内部账号状态，并按 ToolHive 内部配置的后台角色进行授权。
- SSO 只负责确认管理人员身份，不自动同步外部组织、部门或角色，也不赋予工具运行侧调用能力。
- 后续接入 SSO 后仍至少保留一个本地超级管理员作为故障应急入口；是否关闭其他普通账号的本地密码登录，在实际接入 SSO 时通过配置确定。

### Q06：后台角色与管理操作项

- 本项只控制管理账号可以在管理平台中执行哪些操作，不控制调用系统能否执行工具。
- 管理账号与后台角色为多对多关系，后台角色与管理操作项也为多对多关系；一个账号最终可执行的管理操作，是其全部后台角色所含管理操作项的并集。
- 管理操作采用默认拒绝原则；一期只支持允许项，不引入显式拒绝和角色继承。
- 登录、退出、查看本人信息和修改本人密码属于账号基础能力，不要求分配后台角色。
- 系统内置不可删除、不可修改的超级管理员角色，并自动拥有当前及以后新增的全部有效管理操作项。
- 普通后台角色可由具备相应管理能力的管理员创建、修改、启用、停用、归档和分配管理操作项；角色不进行物理删除，以保留历史审计关系。
- 普通角色停用、角色从账号移除或管理操作项被撤销后应立即生效，不要求账号重新登录；会话只保存账号身份，不永久固化角色和管理操作项快照。
- 只有超级管理员可以授予或移除超级管理员角色；普通管理员不能授予自己不具备的管理操作项，也不能修改超级管理员账号和超级管理员角色。
- 不允许移除最后一个启用状态超级管理员的超级管理员角色。
- 管理侧的功能控制单元统一称为“管理操作项”，每项使用稳定且唯一的操作码，按照“管理对象 + 操作”定义，例如 `admin_account:view`、`role:assign`、`tool:review` 和 `tool:publish`。
- 管理操作项的显示名称可以修改，但已发布的操作码不得修改、删除或复用于其他功能；废弃时标记为停用。
- 管理操作项由代码定义，不能由管理员在管理页面中任意创建；新增时必须同时完成后端操作码声明、管理 API 校验、前端菜单或按钮关联，以及启动或数据库升级时的目录同步。
- 新增管理操作项默认只对超级管理员生效，不自动授予已有普通角色；是否授予普通角色由管理员明确配置。
- 管理前端依据账号拥有的管理操作项控制菜单、页面和按钮的展示，管理后端对受控 API 使用相同操作码进行强制校验；前端隐藏不能替代后端安全校验。
- 未登录访问受控管理 API 时返回未认证，已登录但缺少对应管理操作项时返回无权操作。
- 一期只实现管理功能的操作级控制，不增加按部门、人员或数据行划分的后台数据范围。
- 超级管理员自动拥有全部管理操作项，但不会因此获得工具运行侧调用能力；两套控制体系的正式名称和边界留到 Q07 确认。

### Q07：后台管理与工具调用控制边界

- 管理侧采用“后台角色”和“管理操作项”两个业务名称；工具运行侧的控制体系称为“工具调用控制”，其最终计算结果称为“工具调用范围”，不再使用含义模糊的统一“权限管理”。
- 管理侧控制的主体是管理账号，控制对象是后台页面和管理 API；管理账号通过后台角色获得管理操作项，并使用管理登录会话访问管理侧 API。
- 工具运行侧控制的主体是调用系统及请求中携带的业务身份，控制对象是可以发现和执行的工具；调用系统使用 `system_id` 及运行接口认证凭据访问工具运行侧 API。
- 工具调用控制需要结合调用系统、业务身份、能力包、工具范围及策略进行判断，得到当前请求的工具调用范围；具体计算模型留到 Q15 确认。
- 能力包只是工具调用控制中的配置载体，用于组织一组相关工具或能力，不是独立的第三套控制体系，也不等同于最终工具调用范围。
- 管理账号能够配置、审核、发布或停用工具，只表示其具有相应管理操作项，不表示该账号自身能够通过运行接口调用工具。
- 管理账号登录凭据只能访问管理侧 API，调用系统凭据只能访问工具运行侧 API；后台角色不能直接关联工具或能力包，工具调用范围也不能赋予访问管理页面或管理 API 的能力。
- 两套控制体系可以共享工具目录、能力包和调用系统等业务数据，但身份凭据、数据关系和校验结果必须相互隔离，不能使用一张通用控制表混合建模。
- 超级管理员自动拥有全部管理操作项，可以维护工具、调用系统和能力包，但不自动获得任何工具调用范围。
- 超级管理员如需实际调用工具，仍必须使用已登记的调用系统身份，并通过运行接口认证、来源 IP、签名、防重放和工具调用范围等完整校验。
- 后续若在管理后台增加工具测试执行功能，应使用专门的测试调用身份并记录审计，不允许超级管理员直接绕过工具运行侧校验。

### Q08：调用系统登记与生命周期

- “调用系统”表示调用 ToolHive 运行接口的外部软件系统，不表示管理账号或最终业务用户。
- 调用系统按照“一个外部项目 + 一个运行环境”的粒度登记；同一外部项目的开发环境和生产环境必须分别登记，并使用不同的 `system_id`、认证凭据、来源 IP 规则和工具调用范围。
- 同一环境内的多个服务实例可以共用一条调用系统记录；需要独立停用、独立审计或不同调用范围时，应分别登记。
- `system_id` 由 ToolHive 自动生成，采用带 `sys_` 前缀的 UUID 或同类无业务含义全局唯一标识，不允许管理员手工填写。
- `system_id` 创建后永久不变，调用系统注销后也不得重新分配；`system_id` 只是公开的调用系统标识，不能单独作为身份认证凭据。
- 调用系统主记录至少包含系统名称、系统说明、所属环境、所属部门或团队、主要负责人、联系方式、当前状态、可选生效和失效时间、创建和修改信息，以及停用或注销原因。
- 系统名称用于管理页面和审计阅读，可以修改，不编码到 `system_id` 中。
- 来源 IP 规则、认证凭据、运行 API 范围、流量限制、能力包和工具调用范围均作为调用系统的关联配置维护，不直接固化在调用系统主记录中，以支持一对多配置和后续扩展。
- 来源 IP 规则留到 Q10 确认；身份凭据、请求签名和密钥生命周期留到 Q11 确认；运行 API 范围和流量限制留到 Q13 确认；工具调用范围留到 Q15 确认。
- 调用系统生命周期采用“草稿、已启用、已停用、已注销”；“已过期”根据有效期自动判断，不作为管理员手工选择的生命周期状态。
- 草稿状态可以配置负责人、凭据、来源 IP 和调用范围，但不能调用运行接口。
- 已启用状态允许正常发起调用；已停用状态立即拒绝该系统的全部运行接口请求，但保留配置并允许重新启用。
- 超过失效时间后自动拒绝请求；延长有效期并重新确认后可以恢复。
- 已注销表示永久停止使用，立即撤销全部认证凭据，不允许重新启用，且 `system_id` 永不复用。
- 调用系统不进行物理删除，以保留历史调用记录和管理审计关系。
- 调用系统启用前必须具备明确的环境和负责人、有效身份认证凭据、来源 IP 规则、允许运行 API 范围，以及至少一个能力包或明确的工具调用范围；设置有效期时，当前时间还必须处于有效期内。
- 新建调用系统默认没有任何工具调用范围，启用状态也不表示自动获得全部工具。
- 具备相应管理操作项的管理员可以启用、停用和注销调用系统；状态变更必须立即对运行接口生效，不等待缓存过期或调用方重新获取凭据。
- 临时维护、异常流量或疑似凭据泄漏时使用停用；系统永久下线时使用注销。
- 调用系统本身的生效和失效时间可以为空；长期正式业务系统可以不设置失效时间，临时联调、临时项目或外部合作调用方必须设置失效时间。
- 调用系统长期有效不代表认证凭据永久有效，认证凭据应设置独立有效期并按 Q11 确认的规则轮换。
- 创建、启用、停用、恢复和注销操作均记录操作人、时间和原因，具体审计字段和留存规则留到 Q23 确认。

### M01：管理入口网络与安全策略

- 一期管理前端和管理侧 API 允许通过公网 HTTPS 访问，不强制管理员连接公司内网或 VPN。
- 生产访问链路统一为“管理员浏览器 → 公网 HTTPS → Nginx → 管理前端或管理侧 API → ToolHive 后端”；只开放 Nginx 的 HTTPS 入口，ToolHive 后端应用端口不得直接暴露到公网。
- Nginx 使用独立路径区分管理页面、管理 API 和工具运行 API：`/admin/**` 用于管理前端静态资源和页面路由，`/api/admin/**` 用于管理侧 API，`/api/runtime/**` 用于工具运行侧 API。
- `/admin/**` 和 `/api/admin/**` 允许公网访问；`/api/runtime/**` 一期仍仅允许内网来源，公网请求由 Nginx 直接拒绝，不转发给 ToolHive。
- 管理前端与管理 API 一期默认使用同一域名，避免不必要的跨域、Cookie 和 CORS 配置。
- 一期默认不对每个管理员强制配置来源 IP 白名单，但 Nginx 必须保留可选的管理侧 IP 或网段限制能力，以便指定公司出口、VPN 网段或在安全事件中临时收紧访问范围。
- 管理侧来源限制与调用系统的来源 IP 白名单相互独立，不共享配置和校验结果。
- 生产环境的 HTTP 请求自动跳转 HTTPS，只启用 TLS 1.2 和 TLS 1.3，并使用浏览器能够正常信任的证书。
- Nginx 应配置 HSTS、禁止页面被其他网站嵌入、禁止 MIME 类型猜测等浏览器安全 Header，并覆盖或清理不可信的代理 Header。
- 管理 API 默认不开放跨域；后续前后端确需分域部署时，只允许部署配置中明确列出的来源。
- Nginx 对管理登录接口增加按来源的基础请求限流；应用层继续执行 Q04 已确认的账号锁定、账号禁用、会话撤销、关闭注册和统一登录失败提示规则。
- 验证码、MFA、密码复杂度、会话存储和会话时长统一按照 M02 执行。
- 管理前端地址和管理 API 地址通过部署配置提供，不在前端代码中写死服务器 IP；后续独立部署管理前端或接入 SSO 时，不改变管理 API、Nginx 路由和后台角色模型。

### M02：本地登录安全参数

#### 密码规则

- 管理账号密码长度至少 12 位、最多 128 位，支持长密码短语；不强制大小写字母、数字和特殊字符必须同时出现。
- 密码不得与用户名、工号或常见弱密码相同，且不能与最近 5 个历史密码重复。
- 密码使用 `Argon2id` 自适应哈希并为每个密码生成独立随机盐；哈希参数根据生产服务器性能配置，并支持以后自动升级和重新哈希。
- 默认不设置固定的周期性密码过期时间；发生泄漏、管理员重置或安全事件时强制修改。
- 新建和重置账号使用安全随机生成的临时密码，临时密码 24 小时后失效，首次登录必须修改。
- 不提供公开的“忘记密码”自助接口，忘记密码仍由管理员按照 Q04 重置。

#### 登录失败与验证码

- 继续执行 Q04 已确认的默认规则：连续登录失败 5 次后锁定 30 分钟，登录成功后清空失败次数，具备账号管理能力的管理员可以提前解锁。
- 同一账号或来源 IP 在 10 分钟内连续失败 3 次后，后续登录必须完成验证码；即使用户名不存在，也按来源 IP 触发相同规则，避免据此枚举账号。
- 验证码通过后仍须校验密码，不能解除已经生效的账号锁定。
- Nginx 和应用同时限制登录请求频率，防止通过大量更换用户名绕过账号锁定；失败次数和时间窗口均作为环境配置项，文档中的数值为默认值。

#### MFA

- 由于管理侧允许公网访问，一期对全部管理账号强制启用基于标准验证器应用的 TOTP MFA，不使用短信或邮件验证码。
- 管理员首次完成密码修改后必须绑定 TOTP；绑定完成前只能访问账号安全设置，不能进入其他管理页面。
- TOTP 密钥加密保存，只在绑定时展示一次；每个账号生成 8 个一次性恢复码，恢复码只展示一次并以哈希形式保存。
- 一期不提供“记住此设备”，每次重新登录均须完成 MFA；同一个 TOTP 动态码在有效时间窗口内只能使用一次，MFA 连续失败同样计入登录安全限制。
- 管理账号的 MFA 只能由超级管理员重置；重置后立即撤销该账号的全部会话，并要求下次登录重新绑定。
- 最后一个超级管理员同时丢失 MFA 和恢复码时，只允许通过服务器上的一次性应急命令重置，并必须记录安全审计。
- 后续接入 SSO 时，是否使用身份提供方完成的 MFA 代替本地 TOTP，在实际接入时单独确认。

#### 管理会话与互斥登录

- 登录成功并完成 MFA 后，由后端生成至少 256 位安全随机会话 ID；会话保存在所有 ToolHive 实例共享的服务端存储中，不能只保存在单个应用进程。
- 浏览器只保存会话 Cookie，Cookie 必须设置 `HttpOnly`、`Secure` 和 `SameSite=Lax`，不得设置宽泛的父域作用范围，也不得将登录 Token 保存到 `localStorage`。
- 共享会话存储不可用时拒绝访问，不能退回本地进程会话；具体采用 Redis 或其他共享存储留到 Q24 确认。
- 管理会话默认连续 30 分钟无操作后失效，单次登录最长有效 8 小时；一期不提供“记住我”，时长允许通过环境配置调整。
- 管理账号采用互斥登录，同一账号在任意时刻只允许存在一个有效管理会话；本地登录和后续 SSO 登录均遵守相同规则。
- 新登录在密码和 MFA 全部验证成功后，以原子方式撤销该账号旧会话并激活新会话；并发登录时必须保证最终只保留一个有效会话，旧会话下一次请求立即返回未认证。
- 管理员可以查看当前有效会话的登录时间、来源 IP 和最近活动时间，超级管理员可以对其他账号执行强制下线。

#### 会话撤销与权限变化

- 账号被禁用或进行离职处理、管理员重置密码、MFA 被重置或执行强制下线时，立即撤销该账号的有效会话。
- 用户主动修改自己的密码时，重新生成当前会话 ID；由于采用互斥登录，不再保留任何其他旧会话。
- 后台角色或管理操作项变化时不强制退出，但下一次请求必须立即依据最新配置校验，不能继续使用旧角色快照。
- 登出时服务端立即删除会话，不能只清除浏览器 Cookie。

#### CSRF 与敏感信息保护

- 管理侧使用 Cookie 会话，所有新增、修改、删除、审核和发布等非只读请求必须校验 CSRF Token，并检查 `Origin` 或 `Referer` 是否来自允许的管理前端。
- 登录成功、MFA 完成、权限提升和密码修改后重新生成会话 ID，防止会话固定攻击。
- 会话 ID、密码、TOTP 密钥和恢复码不得写入日志。

## 一期下半部分：工具侧已确认

### Q09：运行接口的网络开放策略

- ToolHive 不因网络开放策略拆分后端项目，管理侧和工具运行侧由 Nginx 使用互不重叠的路径前缀进行路由区分，例如管理侧使用 `/api/admin/**`，工具运行侧使用 `/api/runtime/**`。
- 管理前端静态资源和管理侧 API 按 M01 通过公网 HTTPS 开放；工具运行侧 API 一期仅允许通过内网 HTTPS 访问，不直接向公网开放。
- 一期由 Nginx 对工具运行侧路径仅放行明确配置的内网 IP 或网段，并默认拒绝其他来源；服务器防火墙同时限制工具运行侧入口，不能只依靠路径不同实现网络隔离。
- ToolHive 后端应用端口不直接向管理端、调用系统或公网开放，管理侧和工具运行侧请求均必须经过 Nginx 转发。
- 工具运行侧来自内网的请求仍必须完成调用系统状态、`system_id`、身份凭据、来源 IP、签名、防重放、运行 API 范围和工具调用范围等完整校验，私网不能替代应用认证。
- 具体允许的 IP、网段、通配符规则及经过代理时的真实来源 IP 判断方式留到 Q10 确认。
- 对外访问地址和路由前缀通过部署配置提供，不在 ToolHive 或调用系统代码中写死私网 IP。
- 后续需要开放公网 HTTPS 时，继续复用现有工具运行侧 API 和路由规范，通过调整 Nginx 路由开放策略或增加公网 API 网关和 WAF 对外提供服务。
- 公网化后 ToolHive 后端仍部署在私网，不直接分配公网访问入口；原有调用系统认证、签名、防重放、工具调用范围和审计协议继续使用，不因公网化而重构。
- 未来公网域名、证书、WAF 或 API 网关产品、开放时间及是否同时保留内外网入口，在实际公网化时确定。

### Q10：来源 IP 白名单与可信代理

- 来源 IP 采用两层控制：Nginx 负责限制能够访问工具运行侧路由的整体网络范围，ToolHive 再根据 `system_id` 校验对应调用系统的来源 IP 白名单。
- 来源 IP 白名单按照“调用系统 + 环境”独立配置；同一外部项目的开发和生产调用系统不得共用白名单。
- 每个调用系统可以配置多条允许规则，请求命中任意一条即可；未配置任何规则时默认拒绝全部请求，且调用系统不能启用。
- 白名单支持单个 IPv4、IPv4 CIDR 网段、单个 IPv6、IPv6 CIDR 网段和特殊值 `*`。
- 不支持 `10.20.*.*` 等模糊地址写法，网段统一使用 CIDR；不支持使用域名作为来源规则。
- 地址保存前必须校验并标准化，使用标准 IP 地址库完成网段判断，不允许通过字符串前缀匹配；IPv4 映射形式的 IPv6 地址应规范化后再匹配。
- `*` 表示不再对该调用系统做具体来源 IP 限制，但不会绕过 Nginx 网络限制、调用系统状态、身份凭据、签名、防重放、运行 API 范围和工具调用范围等检查。
- 生产环境允许使用 `*`，但作为高风险配置处理：需要单独的管理操作项，例如 `caller_system:allow_any_ip`，配置时二次确认并填写原因，同时记录操作审计。
- `*` 与具体 IP 或网段规则互斥；配置 `*` 后不得同时保留其他来源规则，避免产生错误理解。
- 一期工具运行侧仅内网访问，因此生产环境的 `*` 只表示允许所有能够到达内部 Nginx 的来源；未来开放公网前必须重新检查所有配置了 `*` 的生产调用系统，不能默认沿用原配置对公网开放。
- 调用方直接访问 Nginx 时，以 Nginx 实际连接看到的源地址为准，不能直接相信调用方传入的 `X-Forwarded-For`、`X-Real-IP` 或同类 Header。
- Nginx 前存在负载均衡器或其他网关时，只信任部署配置中明确登记的代理 IP 或代理网段；仅当请求确实来自受信任代理时，才解析代理转发的来源 IP。
- 存在多级代理时，从代理链后方向前查找，第一个不属于受信任代理的地址作为真实来源 IP；生产环境禁止将所有地址配置为受信任代理。
- Nginx 转发请求时必须覆盖调用方传入的来源 IP Header，并向 ToolHive 传递重新解析后的来源信息；ToolHive 只接收来自 Nginx 的请求，也只信任 Nginx 生成的来源信息。
- 调用系统经过 NAT、统一出口或服务网关时，白名单配置 Nginx 实际观察到的出口 IP，而不是调用系统实例自身的地址。
- 一期请求依次经过 Nginx 内网来源限制、ToolHive 调用系统白名单、身份签名及工具调用控制；两层来源检查均通过后才进入后续执行流程。
- 白名单新增、修改、停用或删除后应立即生效；IP 不匹配时返回统一拒绝结果，不向调用方披露允许的 IP 清单。
- 审计记录保留本次解析出的来源 IP、调用系统和匹配结果，详细字段和留存规则留到 Q23 确认。

### Q11：调用系统身份认证、请求签名与密钥生命周期（合并原 Q12）

- 一期采用“HTTPS + 来源 IP 白名单 + 公私钥请求签名”的调用系统认证方案；HTTPS 负责传输加密和服务端身份确认，来源 IP 白名单负责限制请求来源，公私钥签名负责调用系统身份确认、请求完整性校验和防重放。
- `system_id` 只是公开的调用系统标识，不能单独作为认证凭据；一期不使用固定 API Key 或共享密码作为唯一认证方式。
- 公私钥请求签名是一期唯一必须实现的调用系统认证方式；一期不强制 mTLS，也不实现 OAuth2 Client Credentials。
- 后续可为高风险系统或公网调用方增加“请求签名 + mTLS”组合认证；如果未来企业网关或身份中心提供 OAuth2，可增加适配器将 `client_id` 映射到 `system_id`，但新增认证方式仍不能绕过调用系统状态、来源 IP、运行 API 范围和工具调用范围校验。

#### 公私钥归属与绑定

- 每个调用系统、每个环境分别维护自己的密钥，开发和生产不得共用同一对密钥。
- 密钥对由调用系统一侧生成；私钥只保存在调用系统自己的配置中心或密钥管理设施中，不得上传、传输或保存到 ToolHive。
- ToolHive 只保存公钥、`key_id`、算法、公钥指纹、状态和有效期；公钥使用 PEM 编码的 `SubjectPublicKeyInfo` 格式，调用方私钥建议使用 PKCS#8 格式。
- 同一公钥不能绑定到多个调用系统；一个调用系统允许同时存在多把有效公钥，以支持无停机轮换。
- `key_id` 由 ToolHive 为每条公钥记录生成，并与 `system_id` 绑定；验证时 `key_id` 必须属于请求中的 `system_id`。

#### 签名算法

- 一期只支持 `RSA-PSS-SHA256`，不允许调用方自行选择或降级算法。
- RSA 密钥长度至少为 2048 位，摘要算法为 SHA-256，MGF 使用 MGF1-SHA256，Salt 长度固定为 32 字节。
- 签名结果使用不带尾部填充符的 Base64URL 编码。
- 算法由 ToolHive 中登记的公钥记录决定；后续增加其他算法时使用新的签名版本扩展，不改变已有版本含义。

#### 请求认证字段

- 每个工具运行侧请求至少携带 `X-ToolHive-System-Id`、`X-ToolHive-Key-Id`、`X-ToolHive-Timestamp`、`X-ToolHive-Nonce`、`X-ToolHive-Content-SHA256`、`X-ToolHive-Signature-Version` 和 `X-ToolHive-Signature`。
- 时间戳使用 UTC Unix 秒；`nonce` 使用至少 128 位安全随机数。
- 请求体摘要使用请求原始字节计算 SHA-256；无请求体时计算空字节摘要。
- ToolHive 必须根据实际收到的请求体重新计算摘要，不能直接相信调用方提交的摘要值。

#### 待签名内容

- 一期签名版本固定为 `TOOLHIVE-SIGN-V1`。
- 待签名字符串依次包含签名版本、`system_id`、`key_id`、时间戳、`nonce`、大写 HTTP 方法、规范化路径、规范化查询参数、内容类型和请求体 SHA-256 摘要。
- 各字段之间使用单个换行符连接，整体采用 UTF-8 编码，不增加额外尾部换行。
- 路径使用调用方实际访问的 `/api/runtime/**` 路径，Nginx 转发时必须保持该路径不变。
- 查询参数按照 RFC 3986 编码，并按参数名、参数值排序；重复查询参数必须保留。
- 请求体按收到的原始字节计算摘要，不能先解析 JSON 再重新序列化。
- 影响业务语义的 Header，例如后续确定的幂等键，必须纳入签名内容或放入请求体。
- 实现时必须提供固定测试向量，包含请求内容、待签名字符串、摘要和最终签名，供不同语言的调用系统验证兼容性。

#### 时间窗口与防重放

- ToolHive 接受服务器时间前后 5 分钟内的请求，调用系统和 ToolHive 服务器必须保持可靠的时钟同步；超出时间窗口的请求直接拒绝。
- `nonce` 在同一 `system_id + key_id` 下只能使用一次，已验证通过的 `nonce` 至少保存 10 分钟。
- `nonce` 必须保存在所有 ToolHive 实例共享的存储中，不能只存于单个应用进程；写入必须具备原子“首次写入成功”能力，重复写入立即拒绝。
- 防重放共享存储不可用时应拒绝请求，不能跳过检查继续执行；具体存储产品留到 Q24 确认，优先使用支持 TTL 和原子写入的缓存。
- 调用方重试请求时必须生成新的时间戳、`nonce` 和签名；写操作的业务幂等使用独立幂等键，不能使用 `nonce` 代替。

#### 密钥状态与轮换

- 每条公钥记录包含 `key_id`、`system_id`、公钥内容、公钥 SHA-256 指纹、签名算法、生效时间、失效时间、状态，以及创建、启用、停用和撤销信息。
- 密钥状态采用“待启用、有效、已停用、已过期、已撤销”；已停用可以恢复，已撤销不可恢复且 `key_id` 不得复用。
- 已过期密钥不直接延长有效期，应登记并启用新密钥。
- 生产密钥必须设置失效时间，默认有效期建议为一年；具体时长允许通过环境配置调整。
- 密钥轮换时允许新旧两把公钥短时间同时有效：调用方生成新密钥对，管理员登记并启用新公钥，调用方切换并验证成功后，再停用或撤销旧公钥。
- 新旧密钥同时有效的截止时间必须明确配置，不能无限期重叠。

#### 泄漏与紧急处置

- 发现或怀疑私钥泄漏时，立即停用调用系统或撤销对应 `key_id`，并清除认证缓存，使后续请求立即失败。
- 调用方重新生成密钥对，由管理员登记并启用新公钥，同时调查泄漏期间的调用审计。
- 泄漏密钥永久保留为已撤销状态，不允许重新启用；无法确定泄漏密钥时先停用整个调用系统。

#### 认证结果与失败处理

- `system_id` 不存在、未启用或已过期，`key_id` 不存在、归属不符或不可用，请求体摘要不一致，签名错误，时间戳超出窗口，`nonce` 重复，以及认证 Header 缺失或格式错误，均统一视为认证失败。
- 调用方只收到统一的未认证响应、固定错误信息和 `trace_id`，不得获知系统是否存在、具体哪项校验失败、公钥内容或其他认证细节。
- ToolHive 内部审计记录准确失败原因，但不得记录私钥、完整敏感请求体或其他可用于重放请求的敏感信息，详细留存规则留到 Q23 确认。
- 认证成功只表示已确认请求来自对应调用系统，后续仍必须执行 Q13 的运行 API 范围和流量控制，以及 Q15 的工具调用控制。
