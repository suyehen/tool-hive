## 3. 逐项问题与方案记录

### A01：单一后端应用的接口隔离与部署形态需要明确

**状态：已确认**

#### 当前设计

- ToolHive 是一个后端项目，管理模块与工具应用模块属于同一个应用。
- 管理模块提供管理前端和管理 API；工具应用模块只提供运行 API，不提供前端。
- 两个模块采用不同的请求路径、使用主体、认证方式和控制模型，但必须统一部署、启动、停止和升级。
- 当前代码已有一个 FastAPI 应用入口，现阶段只挂载了管理侧 API，工具应用 API 尚待接入。

#### 问题

需要明确“接口边界隔离”不等于“拆成两个进程或两个后端服务”。如果定义不清，开发时可能为管理模块和工具应用模块分别创建启动入口、监听端口和生命周期，偏离一个后端应用统一运行的目标。

单应用方案同时需要明确：

- Nginx 如何将公网管理入口与一期仅内网开放的工具应用入口转发到同一个后端端口。
- 应用如何针对两组路由执行完全不同的认证与控制链，避免只依赖 Nginx 隔离。
- 后续增加实例时，扩容单位必须是包含两个模块的完整 ToolHive 应用，不能分别扩容或独立启停某个模块。

#### 需要确认

- 是否使用一个 FastAPI 根应用、一个应用启动入口和一个监听端口承载两组 API。
- 是否通过应用内路由模块、独立认证链和 Nginx 入口规则实现边界隔离。
- 后续是否只允许按完整 ToolHive 应用实例进行水平扩容。

#### 候选方案（已确认）

使用一个 FastAPI 根应用承载两组接口：

```text
ToolHive 单一后端应用（一个启动入口、一个监听端口）
├── /api/admin/**       管理 API
└── /api/runtime/**     工具应用 API
```

- 管理 API 使用管理登录会话、MFA、后台角色和管理操作项校验。
- 工具应用 API 使用调用系统身份、来源 IP、公钥签名、Nonce、防重放和工具调用控制。
- Nginx 使用不同入口和路由规则控制公网管理访问与内网工具调用，但两者最终转发到同一个 ToolHive 上游端口。

#### 确认结论

ToolHive 采用一个代码库、一个 FastAPI 根应用、一个应用启动入口、一个监听端口和一个生命周期单元。管理模块与工具应用模块只是同一应用中的两组接口，不拆分为管理子进程和运行子进程，必须同时启动、停止、发布和升级。

#### 最终方案

- 使用统一的 FastAPI 应用入口启动 ToolHive，不增加用于拉起管理和运行子进程的主控进程。
- 同一个应用监听一个后端端口，同时挂载 `/api/admin/**` 与 `/api/runtime/**`。
- 管理模块提供管理前端和管理 API；工具应用模块只提供 API，不提供前端。
- 两组路由分别接入各自的认证和控制链，任何一组凭据都不能用于访问另一组接口；后端不能仅依赖 Nginx 完成认证和授权。
- 后端端口只允许 Nginx 或可信网关访问。Nginx 分别提供公网管理入口和一期仅内网开放的工具应用入口，并将允许的请求转发到同一个后端端口。
- 后续将工具应用 API 改为公网 HTTPS 时，只调整网关、WAF、网络准入和安全策略，不改变后端路由及应用形态。
- 如需负载均衡，增加的是包含管理模块与工具应用模块的完整 ToolHive 实例；每个实例仍使用同一个应用入口并同时承载两组 API，不支持按模块独立启动、停止或扩容。

**已解决**：2026-08-18，已按本方案完成代码修改（`config.py` 统一为 `bind_host`/`bind_port` 单端口配置、配置测试同步更新、前端开发代理端口同步为 8100）。

### A03：跨项目运行 API 需要建立版本兼容边界

**状态：已确认**

#### 当前设计

- 管理 API 使用 `/api/admin/**`。
- 现行目标文档原计划运行 API 使用 `/api/runtime/**`，工具应用模块尚未实现。
- 运行请求签名内容包含实际请求路径。
- 运行 API 将由多个外部项目长期调用。

#### 问题

- 路径、请求 Schema 或响应 Schema 变化时缺少兼容边界。
- 路径参与签名，后续改路径会同时影响调用方签名代码和固定测试向量。
- 公网化、网关迁移或多版本并存时容易被迫做破坏性升级。

#### 需要确认

- 是否从第一版开始使用 URL 版本号。
- 管理侧是否同步版本化，还是只对运行侧强制版本化。
- 签名规范中的 canonical path 是否包含版本路径。

#### 候选方案（已确认）

```text
/api/admin/**
/api/runtime/v1/**
```

- 签名固定使用调用方实际访问的 `/api/runtime/v1/**` 路径。
- 破坏性变更新增 `/v2`，旧版本保留明确过渡期。
- 非破坏性字段扩展继续在当前版本内兼容演进。

#### 确认结论

- API 版本号表示 ToolHive 与调用系统之间的接口契约版本，与 ToolHive 软件版本、工具版本无关。
- 工具运行 API 从第一版开始使用 `/api/runtime/v1/**`。
- 管理 API 一期继续使用 `/api/admin/**`，暂不增加版本号，因为管理前端与后端同步发布。
- 如果未来管理 API 需要提供给其他项目调用，再单独建立版本化的开放接口。

#### 最终方案

- URL 只使用整数主版本，例如 `v1`、`v2`，不使用 `v1.1`。
- 新增接口、新增可选字段等兼容性变更继续使用 `v1`。
- 删除或重命名字段、修改字段类型或语义、增加必填字段、改变签名规范等破坏性变更，必须新增 `v2`。
- 新旧主版本允许并存，为各调用系统提供迁移时间；具体保留期限在发生版本升级时确认。
- 请求签名中的路径包含调用方实际访问的完整版本路径，例如 `/api/runtime/v1/tools/execute`。
- Nginx 必须原样转发运行 API 路径，不删除或改写其中的 `/v1`。
- 后续运行 API 从内网调整为公网 HTTPS 时，保持 `/api/runtime/v1/**` 接口契约不变。

**已解决**：2026-08-18，核实确认：当前代码未实现任何运行 API 路由，不存在违反版本兼容边界的问题；一期下半实现 runtime 时按 `/api/runtime/v1/**` 版本化路径、整数主版本和签名含完整版本路径的规则执行。无当前代码修改项。

### A04：单体应用内部的业务模块边界和调用方向需要明确

**状态：已确认**

#### 当前设计

当前目录主要按技术层划分：

```text
api/
models/
services/
infrastructure/
```

当前管理侧代码规模较小时可以继续使用该结构；但 Catalog 和工具运行侧加入后，需要按业务领域建立清晰边界，避免所有业务能力继续平铺在公共 `services/` 中。

#### 问题

随着 Provider、Catalog、Policy、执行、审计和索引加入，平铺 Service 容易出现：

- 管理路由直接调用执行能力，绕过运行侧认证和 ToolPolicy。
- 运行侧误用管理写服务，修改 Catalog 草稿或角色配置。
- Catalog 发布、Policy 和 Provider 执行相互循环依赖。
- 单元测试难以隔离领域规则与数据库、Redis、HTTP 客户端。

这里的模块边界属于同一个单体应用内部的包与 Service 调用约束，不表示拆分微服务、独立进程或独立部署单元。

#### 需要确认

- 是否采用轻量的模块化单体，而不是继续增加平铺 Service。
- 哪些模块可以共享，哪些只能通过应用层接口访问。
- 管理侧是否禁止直接调用 Provider Executor。
- 是否需要立即重构现有管理侧代码。

#### 候选方案（已确认）

保持一个项目和一个 FastAPI 应用，新增功能按业务边界组织代码：

```text
toolhive/
├── main.py                    单一应用入口
├── api/
│   ├── admin/                 管理侧接口
│   └── runtime/v1/            工具运行侧接口
├── services/                  保留现有管理基础服务
├── catalog/                   Catalog 管理与已发布数据查询
├── runtime/
│   ├── authentication/        调用系统认证
│   ├── tool_control/          工具调用控制
│   └── execution/             Provider 受控执行
├── core/                      公共异常、类型和常量
└── infrastructure/            PostgreSQL、Redis、HTTP；Secret Store（二期可选）
```

- 管理侧只通过 Catalog 管理服务创建草稿、审核、发布和停用配置。
- 运行侧只能读取已发布且已启用的 Catalog，并依次调用认证、工具调用控制和执行能力。
- 共享基础设施和公共类型，不共享未受控的业务入口。

#### 确认结论

- ToolHive 采用轻量的模块化单体结构。
- 仍然是一个 FastAPI 应用、一个启动入口、一个监听端口和一个部署单元，不拆分微服务。
- 新增功能按照业务领域组织代码，类似 Spring Boot 单体项目按业务包划分。
- 不强制使用 `modules/` 目录，也不进行一次性的大规模目录重构。

#### 最终方案

- `api/admin/` 放置管理侧接口，`api/runtime/v1/` 放置工具运行侧接口。
- 保留现有账号、登录、角色和调用系统相关代码结构。
- 后续新增 `catalog/`，负责工具配置、草稿、审核、发布、停用以及已发布配置查询。
- 后续新增 `runtime/`，负责调用系统认证、工具调用控制和 Provider 受控执行。
- 管理调用链为：管理认证与操作项校验 → Catalog 管理服务 → 配置、审核或发布。
- 运行调用链为：调用系统认证 → 工具调用控制 → 查询已发布 Catalog → Provider 执行。
- 运行侧只能读取已发布且已启用的配置，不能调用 Catalog 管理写服务。
- 管理侧不能直接调用正式工具执行链，避免绕过运行侧认证和工具调用控制。
- 管理侧如需测试 Provider，应建立独立测试功能，并配置管理操作项、目标限制和审计。
- Provider 执行只能使用已审核发布的固定配置，不能接收任意 URL、Header 或明文凭据。
- PostgreSQL、Redis、日志、配置和异常体系可以共享，但管理与运行的业务入口不能相互调用。
- 现有代码不立即整体迁移；从 Catalog 和运行侧开发开始执行该边界，旧代码按实际需要逐步整理。

**已解决**：2026-08-18，已按本方案添加模块结构骨架：新增 `api/runtime/v1/`、`catalog/`、`runtime/{authentication,tool_control,execution}/` 包及职责说明；现有 `services/` 等结构保留不迁移；业务实现待 Catalog 与运行侧开发阶段按本边界执行。

### A05：一期核心业务模型需要分阶段确认后再实现

**状态：已确认**

#### 当前设计

现行总体架构文档中已经出现以下领域概念：

- Provider、Tool、ToolVersion、ToolBinding。
- Capability、能力包、PolicyBinding。
- draft、active、deprecated、disabled、archived 等版本状态。
- Discover/Execute 两阶段策略。
- 确认令牌、Audience Scope、索引 Outbox。

现行文档同时明确：Catalog 和工具调用控制的详细字段、状态机及关联规则仍需在对应功能开发前单独确认。当前代码尚未实现上述核心模型。

#### 问题

- 架构概念图可能被误当成最终数据库模型，导致开发人员自行补全字段、关联关系和状态。
- 环境、租户、调用系统和业务身份等关键维度尚未确认，过早落表可能造成大规模迁移。

- Provider、工具和版本的命名空间、唯一性、环境边界及状态流转尚未形成可编码规则。

#### 需要确认

- 架构文档中的领域名称是否可以直接作为最终数据模型实现。
- 核心模型需要确认到什么程度后才能建表和编码。
- 哪些业务设计需要用户确认，哪些普通技术实现可由开发人员按规范处理。
- 各核心模型按什么顺序确认和实现。

#### 候选方案（已确认）

- 总体架构中的名称只表示领域概念，不等于最终表结构或接口契约。

#### 确认结论

- 总体架构中的 Provider、工具、工具版本、能力包、策略和确认令牌等名称，目前只表示领域概念，不代表最终数据模型。

- 当前代码尚未实现这些核心模型，因此不需要回退或删除现有实现。

#### 最终方案

- 开发对应功能前，先确认其核心实体关系、业务状态和流转规则、对外 API 契约、权限及安全边界。

  2. 草稿、审核、发布、停用等状态流转。
  3. 调用系统与可用工具范围的关系。
  4. ToolContext 的业务身份字段和可信规则。
  5. Discover 与 Execute 的接口职责。
  6. HTTP Provider 的执行与安全规则。
  7. 检索方式以及是否使用 Chroma。
- 普通类名、函数拆分和内部代码组织等实现细节不需要逐项确认，可按项目规范直接处理。
- 每项业务设计经讨论确认并获准更新文档后，才能进入对应编码阶段。
- 最终设计归并到 `docs/功能架构梳理/` 的对应现行文档，不额外增加大量设计文件。

### A06：数据库事务边界与跨基础设施副作用处理需要明确

**状态：已确认**

#### 当前设计

- 当前由请求级数据库依赖在请求正常结束时提交、出现异常时回滚。
- 业务 Service 已经可能同时修改 PostgreSQL 和 Redis，后续还会涉及 Chroma。
- 账号禁用、公钥撤销、调用系统停用要求立即生效。
- Catalog 发布还会同时涉及业务数据、审计记录、Outbox 和派生索引。

#### 问题

- PostgreSQL 提交失败但 Redis 会话已经删除时，状态发生分裂。
- PostgreSQL 已停用调用系统但缓存未失效时，运行请求可能继续通过。
- 登录失败等业务流程最终会抛出认证异常，当前请求级事务可能把必须保留的数据库安全计数一并回滚，而 Redis 计数已经生效。
- 事务所有权位于框架依赖中，Application Service 无法明确表达一个完整业务操作的原子边界。
- PostgreSQL 提交后，如果 Redis 或 Chroma 更新失败且没有可靠任务记录，更新可能永久丢失。

#### 需要确认

- 是否提供类似 Spring `@Transactional` 的统一异步事务机制。
- 事务由 Controller、Application Service 还是 Repository 管理。
- 哪些跨存储操作必须强一致，哪些允许最终一致。
- Redis 或 Chroma 失败时各类操作应该回滚、重试还是 fail-closed。
- Outbox 保存在哪里，以及多个投递目标如何分别记录成功和失败。

#### 候选方案（已确认）

- Application Service 通过项目统一封装的异步事务机制声明完整业务操作的 PostgreSQL 事务边界。
- 业务数据、成功审计记录、`outbox_event` 和 `outbox_delivery` 在同一个 PostgreSQL 事务中提交。
- PostgreSQL 提交成功后，由后台 Worker 将投递任务分别处理到 Redis 和 Chroma。
- Redis、Chroma 和外部 Provider 调用不加入 PostgreSQL 长事务。
- 安全敏感的同步状态写入失败时采用拒绝请求或读取 PostgreSQL 最新状态等方式保证不能被绕过。

#### 确认结论

- 使用项目统一封装的异步事务机制，效果类似 Spring 的 `@Transactional`。
- 事务边界由完成一项完整业务操作的 Application Service 声明。
- 方法正常结束自动提交，抛出异常自动回滚；内部调用默认加入当前事务。
- Controller 不负责事务，Repository 和普通 Service 不得自行 `commit`。
- PostgreSQL 中的业务数据、成功审计记录和 Outbox 记录必须在同一事务中提交。
- Outbox 数据保存于 PostgreSQL，不保存于 Redis、Chroma、文件或内存。
- Redis、Chroma 和外部 Provider 调用不加入 PostgreSQL 长事务。

#### 最终方案

```text
Application Service（PostgreSQL 事务范围）
├── 修改业务数据
├── 写成功审计记录
├── 写 outbox_event
└── 写 outbox_delivery
        ↓ PostgreSQL 提交成功
后台 Worker 独立投递
├── Redis
└── Chroma
```

- `outbox_event` 保存事件 ID、事件类型、业务对象 ID、业务对象版本和必要的非敏感事件信息。
- `outbox_delivery` 按投递目标分别保存 Redis、Chroma 的处理状态，不能使用一个状态代表所有目标。
- 投递任务支持 `PENDING`、`PROCESSING`、`RETRY`、`SUCCEEDED`、`DEAD` 等逻辑状态。
- Redis 和 Chroma 独立成功、独立重试；一个目标成功不影响另一个目标保留失败状态并继续处理。
- 所有投递必须幂等，并支持 Worker 宕机恢复、失败重试、告警和人工重放。
- PostgreSQL 提交成功后，即使 Redis 或 Chroma 更新失败，也不回滚业务数据；保留对应投递任务继续处理。
- Chroma 是 PostgreSQL 的派生索引。短暂落后时允许暂时搜索不到新工具；运行侧对候选工具仍必须回 PostgreSQL 校验当前发布状态、启用状态和调用范围。
- 普通 Redis 缓存失效可以通过 Outbox 重试；缓存不可用或未命中时回源 PostgreSQL。
- Nonce、防重放等安全 Redis 操作必须在请求中同步完成；Redis 不可用时直接拒绝运行请求，不能通过 Outbox 延后补写。
- 登录失败次数、限流计数等即使请求最终返回失败也必须保留，使用 Redis 或类似 `REQUIRES_NEW` 的独立事务处理。
- 账号禁用、调用系统停用、公钥撤销等安全状态，以 PostgreSQL 最新状态或后续确认的安全版本为校验依据，不能仅依赖异步缓存清理。
- 外部 Provider 调用不占用长时间数据库事务；调用开始和调用结果使用独立短事务保存。
- A07 再确认 Worker 运行形式、重试次数、退避间隔、任务锁超时、失败告警、数据保留和清理策略。

**已解决**：2026-08-18，已完成：引入 `@transactional()` 统一事务封装（含 `requires_new` 独立事务），`get_db()` 改为只注入 session；登录失败计数改用独立事务持久化；`tool-hive/sql/init.sql` 落地全部现有表及 `outbox_event`/`outbox_delivery` 两张表（状态、尝试次数、锁定、重试时间、错误信息字段已建）。Outbox 后台 Worker、投递、失败重试/死信、查询与人工重放按 A07 实施。

### A07：PostgreSQL、Redis、Chroma 的一致性和缓存失效协议缺失

**状态：已确认**

#### 当前设计

- PostgreSQL 是唯一事实来源。
- Redis 保存会话、Nonce、限流等带 TTL 的临时安全状态，并可在后续保存普通派生缓存。
- 一期确定使用嵌入式 Chroma，保存 PostgreSQL 派生的工具检索索引。
- A06 已确认业务数据、审计、`outbox_event` 和 `outbox_delivery` 在同一个 PostgreSQL 事务中提交。
- 生产服务器的 ToolHive 工作根目录固定为 `/vdb/tool-hive`。

#### 问题

- Outbox 后台任务的运行位置、参数加载、任务领取和停止方式尚未定义。
- 重复消费、失败重试、乱序事件和毒消息如何处理。
- 成功、失败、重试和积压任务缺少结构化监控日志及查询入口。
- Chroma 落后或不可用时 Resolve 如何降级。
- 角色、调用系统、公钥、IP 规则和工具调用范围等安全事实能否缓存尚未明确。
- 全局业务 ID 的生成方式和跨前后端类型尚未统一。
- 嵌入式 Chroma 与多实例部署、进程并发、本地磁盘和后续服务化之间存在边界。

#### 需要确认

- Outbox 后台任务是否作为独立进程运行，以及如何支持多实例竞争和宕机恢复。
- 所有执行参数是否允许由外挂配置文件覆盖代码默认值。
- 如何查询每次 Redis、Chroma 投递的成功、失败和重试状态。
- Catalog 和投递事件如何通过 revision/version 防止乱序覆盖。
- Redis 一期允许保存哪些数据，哪些安全事实禁止缓存。
- 全局业务 ID 是否采用雪花算法，以及数据库、API 和前端使用什么类型。
- 一期 Chroma 的部署形态、持久化目录、并发限制和二期演进方式。

#### 方案（已确认）

```text
ToolHive 单一应用进程
├── 管理 API
├── 工具运行 API
├── Outbox 后台消费任务
└── 嵌入式 Chroma
```

- Outbox 消费任务是同一 ToolHive 进程内的后台任务，类似 Spring `@Scheduled`，不增加独立服务或子进程。
- PostgreSQL 负责持久化任务、投递状态和竞争锁；Redis 与 Chroma 只作为投递目标。
- 一期 Chroma 使用 Embedded/Persistent 模式，只支持一个 ToolHive 应用实例和一个应用 Worker。
- 所有运行参数支持外挂 YAML 配置覆盖代码默认值，生产部署统一使用 `/vdb/tool-hive` 下的持久化目录。
- 一期生产运行基线固定为 CPython 3.11.6，后端代码、依赖选择、构建产物和部署验收必须兼容该版本。
- 新增业务主键和 Outbox ID 使用标准雪花算法生成，并在数据库、Python、API 和前端中统一表示为字符串。

#### 确认结论

- Outbox 后台消费任务运行在同一个 ToolHive 应用进程内，跟随应用统一启动和停止，不拆分独立 Worker 服务。
- 任务使用 PostgreSQL `FOR UPDATE SKIP LOCKED` 领取；领取任务和更新状态使用短事务，Redis 与 Chroma 调用在数据库事务之外执行。
- 轮询、批量、并发、锁超时、重试、日志和数据保留等 Outbox 参数全部支持配置文件覆盖代码默认值。
- 每个新增配置字段必须在 YAML 示例中提供中文注释，并在 Pydantic `Field` 中提供功能说明和范围校验。
- 支持通过 `--config` 或 `TOOLHIVE_CONFIG_FILE` 指定外挂 YAML。明确指定的文件不存在、不可读或内容非法时，服务启动失败。
- 配置值优先级为环境变量中的具体配置值、外挂 YAML、代码默认值；一期配置变更在重启后生效。
- 每次投递必须生成可查询的结构化监控日志，并在 PostgreSQL 中保留成功、重试、失败和积压状态。
- 全局业务 ID 使用标准 64 位雪花算法生成，生成器直接返回十进制字符串；业务主键、外键和 API ID 全部使用字符串表示。
- 一期确定使用嵌入式 Chroma，持久化目录为 `/vdb/tool-hive/chroma`，不单独部署 Chroma 服务。
- 嵌入式 Chroma 的多实例、本地磁盘和独立扩容风险记录到二期目标，二期可改造为独立共享服务。

#### 最终方案

##### Outbox 后台任务

- 后台任务默认每 `1000ms` 轮询一次，每批领取最多 `50` 条，单实例最大并发 `5` 条，任务锁默认 `60s`；所有值均可由配置文件覆盖。
- 领取任务时使用 `FOR UPDATE SKIP LOCKED`，写入 `locked_by` 和 `locked_until` 后立即提交，不在调用 Redis 或 Chroma 时持有数据库行锁。
- 临时连接失败、超时和服务不可用进入 `RETRY`，采用带随机抖动的退避策略；默认等待时间从 `5s` 开始，最大为 `1800s`。
- 无法识别的事件类型、非法事件结构等确定性错误在有限重试后进入 `DEAD`，不得丢弃记录。
- Redis 与 Chroma 使用独立 `outbox_delivery` 状态；一个目标成功后不因另一个目标失败而重复处理。
- 任务处理必须幂等。Redis 普通缓存失效使用可重复的删除操作；Chroma 使用稳定业务 ID 执行 `upsert/delete`。
- 每个业务聚合维护递增 revision。Worker 处理事件时读取 PostgreSQL 当前状态，旧事件不得覆盖较新的业务状态。
- Worker 在目标更新成功但尚未标记 `SUCCEEDED` 时宕机，锁超时后允许重新执行，并依靠幂等规则安全收敛。

##### 配置加载与生产目录

```text
配置文件路径：--config → TOOLHIVE_CONFIG_FILE → 默认配置路径
配置字段取值：环境变量具体值 → 外挂 YAML → 代码默认值
```

- 当前模块导入时立即创建全局 Settings 的方式，在实现外挂配置时改为应用启动阶段统一加载。
- 生产环境使用绝对配置路径 `/vdb/tool-hive/config/production.yaml`，服务启动时记录实际配置路径，但不得输出密钥值。
- 所有新增字段同时写入带中文注释的 `toolhive.example.yaml`；配置文件值必须覆盖代码默认值。
- 生产工作目录固定如下：

```text
/vdb/tool-hive/
├── service/                    后端程序
├── frontend/                   管理前端静态文件
├── venv/                       Python 虚拟环境
├── config/                     外挂配置文件和示例

```

- 升级只替换 `service/` 和必要的前端文件，不得覆盖 `config/`、`chroma/`、`logs/` 和 `backup/`。
- 生产配置文件建议权限为 `0600`；Chroma 和日志目录只允许 ToolHive 服务账号读写。
- Chroma 目录不存在时可在启动阶段创建；存在但不可写时必须启动失败。

##### Python 运行基线

- 一期生产运行基线固定为 CPython `3.11.6`，不以当前检查机器或其他开发机器上的 Python 版本作为生产兼容性依据。
- 后端项目使用 `requires-python = ">=3.11.6,<3.12"`，代码检查目标使用 `py311`。
- 后端代码不得使用仅在 Python 3.12 及以上版本提供的语法或标准库 API。
- FastAPI、Chroma 及所有直接和间接依赖必须选择兼容 Python 3.11.6 的版本，并在正式交付前锁定依赖版本。
- 最终交付物必须在 CPython 3.11.6 环境完成依赖安装、数据库迁移、服务启动和自动化测试验收。
- 嵌入式 Chroma 所需的 SQLite 等运行依赖由部署及启动检查负责；不满足最低要求时服务必须启动失败并输出明确原因。

##### 配置字段要求

```yaml
outbox:
  # 是否启用 Outbox 后台投递任务。
  enabled: true

  # 查询 PostgreSQL 待处理任务的间隔，单位毫秒。
  poll_interval_ms: 1000

  # 单次领取的最大任务数量。
  batch_size: 50

  # Redis 等普通投递目标的最大并发处理数量。
  max_concurrency: 5

  # 一期固定使用 embedded；二期可以扩展为 service。
  mode: embedded

  # 嵌入式模式的写入并发数，一期只能为 1。
  write_concurrency: 1

snowflake:
  # 雪花算法使用的固定起始时间戳，投产后不得随意修改。
  epoch_ms: 1767225600000

  # 数据中心编号，取值范围为 0～31。
  datacenter_id: 1

  # 当前运行节点编号，取值范围为 0～31；多实例不得重复。
  worker_id: 0

  # 允许等待恢复的系统时钟回退时间，单位毫秒。
  clock_rollback_tolerance_ms: 5
```

##### 监控、查询和人工恢复

- 每次投递记录 `event_id`、`delivery_id`、目标、事件类型、业务对象 ID、业务版本、状态、尝试次数、耗时、下次重试时间、实例 ID 和脱敏错误信息。
- `SUCCEEDED` 使用 `INFO`，等待重试使用 `WARN`，进入 `DEAD` 和 Worker 自身异常使用 `ERROR`。
- 日志不得包含完整事件 Payload、Provider 凭据、公钥、私钥或其他敏感字段。
- 管理侧提供按状态、目标、事件类型、业务对象 ID、事件 ID 和时间范围查询投递任务的接口。
- 查询和人工重新投递分别使用 `system_task:view`、`system_task:retry` 管理操作项；人工重试必须写管理审计。
- 完整监控看板可以后续建设，但一期必须能够查询成功、失败、重试和积压任务，并支持重新投递及全量重建 Chroma。

##### ID 规则

- 标准雪花算法内部使用 64 位结构计算，最终直接返回十进制字符串。
- 新增业务主键、Outbox Event ID、Outbox Delivery ID、Catalog、Provider、工具、工具版本和审计记录 ID 使用雪花字符串。
- PostgreSQL 主键和外键统一使用 `VARCHAR(32)`，Python 与 Pydantic 使用 `str`，API 和前端始终按字符串处理。
- 雪花算法的 `datacenter_id + worker_id` 在所有运行实例间必须唯一；时钟严重回退时拒绝生成 ID，不能冒险产生重复值。
- 业务排序使用明确的时间或排序字段，不依赖字符串 ID 排序。
- Session ID、Nonce、CSRF Token、恢复码、API Key 和确认令牌继续使用密码学安全随机数；Trace ID 使用标准 128 位链路追踪格式。上述值的表示类型仍统一为字符串。
- 现有 UUID 数据不在 A07 中迁移；后续新增数据采用统一生成器，是否调整现有实体的生成策略另行确认。

##### Redis 与 Chroma

- 一期 Redis 保存会话、互斥登录索引、登录及限流计数、验证码和运行侧 Nonce 等临时状态。
- 一期不在 Redis 缓存账号状态、后台角色、管理操作项、调用系统状态、公钥、IP 规则、工具调用范围和授权结果等安全事实。
- Nonce、防重放等请求内安全操作不经过 Outbox；Redis 不可用时直接拒绝运行请求。
- 一期 Chroma 为同一 ToolHive 进程中的 Embedded/Persistent Client，生产持久化目录固定为 `/vdb/tool-hive/chroma`。
- 一期只支持一个 ToolHive 应用实例和一个应用 Worker，Nginx 不向多个 ToolHive 实例做负载均衡。
- 所有 Chroma 写入只通过 Outbox 后台任务完成；Discover 获得候选 ID 后必须回 PostgreSQL 校验当前状态和工具调用范围。
- 提供以 PostgreSQL 为来源的 Chroma 全量重建命令，Chroma 数据不能反向恢复业务事实。
- Chroma 访问从一期开始封装为 `VectorIndex` 接口，业务代码不直接依赖嵌入式客户端。
- 只有所有投递目标成功后，Outbox 事件才允许在保留期后清理；未完成的 `PENDING`、`RETRY` 和 `DEAD` 记录不得自动删除，具体保留策略在 A13 统一复核。

**已解决**：2026-08-18，已完成：Python 基线改为 CPython 3.11.6（`requires-python >=3.11.6,<3.12`、ruff `py311`）；配置改为启动阶段统一加载并支持外挂 YAML（`--config`/`TOOLHIVE_CONFIG_FILE`，优先级 环境变量 > YAML > 默认值，含 `toolhive.example.yaml` 与分区配置 outbox/chroma/snowflake）；新增雪花 ID 生成器（时钟回退保护）；新增 Outbox 后台 Worker（`FOR UPDATE SKIP LOCKED` 短事务领取、锁超时回收、退避重试、DEAD、按目标独立投递、幂等）并随应用启停；新增 `system_task:view`/`system_task:retry` 操作码及投递任务查询/人工重投接口（支持状态、目标、事件类型、对象 ID、事件 ID、`create_time_start`/`create_time_end` 过滤，记录耗时与 Worker 实例）；新增 `VectorIndex` 接口与嵌入式 Chroma 实现、`rebuild-chroma` 命令骨架。待后续：操作项接口校验统一接入；Chroma 检索数据源与召回逻辑在一期下半接入。

### A08：嵌入式本地 Chroma 与多实例负载均衡冲突

**状态：已确认**

#### 当前设计

- 一期确定使用嵌入式 Chroma，并通过 Persistent Client 保存本地索引。
- Chroma 与管理 API、运行 API 和 Outbox 后台任务位于同一个 ToolHive 应用进程。
- Nginx 作为生产统一入口，负责 HTTPS、路径路由、网络隔离和反向代理。
- 二期可能部署多个完整 ToolHive 应用实例。

#### 问题

- 如果一期部署多个 ToolHive 实例，每个实例会拥有独立的本地 Chroma 索引，索引版本和检索结果可能不一致。
- Outbox 任务无法可靠地将同一变更同步到多个实例的本地索引。
- 本地索引与具体服务器绑定，服务器迁移、磁盘损坏或目录丢失后需要恢复或重建。
- Windows 开发环境和 Linux 生产环境需要使用不同的持久化路径。
- Chroma 或 Embedding 临时不可用时，需要明确 Discover、Resolve 和 Execute 的不同处理方式。

#### 需要确认

- 一期 Chroma 的部署形态和应用实例数量。
- Nginx 一期是否向多个 ToolHive 实例进行负载均衡。
- PostgreSQL 与 Chroma 的事实来源边界。
- Chroma 或 Embedding 不可用时的检索降级规则。
- 二期开放 ToolHive 多实例部署的前置条件。

#### 方案（已确认）

- 一期使用嵌入式 Chroma，只运行一个完整 ToolHive 应用实例和一个 Uvicorn 应用 Worker。
- Nginx 一期不向多个 ToolHive 实例负载均衡，只负责 HTTPS、路由、网络隔离和反向代理。
- PostgreSQL 是工具定义、版本、发布状态和授权数据的唯一事实来源，Chroma 只是可重新生成的检索索引。
- Execute 和按工具 ID 或工具编码进行的精确 Resolve 不依赖 Chroma。
- 自然语言 Discover 优先使用 Chroma；Chroma 或 Embedding 临时不可用时，降级为 PostgreSQL 有界关键词检索。
- 二期先完成 Chroma 独立共享服务改造，再开放多个完整 ToolHive 实例。

#### 确认结论

- 一期确定使用嵌入式 Chroma，不再讨论暂缓 Chroma 或一期直接部署共享 Chroma 服务。
- 一期生产只允许一个完整 ToolHive 应用实例和一个 Uvicorn Worker。
- 一期保留 Nginx，但不配置多个 ToolHive upstream，不宣称支持应用多实例负载均衡。
- Chroma 生产持久化目录固定为 `/vdb/tool-hive/chroma`；Windows 开发路径通过开发配置覆盖。
- Chroma 及其依赖必须兼容一期生产运行基线 CPython 3.11.6。
- Chroma 数据不得作为业务事实或授权事实使用，目录损坏或丢失后必须能够从 PostgreSQL 全量重建。
- Chroma 运行期间发生临时检索错误时执行受控降级；依赖不兼容、目录不可写等部署错误必须启动失败。
- 二期完成共享 Chroma 服务化、索引迁移和结果校验后，才允许 Nginx 向多个完整 ToolHive 实例负载均衡。

#### 最终方案

##### 一期部署边界

- ToolHive 使用一个进程、一个监听端口和一个 Uvicorn Worker，同时承载管理 API、运行 API、Outbox 后台任务和嵌入式 Chroma。
- 所有 Chroma 写入只允许通过 Outbox 后台任务执行，Chroma 写并发固定为 `1`。
- Nginx 只配置一个 ToolHive 后端实例，不通过复制本地 Chroma 目录实现多实例。
- Chroma 生产目录为 `/vdb/tool-hive/chroma`；开发环境通过外挂配置使用适合当前操作系统的路径。
- Chroma 目录可以在启动阶段创建；目录不可读写、依赖不兼容或初始化失败时，服务启动失败并输出明确错误。

##### 数据与恢复边界

- PostgreSQL 保存工具、工具版本、发布状态、工具调用范围和其他业务事实。
- Chroma 只保存由已发布 Catalog 派生的向量及检索字段。
- Discover 从 Chroma 获得候选工具 ID 后，必须回 PostgreSQL 校验当前版本、发布状态和工具调用范围。
- 提供以 PostgreSQL 为来源的 Chroma 全量重建能力；Chroma 不得反向恢复 PostgreSQL 数据。
- Chroma 的备份可以缩短恢复时间，但不能替代全量重建能力。

##### 检索降级边界

- Execute 已明确指定工具，Chroma 故障不得阻断通过 PostgreSQL 完成的工具状态、授权和执行校验。
- 按工具 ID 或工具编码进行的精确 Resolve 直接查询 PostgreSQL，不依赖向量索引。
- 自然语言 Discover 正常情况下使用 Chroma 召回候选。
- Chroma 或 Embedding 临时不可用时，只允许在 PostgreSQL 中按工具编码、名称、关键词和标签执行有数量上限的关键词检索。
- 所有降级候选必须继续校验发布状态、调用系统范围和工具调用控制，禁止返回未授权工具或将全部工具作为降级结果。
- 无法获得可靠候选时返回明确的检索暂不可用错误，不得静默扩大结果范围。
- 降级原因、检索模式、候选数量、最终结果和耗时必须写入结构化日志及 Trace，但不得记录敏感业务内容。

##### 二期演进边界

- 二期将 `VectorIndex` 的嵌入式实现替换为独立共享 Chroma 服务实现。
- 服务化改造必须包含全量导入、增量追平、索引版本校验、召回结果验证、流量切换和失败回滚。
- 只有共享索引通过验收后，才允许部署多个完整 ToolHive 实例并由 Nginx 进行负载均衡。

**已解决**：2026-08-18，核实确认：一期单实例、嵌入式 Chroma、`VectorIndex` 接口与全量重建命令已落实；Chroma 写并发固定为 1；Execute 与精确 Resolve 不依赖 Chroma、自然语言 Discover 降级规则及 Nginx 单实例配置属一期下半与部署范围，届时执行。

### A09：管理侧与运行侧共享全部密钥、出站网络和进程权限

**状态：已确认**

#### 当前设计

- ToolHive 一期是一个应用、一个进程、一个 Linux 服务账号和一个生命周期单元。
- 管理 API、运行 API、Outbox 后台任务、检索和 Provider 执行均在同一个进程中运行。
- 当前配置结构倾向于通过一个全局 Settings 对象同时保存管理安全配置、运行安全配置、模型 Key 和基础设施连接信息。
- 一期不需要 ToolHive 持有目标业务系统的密码、API Key、OAuth Secret 或客户端私钥。

#### 问题

- 如果所有模块都能获得完整 Settings，普通代码错误或接口越权可能扩大密钥暴露范围。
- 如果未来引入需要凭据的 Provider，管理 API 也不得在正常查询过程中读取凭据原文或获得通用 Provider HTTP 调用能力。
- 同一进程只能使用一个 Linux 身份和一套主机出站权限，无法通过防火墙区分管理模块与运行模块。
- Python 模块、依赖注入和配置分区只能形成代码级边界，不能阻止任意代码执行漏洞读取整个进程内存。
- 如果不明确一期安全上限，容易将单进程内的逻辑隔离误认为操作系统级强隔离。

#### 已确认范围与后续评估

- 保持 A01 确认的单进程方案，不拆分 admin-api、runtime-api 或 executor-worker。
- 按用途拆分配置对象和模块依赖，不向业务模块传递完整全局 Settings。
- 二期评估是否需要目标系统凭据代持，以及是否建设 Secret Store。
- 单进程下通过 ProviderGateway 和主机出站策略限制 Provider 出站调用入口。
- 一期明确接受无法抵御单进程任意代码执行后跨模块读取进程资源的剩余风险。

#### 方案（已确认）

- 一期保持一个 ToolHive 进程，不拆分独立管理进程、运行进程或执行器进程。
- 按管理安全、运行安全、检索模型、Provider 执行和基础设施连接拆分配置对象。
- 管理模块、运行模块和执行模块只注入自身需要的配置及接口，不获得完整 Settings。
- 调用系统私钥始终由调用系统保管，ToolHive 只保存公钥。
- 一期不保存目标系统凭据，不引入 `credential_ref`、`CredentialWriteService` 或 `ProviderSecretResolver`。
- 如果目标系统需要凭据，该工具不纳入一期交付，转入二期重新确认。
- 所有业务 HTTP 出站统一通过 `ProviderGateway`，禁止管理 Controller 或其他业务模块自行发起任意地址请求。
- 一期接受单进程无法提供操作系统级密钥隔离的剩余风险；二期如需强隔离，再将执行器拆为独立进程或服务。

#### 确认结论

- A09 不改变 A01：ToolHive 一期仍是一个进程、一个服务账号和一个统一启停单元。
- A09 当前候选方案中的 admin-api、runtime-api 和 executor-worker 多进程拆分方案作废。
- 一期采用单进程内的配置分区、模块依赖隔离、凭据读写接口分离和统一出站网关。
- TOTP 加密密钥、CSRF 密钥、模型 Key 和基础设施连接信息必须使用不同配置字段和不同用途，不得相互复用。
- 开发和生产使用各自的外挂配置文件及密钥；敏感值不得输出到日志、Trace、审计正文或管理 API 响应。
- 一期管理 API 不提供目标系统凭据的录入、查询、轮换或撤销能力。
- 单个 Linux 进程的主机防火墙只能统一限制整个 ToolHive 的出站范围，无法按 Python 模块区分；具体白名单、DNS、重定向和 SSRF 规则在 A11 确认。
- 如果管理侧出现任意代码执行漏洞，一期不能保证其无法读取进程内其他密钥或使用进程出站权限；该剩余风险明确记录，不使用“模块隔离”掩盖。
- 二期只有在安全等级要求提升时才考虑拆分独立执行器，不作为一期前置条件。

#### 最终方案

##### 单进程安全边界

- ToolHive 一期使用一个应用进程和一个 Linux 服务账号，管理、运行、检索及执行模块共享操作系统身份。
- 路由隔离、Python 模块边界和依赖注入属于应用级隔离，不属于进程、容器或主机级隔离。
- 一期不保存目标系统凭据；普通管理查询、权限错误和模块误用不得扩大模型 Key 或其他安全配置的暴露范围。
- 任意代码执行导致的进程级失陷被视为一期剩余风险，需要通过依赖升级、安全编码、输入校验、最小出站和运行监控降低发生概率。

##### 配置和依赖注入边界

配置按用途拆分，类似 Spring Boot 使用多组独立的 `@ConfigurationProperties`：

| 配置分区 | 保存内容 | 允许使用的模块 |
|----------|----------|----------------|
| `AdminSecuritySettings` | TOTP 加密密钥、CSRF 密钥、管理会话安全参数 | 管理身份与会话模块 |
| `RuntimeSecuritySettings` | 请求签名、时间窗口、Nonce 和运行认证参数 | 运行认证模块 |
| `RetrievalSettings` | Embedding 模型、模型 Key 和检索参数 | 检索及索引模块 |
| `ProviderExecutionSettings` | Provider 固定目标、超时、重试和受控出站参数 | Provider 执行模块 |
| `InfrastructureSettings` | PostgreSQL、Redis 和 Chroma 连接配置 | 对应基础设施适配器 |

- 应用启动阶段统一读取外挂配置，再构造各配置分区。
- 不允许 Controller、Application Service 或领域服务直接依赖完整全局 Settings。
- 管理模块不能导入通用 Provider HTTP 客户端。
- 通过模块依赖检查或架构测试校验禁止的导入方向，作用类似 Java 项目中的 ArchUnit 规则。
- 配置分区用于降低正常代码误用风险，不宣称能够阻止进程内恶意代码绕过。

##### 一期密钥边界

- 调用系统私钥不生成、不上传、不保存于 ToolHive；ToolHive 只维护调用系统公钥及其版本和状态。
- 一期不保存目标业务系统密码、API Key、OAuth Secret 或客户端私钥。
- 模型 Key 按开发/生产配置文件加载，并通过文件权限、配置分区和日志脱敏保护。
- 如果二期引入目标系统凭据，再单独确认 Secret Store、凭据轮换、审计和执行权限模型。

##### 出站调用边界

- ToolHive 所有业务 HTTP 出站必须经过统一 `ProviderGateway`。
- 管理 Controller、运行 Controller、领域服务和 LLM 均不能直接决定目标 URL、请求方法、认证 Header 或凭据。
- 主机防火墙按整个 ToolHive 进程限制允许的目标网络和端口。
- `ProviderGateway` 负责应用级目标校验、固定映射、超时、重试和审计接入，不负责读取一期不存在的目标系统凭据。
- 目标白名单、DNS 重绑定、重定向、TLS 和 SSRF 防护规则在 A11 继续确认。

##### 二期强隔离条件

- 一期不拆分独立执行器。
- 如果二期引入目标系统凭据，且要求管理侧失陷后仍不能访问这些凭据或业务系统网络，则必须将 Provider 执行器拆为独立进程或独立服务。
- 二期独立执行器需要使用不同 Linux 用户、容器身份、Secret Store 身份和出站防火墙规则。
- 是否实施该改造由二期安全等级、工具风险、凭据需求和实际运维能力决定。

**已解决**：2026-08-18，已完成配置分区与最小权限注入：Settings 提供 `AppSettings`/`AdminSecuritySettings`/`RuntimeSecuritySettings`/`RetrievalSettings`/`InfrastructureSettings`/`OutboxSettings`/`SnowflakeSettings` 分区；数据库与 Redis 改为启动时 `init_infrastructure`/`init_redis` 显式初始化；Service 构造注入所需分区（`AccountService`/`AuthService` 注入管理安全配置、`OutboxWorker` 注入 outbox 配置）；安全工具模块通过 `configure_security` 绑定专用分区；Router 通过 `Depends(get_admin_security)` 获取分区；业务模块（Controller/Service）不再依赖完整全局 Settings，仅 main.py/cli.py/deps.py 三个入口保留访问。ProviderGateway 与运行侧配置在对应阶段接入。

### A10：网络隔离和真实来源 IP 判断过度依赖 Nginx 配置

**状态：已确认**

> **适用前提**：以下方案仅适用于一期 Nginx 与 ToolHive 部署在同一台 Linux 服务器上。ToolHive 只监听本机回环地址，Nginx 是唯一允许访问 ToolHive 后端的代理。若后续将 Nginx、WAF 或网关部署到其他服务器，必须重新配置专用私网、可信代理网段和防火墙规则，不能直接沿用一期的回环地址前提。

#### 当前设计

- ToolHive 是一个后端进程、一个监听端口，管理 API 和运行 API 通过 Nginx 路由区分。
- Nginx 负责公网管理入口、内网运行入口、路径路由、来源网络限制和代理 Header 清理。
- ToolHive 需要根据经过清洗的真实来源 IP 校验调用系统的 IP 规则。
- 一期生产环境计划将 Nginx 与 ToolHive 放在同一台 Linux 服务器上。

#### 问题

- 如果应用端口监听 `0.0.0.0` 或被其他主机直接访问，调用方可以自行伪造代理 Header。
- 如果无条件信任 `X-Forwarded-For`、`X-Real-IP` 或 `Forwarded`，外部调用方可以伪造来源 IP 并绕过白名单。
- 同一后端端口同时承载管理和运行 API 时，应用需要知道请求是从哪个 Nginx 入口进入的。
- 如果 Nginx 前面未来增加 WAF 或负载均衡器，代理链和可信代理范围必须显式配置。
- 调用系统配置中的 `*` 不能被误解为绕过一期运行入口的内网限制。

#### 已确认前提

- 一期 Nginx 与 ToolHive 位于同一台 Linux 服务器。
- ToolHive 只绑定 `127.0.0.1` 和必要的 `::1` 回环地址，不绑定 `0.0.0.0` 或公网网卡。
- Nginx 是一期唯一可以访问 ToolHive 应用端口的进程。
- 生产服务器防火墙不开放 ToolHive 应用端口，只开放 Nginx 所需的 HTTPS 端口。
- 管理入口和运行入口可以使用不同的 Nginx `server`/`location` 规则，但最终都转发到同一个 ToolHive 应用端口。
- 一期不存在位于 Nginx 前面的其他代理；未来增加 WAF、负载均衡器或 API Gateway 时，必须重新登记可信代理网段。
- Win11 开发环境可以显式开启仅回环地址直连模式，但该模式不得用于生产配置。

#### 方案（已确认）

- ToolHive 使用一个本机回环监听端口，Nginx 管理入口和运行入口通过不同路由转发到该端口。
- Nginx 删除外部传入的 `Forwarded`、`X-Forwarded-For`、`X-Real-IP` 和 `X-ToolHive-*` Header，并重新写入可信内部 Header。
- Nginx 写入 `X-ToolHive-Ingress: admin` 或 `X-ToolHive-Ingress: runtime`，标识入口类型。
- Nginx 写入 `X-ToolHive-Client-IP`，其值来自已校验的实际连接来源 IP。
- ToolHive 只有在 TCP 对端属于配置的可信代理范围时，才读取这些内部 Header。
- 管理路由必须匹配 `admin` 入口标识，运行路由必须匹配 `runtime` 入口标识；入口标识缺失或不匹配时默认拒绝。
- 一期运行入口先由 Nginx 限制为允许的内网网段，ToolHive 再按 `system_id` 的 IP 规则进行第二次校验。
- 未来公网运行入口仍必须经过 Gateway/WAF/Nginx，不直接暴露 runtime API。

#### 确认结论

- 一期采用“同机 Nginx + ToolHive 回环监听”的部署方式。
- 一期不使用独立管理端口和运行端口，保持 A01 确认的一个应用端口。
- Nginx 只允许管理入口转发管理路由，只允许运行入口转发运行路由。
- 生产模式下，缺少可信入口 Header、入口类型与路由不匹配、来源 IP 无法解析或 TCP 对端不在可信代理范围内时，ToolHive 必须拒绝请求。
- Nginx 不得无条件信任调用方提交的代理 Header；没有前置代理时直接使用 `$remote_addr`，存在前置代理时只信任明确配置的代理 CIDR。
- 调用系统 IP 规则中的 `*` 只表示允许所有已经通过 Nginx 运行入口网络限制的来源，不代表允许公网访问。
- 开发直连仅允许回环地址，并通过开发配置显式开启；生产配置必须关闭。
- Nginx 与 ToolHive 改为不同服务器部署时，必须重新确认 A10 的连接方式和可信代理范围。

#### 最终方案

##### 一期网络拓扑

```text
公网管理请求
  → Nginx 管理入口
  → 仅转发 /admin/**、/api/admin/**
  → 127.0.0.1:{toolhive_port}

内网运行请求
  → Nginx 运行入口
  → 仅转发 /api/runtime/v1/**
  → 127.0.0.1:{toolhive_port}
```

- 两个 Nginx 入口最终连接同一个 ToolHive 应用端口。
- ToolHive 应用端口不得被服务器外部网络访问。
- Nginx 的管理入口访问运行路径、运行入口访问管理路径时直接返回拒绝，不转发到应用。

##### Nginx Header 处理

- Nginx 覆盖而不是追加 `X-Forwarded-For`，不得保留调用方提交的来源链。
- Nginx 清除外部 `Forwarded`、`X-Real-IP`、`X-ToolHive-Ingress` 和 `X-ToolHive-Client-IP`。
- 管理入口重新设置 `X-ToolHive-Ingress: admin`。
- 运行入口重新设置 `X-ToolHive-Ingress: runtime`。
- `X-ToolHive-Client-IP` 使用没有前置代理时的 `$remote_addr`。
- 如果未来存在 WAF 或负载均衡器，Nginx 只对明确配置的代理 CIDR 使用 `set_real_ip_from` 和真实来源解析，不得信任任意地址。
- ToolHive 应用只读取经过可信代理校验的 `X-ToolHive-Client-IP`，不直接采用调用方原始 Header。

##### 应用入口校验

- `/api/admin/**` 必须具有 `X-ToolHive-Ingress: admin`。
- `/api/runtime/v1/**` 必须具有 `X-ToolHive-Ingress: runtime`。
- Header 缺失、值非法、路由与入口不匹配或来源 IP 不是合法单 IP 时默认拒绝。
- Uvicorn 的代理信任范围必须显式限制为可信 Nginx 地址，不允许配置为 `*`。
- 入口校验完成后，运行 API 继续校验调用系统状态、公钥签名、Nonce、来源 IP 规则和工具调用控制。

##### 来源 IP 与白名单

- Nginx 负责运行入口的全局内网网段限制。
- ToolHive 使用 `X-ToolHive-Client-IP` 与当前 `system_id` 的单 IP、CIDR 或 `*` 规则匹配。
- `*` 仅在已经通过 Nginx 运行入口限制的范围内生效，不能绕过公网/内网边界。
- IP 解析统一处理 IPv4、IPv6 和 IPv4-mapped IPv6，异常格式一律拒绝。
- 认证失败、来源 IP 不匹配和入口不匹配均记录 Trace，但不得记录可用于伪造代理链的敏感配置。

##### 开发与后续改造

- Win11 开发配置可以开启仅回环地址直连，直连来源只能是 `127.0.0.1` 或 `::1`，并输出开发模式警告。
- Linux 生产配置强制使用 Nginx 入口，禁止应用端口直连。
- 后续若 Nginx、WAF 或 Gateway 与 ToolHive 分离，改用专用私网或受控 Unix Socket/代理链，并更新可信代理 CIDR、防火墙和健康检查配置。
- 后续若开放公网运行 API，仍必须经过 Gateway/WAF/Nginx，不能把 ToolHive 应用端口直接暴露到公网。

**已解决**：2026-08-18，已完成代码层入口校验：新增 `NetworkSettings`（`trusted_proxies`、`allow_loopback_direct`，含 YAML/环境变量配置）；新增 `core/network.py` 来源 IP 工具（IPv4/IPv6/IPv4-mapped 统一解析、回环与可信代理判断）；新增 `IngressMiddleware` 挂载到根应用，校验请求对端属于可信代理范围、`/api/admin/**` 必须携带 `X-ToolHive-Ingress: admin`、从 `X-ToolHive-Client-IP` 解析真实来源 IP（非法值拒绝），开发直连仅允许回环且显式开启并输出警告；非 API 路径仅做来源校验。Nginx 配置（入口路由、Header 清洗、内网限制）作为部署交付物另行产出。

### A12：会话中保存授权快照，与权限实时生效原则冲突

**状态：已确认**

#### 当前设计

- Redis 管理会话中保存 `is_super_admin`。
- Q06 要求角色和管理操作项变化后，下一次请求立即按最新配置校验。
- 权限服务又计划每次请求从数据库计算有效操作项。

#### 问题

- 超级管理员角色被移除后，会话中的 `is_super_admin` 仍可能保持为真。
- 前端和部分后端逻辑可能误用会话快照进行授权。
- 会话存储和实时授权出现两套身份判断来源。

#### 确认结论

采用“身份会话 + 实时授权”模型：

- 管理侧 Session 只负责证明登录身份和维护会话生命周期，不保存角色、管理操作项或 `is_super_admin` 等授权快照。
- 每次管理侧受保护请求都根据当前账号状态、角色和管理操作项重新计算有效授权。
- `security_version` 用于账号级安全事件造成的会话失效；权限实时生效与会话失效分别处理。
- 工具执行侧使用独立的调用方认证，不使用管理侧 Session。

#### 最终方案

1. **Session 字段边界**

   Session 可保存以下身份、生命周期和审计元数据：

   ```text
   session_id
   account_id
   username              # 可作为展示/审计快照，但不能作为授权依据
   created_at
   last_activity
   expires_at
   source_ip             # 用于审计或风控，不作为唯一身份依据
   security_version
   ```

   Session 不保存 `is_super_admin`、角色列表或管理操作项列表。

2. **管理请求授权流程**

   - 先校验 Session 是否存在、未过期，且账号仍处于可用状态。
   - 比较 Session 中的 `security_version` 与账号当前版本；版本不一致时拒绝请求并要求重新登录。
   - 通过权限服务读取账号当前角色和管理操作项，计算本次请求的有效授权。
   - 权限数据可以使用 Redis 等带版本/失效机制的缓存，但缓存不能形成永久授权快照。
   - Controller/Service 的后端权限校验始终以本次实时计算结果为准；前端权限数据只用于界面展示和操作项隐藏。

3. **权限查询接口**

   登录成功后，前端调用 `/api/admin/auth/me` 或 `/api/admin/auth/me/operation-items` 获取当前账号信息和有效管理操作项。权限配置变化后，前端重新调用该接口刷新显示状态。

4. **安全版本与会话失效**

   账号禁用、密码重置、MFA 重置等安全事件递增账号的 `security_version`，使该账号已有 Session 在下一次请求时统一失效；必要时同时删除 Redis 中的会话记录。

5. **普通权限变更**

   角色或管理操作项增删时清理该账号的权限缓存（如启用缓存），下一次请求重新读取最新配置并立即生效，默认不要求重新登录。若后续安全策略要求强制下线，可另行递增 `security_version`。

> **待补记录（2026-08-18）**：已随 A12 一并解决：新增 `/api/admin/auth/me` 与 `/api/admin/auth/me/operation-items`。

**已解决**：2026-08-18，已完成：会话不再保存 `is_super_admin`，改为保存 `security_version`；登录流程不再固化授权快照；新增 `/api/admin/auth/me`（当前账号信息）与 `/api/admin/auth/me/operation-items`（实时计算有效操作项，超管自动全量）；`management_account` 增加 `security_version` 字段（同步 init.sql 与 ORM），账号禁用、离职、密码重置时递增版本，`_get_current_user` 校验会话版本与账号当前版本不一致即拒绝并要求重新登录；登录响应与会话信息接口不再返回 `is_super_admin`。MFA 重置接口后续补全时沿用同一版本机制。

### A13：数据约束、状态机、审计和保留策略尚未统一

**状态：已确认**

#### 当前设计

- 账号、角色、调用系统等强调不物理删除。
- 多个状态使用普通字符串字段。
- 当前关联模型使用部分 `ON DELETE CASCADE`。
- Q23 的审计字段、脱敏和留存规则尚未确认。

#### 问题

- 数据库不能阻止非法状态值和部分非法状态转换。
- 误执行物理删除时，级联删除可能破坏历史关联。
- 审计记录如果只引用可变业务表，后续无法还原当时名称、版本和操作结果。
- Trace、Audit、Outbox 持续增长，但没有分区、归档和清理策略。
- 日期时间的 UTC 和时区约定没有形成数据库级规范。

#### 确认结论

采用“数据库约束 + 领域状态机 + 事务审计 + 配置化留存”的分层方案：

- 数据库约束负责阻止明显非法数据，领域 Service 负责合法状态之间的流转。
- 核心业务对象一期不作为普通操作物理删除，以禁用、归档或逻辑删除表达生命周期结束。
- 核心业务外键默认禁止级联删除；只有纯关联表可以使用级联。
- Audit、Trace、Outbox 的数据生命周期彼此独立，具体保留天数作为生产部署参数另行确认，不影响一期模型设计。

#### 最终方案

1. **字段和状态约束**

   - 核心字段按模型要求使用 `NOT NULL`、外键和业务唯一约束；唯一约束按对象及其业务作用域定义。
   - 状态字段采用“应用枚举 + PostgreSQL `CHECK`”的组合，不采用 PostgreSQL 原生 `ENUM`，以降低后续增加状态时的迁移成本。
   - `CHECK` 只负责保证状态值合法；状态转换由领域 Service 的显式方法统一执行，在同一事务中校验当前状态、更新状态并记录审计。
   - 需要并发控制的核心表增加 `row_version`，使用乐观锁避免并发更新互相覆盖。

2. **删除和关联策略**

   - 账号、角色、调用系统、Provider、工具及工具版本等核心业务对象，一期采用禁用、归档或逻辑删除，不提供普通物理删除。
   - 核心业务外键默认使用 `RESTRICT` 或等价的 `NO ACTION`，避免删除父对象破坏历史数据。
   - 纯关联表（例如账号—角色、角色—管理操作项）可以使用 `CASCADE`，因为关联记录不作为独立业务事实追溯。
   - Audit、Trace、Outbox 不允许被父业务对象级联删除；记录保存逻辑对象引用和必要的不可变快照，使对象改名、停用或归档后仍能还原当时的名称、版本和操作结果。

3. **审计记录**

   审计采用追加式、不可修改的记录，至少包含：

   ```text
   actor_account_id / actor_system_id
   object_type
   object_id
   action
   before_summary
   after_summary
   reason
   result
   trace_id
   source_ip
   occurred_at
   ```

   成功的业务变更与对应审计在同一数据库事务中提交；失败尝试单独记录安全事件或失败审计，不能把已经回滚的业务变更记录为成功。密码、TOTP 密钥、恢复码、私钥和敏感业务字段只保存脱敏摘要，不写入普通日志或审计快照。

4. **时间规范**

   - PostgreSQL 统一使用 `TIMESTAMPTZ` 保存时间。
   - 服务内部统一使用 UTC 处理时间，接口统一输出 ISO 8601 格式，例如 `2026-08-16T08:30:00Z`。
   - 不把服务器本地时区作为业务事实；Python 服务使用带时区的 UTC 时间对象，语义与 Java `Instant` 一致。

5. **Trace、Audit、Outbox 的留存**

   - Trace 为高频、短期查询数据，按时间分区并定期清理或归档。
   - Audit 为长期追责数据，保留时间长于 Trace，清理前必须经过明确的留存策略。
   - Outbox 在事件确认处理完成并经过安全保留窗口后清理；失败事件保留重试、死信状态和处理日志。
   - 清理周期、批量大小、归档开关和执行频率全部支持配置文件配置，配置项必须有默认值和说明。
   - 清理任务本身记录可查询的运行日志；具体保留天数在生产部署前根据合规和业务要求确定。

> **待补记录（2026-08-18）**：核实发现账号—后台角色关联（纯关联表）的维护接口未暴露：`RoleService` 已有 `assign_role_to_account`/`remove_role_from_account` 方法，但 accounts/roles 路由没有对应端点；一期目标要求支持账号与后台角色多对多关联维护。

### A14：生产可用性、健康检查、追踪和发布迁移方案不完整

**状态：延后**

#### 当前设计

- 目前只有简单 `/health`。
- Q24 的容量、可用性、RPO/RTO 和备份恢复仍待确认。
- 运行侧后续需要通过 Trace 标识关联工具发现、执行和 Provider 调用过程。
- 操作项目录计划在应用启动时同步。

#### 问题

- 进程存活、基础请求追踪和生产运维可用性目前没有形成统一边界。
- 认证、工具执行和 Provider 出站失败的查询关联方式尚未冻结。
- 备份恢复、容量、告警和发布迁移规则尚未形成一期上半的交付要求。
- 多实例启动、滚动发布和嵌入式 Chroma 之间存在部署约束。

#### 延后结论

A14 不作为一期上半的完成判定，按两个阶段处理：

- **一期下半**：统一设计和实现基础 Trace/审计，覆盖工具发现、工具执行、Provider 调用及必要的管理操作；届时回头补齐管理侧的关联字段、脱敏和留存规则。
- **二期**：再处理生产运维增强，包括健康检查分层、metrics、监控告警、备份恢复演练、RPO/RTO、容量治理、发布迁移、多实例滚动发布和高可用。

一期上半可以保留现有基础 `/health`，但不新增 A14 的生产可用性验收要求。

#### 一期下半预留范围

- 为运行请求生成并传递字符串 `trace_id`，关联认证、授权、Discover、Execute、Provider 和结果处理。
- 对关键管理操作和运行决策形成追加式、脱敏的基础审计记录。
- 在日志、错误响应和运行记录中保留 `trace_id`，便于定位一次工具调用。
- 一期下半开始前重新确认管理侧审计是否复用同一 Trace 关联模型。

#### 二期范围

- `/live`、`/ready`、`/metrics` 的正式职责和访问边界。
- 结构化指标、监控看板、告警阈值、容量和时钟偏移监控。
- PostgreSQL、Redis、Chroma 的备份恢复演练及 RPO/RTO。
- 独立 release job、Schema 向后兼容迁移、滚动发布和多实例高可用。
- 嵌入式 Chroma 服务化后再评估多实例部署。

#### 恢复确认时机

- 一期下半开始设计 Trace/审计前，重新确认基础字段、脱敏、留存和查询范围。
- 二期运维建设前，再确认健康检查、备份恢复、容量、发布和可用性指标。
