# 工具平台从零搭建设计

> 状态：架构基线，待进入需求确认与实施拆分
> 更新日期：2026-08-07
> 目标：新建独立工具平台，为 CountBot 及后续其他调用方提供统一的工具目录、检索、授权和执行能力。

## 1. 已确认的架构决策

- 工具平台是独立项目，不以继续堆叠 CountBot 的 `backend/modules/tools` 为建设方式。
- PostgreSQL 是工具完整定义、版本、Provider、权限绑定和运行状态的唯一事实来源。
- Chroma 只保存从 PostgreSQL 派生的检索文本和过滤元数据；它不是工具定义或权限的事实来源。
- 并非所有工具都进入工具平台。计算、JSON 处理、字符串格式化、简单规则判断等无外部副作用的轻量纯函数工具由 CountBot 进程内执行。
- 首期外部工具以现有 **HTTP 接口** 接入。外部 Java 项目不需要为了 CountBot 改造成 MCP Server。
- MCP 是可选 Provider 协议：后续可消费第三方或自建 MCP Server，也可按需求把审核后的工具以 MCP 形式对外开放。
- 不自建一套与 MCP 重复的外部工具协议。平台内部定义统一工具契约，再用 HTTP、MCP、gRPC 等 Provider 适配实际调用方式。
- 工具平台承担 `ToolPolicy`、检索、执行编排和审计；LLM、CountBot 和用户输入都不能绕过平台决定权限或任意发起网络请求。
- 首期必须具备全链路追踪。高可用、专业搜索引擎、复杂任意 ACL 等按实际规模后延。

## 2. 一期目标、范围与交付顺序

一期的目标不是覆盖 CountBot 的全部历史工具，而是交付“CountBot 可安全调用外部 Java HTTP 工具”的最小闭环：外部工具有统一目录、可检索、可授权、可执行、可追踪。

### 一期交付范围

- 管理面 API：一期使用独立域名 `https://tools.xuan2.com`，通过 HTTPS 对外提供工具查看、创建、更新、版本查询、启停和审核等受认证的管理能力。
- 运行面 API：`Resolve`、`Execute`、Provider 健康与内部执行相关接口只在本机/VPC 私网开放，仅接受受认证的服务间调用。
- PostgreSQL Catalog：Provider、工具/版本、Capability、权限绑定、执行配置引用、索引 Outbox 和审计数据。
- `HttpToolProvider`：只调用管理员预先审核的固定 HTTP 方法、路径、参数映射和凭据引用。
- `ToolPolicy`：角色—权限包—Capability 的 Discover/Execute 两阶段校验。
- Chroma Tool Index：从 Catalog 派生检索摘要，按 Audience Scope 过滤并支持混合召回。
- `ToolResolver`、`ToolExecutor`、覆盖度结果、JSON Schema 校验、脱敏 Trace 和管理/健康检查 API。
- 与 CountBot 的 Resolve/Execute 接入；试点少量只读外部 Java 工具，再接入需确认的写操作。
- CountBot 进程内轻量工具继续留在 CountBot，由本地 allowlist 和 `LocalToolSelector` 管理。
- 工具平台管理面自带账号、密码、会话和粗粒度角色；一期不复用 CountBot 登录 Cookie，也不建设 CountBot 与工具平台的统一登录或授权码交换。

### 一期明确不做

- MCP Provider、MCP Registry 发现与平台 MCP Server 网关。
- gRPC Provider、异步长任务、宿主 Agent/`CountBotHostProvider`。
- 分布式向量数据库、专业搜索引擎、分片/多副本、多区域灾备和大规模任意账号—工具 ACL 专用检索。
- 复杂灰度发布、自动回滚、长任务任务中心、死信处理和高级成本/质量评测。

### 一期实施顺序

1. **契约与安全基线**：确定管理面与运行面 API、`ToolContext`、统一 Schema、错误码、Trace Header、服务间身份认证、管理端登录/授权、Secret Store、网络 allowlist 和首批 Java HTTP API 契约。
2. **Catalog 与 HTTP 闭环**：建立 PostgreSQL 表、版本状态、索引 Outbox、工具管理 API、固定请求映射、健康检查和受控执行。
3. **Policy、检索与 Trace**：建立角色—权限包—Capability 模型，接入 Chroma 索引、Audience Scope、混合召回、覆盖度判断和脱敏追踪。
4. **接入 CountBot 试运行**：以少量只读工具灰度验证聊天链路、权限不足、Provider 故障、超时、Schema 变更和审计；完成后再接入写操作确认。

### 一期开始前需确认

1. 运行面服务间认证和 Secret Store 选型。
2. 首批 Java HTTP 工具的 API 契约、业务数据权限和幂等性要求。
3. 首期角色、权限包、Capability 的命名空间与继承规则。
4. `permission_missing` 的用户披露范围及高风险确认交互的归属。
5. 嵌入式 Chroma、Embedding 服务和不可用时的受控降级语义。
6. Catalog 变更与索引同步完成前的版本可见性规则。

## 3. 一期职责边界

```text
CountBot / 其他调用方
        │ 认证后的 ToolContext、用户请求、LLM 工具调用
        ▼
CountBot 本地轻量工具              工具平台
计算 / JSON / 字符串 / 简单规则       Tool Catalog → ToolPolicy → Tool Resolver → Tool Executor → Trace
        │                                  │                         │                 │
        └──────────── CountBot ToolGateway ─┘                         │                 │
                                                           PostgreSQL         ToolProvider
                                                                │                 │
                                                                ▼                 ▼
                                                             Chroma       HTTP / MCP / gRPC / 本地实现
                                                                                 │
                                                                                 ▼
                                                                         外部 Java 项目等实际系统

互联网管理用户
        │ HTTPS + 管理员认证
        ▼
tools.xuan2.com → Nginx / API Gateway → 工具平台管理面（查看、维护、版本、审核）
```

### 工具平台负责

- 对外管理面与内网运行面隔离：管理面负责工具查看和维护；运行面负责 Resolver、Executor 和 Provider 调用，不能因公网可达而接受运行请求。
- 管理面维护自己的账号和会话；`admin` 可以维护、审核和发布工具，`viewer` 只能查看工具和版本。该角色模型只保护管理面，不等同于运行时的 Capability/ToolPolicy。
- 工具目录、版本、状态、Provider 配置引用、能力声明和索引同步。
- 工具发现阶段与执行阶段的统一权限决策。
- 基于请求意图的候选工具检索、能力覆盖度判断和完整 Schema 下发。
- 参数校验、固定执行配置路由、结果规范化、错误归类和全链路追踪。

### 外部业务项目负责

- 提供自身真实业务能力，例如订单查询、工单创建或项目数据查询。
- 按自身系统已有标准提供 HTTP 接口；内部高频场景可在后续提供 gRPC；需要生态互通时可提供 MCP。
- 校验平台服务身份、实施业务侧数据权限，并返回稳定的业务结果和错误码。

### 工具平台不负责

- 不承载 CountBot 的轻量进程内纯函数工具，也不要求这类工具写入 PostgreSQL 或 Chroma。
- 不把任意 URL、HTTP 方法、认证头或请求模板交给 LLM 决定。
- 不保存明文密钥，不替代外部业务系统自身的业务校验。
- 不把 MCP Registry 当作可信工具目录或自动安装源。

## 4. 一期统一工具契约与数据模型

平台内部的统一工具契约应与底层协议无关。LLM 可见的部分只包括工具名称、说明、输入 Schema、输出摘要和必要的使用约束；执行配置和凭据不对 LLM 暴露。

### 核心实体

| 实体                    | 关键内容                                               | 责任                  |
| --------------------- | -------------------------------------------------- | ------------------- |
| `provider`            | `provider_id`、类型、所有者、健康状态、配置引用、信任级别                | 描述工具来源和执行适配器        |
| `tool`                | `tool_id`、命名空间、可读名称、状态、风险等级、能力、归属                  | 工具逻辑身份              |
| `tool_version`        | `tool_id + version`、描述、输入/输出 JSON Schema、超时、重试、幂等性 | 不可变的可调用定义           |
| `tool_binding`        | 工具版本与 Provider、执行配置引用、有效期                          | 将定义绑定到实际实现          |
| `capability`          | 例如 `order.read`、`ticket.create`                    | 最小授权语义              |
| `entitlement_bundle`  | 能力集合与继承关系                                          | 避免为每个工具重复配置角色       |
| `policy_binding`      | 工具、能力、风险和上下文规则                                     | ToolPolicy 的配置来源    |
| `credential_ref`      | 密钥管理系统中的引用                                         | 不保存明文凭据             |
| `index_outbox`        | Catalog 变更事件、索引版本、重试状态                             | 保证 PG 与 Chroma 最终一致 |
| `management_user`     | 用户名、密码哈希、角色、启用状态                                   | 管理面登录主体             |
| `management_session`  | 会话 Token 哈希、用户、过期时间、撤销状态                           | 管理面会话               |
| `trace` / `tool_call` | 检索、授权、调用、结果和脱敏审计信息                                 | 可观测与追责              |

`tool_id + version` 是一次实际调用的唯一定位，不可只使用可读工具名。只有已启用、已审核且索引版本一致的工具版本可以进入在线检索。

### 工具版本生命周期

管理面中的“更新工具”必须创建新的不可变 `tool_version`，不能覆盖既有版本。旧版本保留用于审计、调用记录还原和必要的在途请求处理；是否还能被新请求发现或执行由版本状态决定：

- `draft`：已创建，尚未完成校验或审核，不可发现、不可执行。
- `active`：当前默认版本，可进入索引、被 Resolver 下发并允许执行。
- `deprecated`：保留历史定义；默认不再被新 Resolve 下发，可在受控过渡期完成已开始的调用。
- `disabled`：因风险、故障或人工操作停止新执行；保留审计，不可发现。
- `archived`：仅历史保留，不能发现或执行。

版本从 `draft` 变更为 `active` 时，通过索引 Outbox 发布新版本；新版本完成索引和健康校验后才切换默认版本。旧版本的下线时机和在途调用语义属于一期需确认项。

### HTTP 工具的固定实现配置

首期外部 Java 工具由 `HttpToolProvider` 调用。每个工具版本必须在平台侧预先定义和审核执行映射，例如：

```text
tool_id           = order.query
provider_type     = http
method            = GET
path_template     = /internal/orders/{order_id}
credential_ref    = order-service-prod
timeout_ms        = 3000
input_schema      = 仅允许 order_id
```

LLM 只能传入符合 `input_schema` 的业务参数。`HttpToolProvider` 负责路径变量编码、请求体映射、固定认证、超时、响应转换和错误标准化；不得接受由 LLM 给出的 URL、方法、任意 Header 或额外参数。

### 管理面与运行面网络边界

- **管理面**：`tools.xuan2.com` 的 Nginx/API Gateway 仅将 HTTPS 管理路由转发给工具平台；所有接口仍在应用层校验工具平台自己的用户会话、`admin/viewer` 角色和操作审计，不能只依赖反向代理路径限制。运行面路由不得在该域名公开。
- **运行面**：`Resolve`、`Execute`、Provider 注册后的运行控制和内部 Trace 查询使用独立的内网监听地址或严格的私网访问策略。即使路由误被代理到公网，应用层也必须拒绝非服务身份请求。
- **运行调用链**：CountBot 通过私网地址调用工具平台；工具平台再按 allowlist 调用外部 Java 项目的 HTTP API。外部 Java 项目的服务凭据只由工具平台持有。

### 一期管理面认证边界

- 工具平台独立维护账号、密码哈希、会话和角色；管理 Cookie 只对 `tools.xuan2.com` 生效。
- CountBot 的 `CountBot_token` 不发送给工具平台，CountBot 登录、退出和密码修改不会直接操作工具平台管理会话。
- 工具平台一期只提供 `admin` 和 `viewer` 两种粗粒度角色；不做用户级、租户级、Capability 级或工具级管理权限拆分。
- 管理面登录仍需密码哈希、HTTPS、HttpOnly/Secure/SameSite Cookie、登录限流、会话过期、退出撤销和密码修改后的会话撤销。
- 管理面账号认证与运行时 `ToolPolicy` 分开：前者保护谁能维护工具，后者决定 CountBot 请求能否发现/执行业务工具。

## 5. 一期 Provider 模型与协议策略

所有来源都实现同一组平台内部能力：`sync`、`get_definition`、`health_check`、`execute`。这是一层代码接口，不是对外再发明一种网络协议。

### 首期：HTTP Provider

- 外部 Java 项目继续使用现有、受认证保护的 HTTP API。
- 平台管理员创建 Provider、登记允许的目标服务和工具映射；工具定义经审核写入 PostgreSQL。
- 平台使用服务身份调用外部项目，外部项目仍负责业务数据权限和最终数据校验。
- 所有出站地址使用 allowlist、固定域名/IP 解析策略和网络访问控制，防止 SSRF。

### CountBot 进程内轻量工具

计算、JSON 解析/转换、字符串格式化和不依赖外部系统的简单规则判断，属于 CountBot 的本地能力，不应为统一化而引入跨服务调用、Catalog 登记或向量检索。它们必须同时满足以下边界：

- 无网络访问、无数据库或文件写入、无外部副作用，也不需要业务系统凭据；
- 工具定义和实现随 CountBot 代码发布，由本地 allowlist、输入 JSON Schema 和资源上限保护；
- 通过 CountBot 的 `ToolGateway` 与外部工具一起提供给 LLM，但由本地执行器完成调用；
- 记录 CountBot 侧 Trace Span，标识 `execution_domain=countbot_local`，无需把调用转发给工具平台。

一旦工具需要访问外部项目、密钥、租户业务数据或产生业务副作用，就不再属于此类，应接入工具平台并接受 ToolPolicy 治理。

## 6. 一期 ToolPolicy：发现与执行两阶段授权

权限关系统一为：

```text
角色 → 权限包（Entitlement Bundle）→ Capability → ToolPolicy → 工具
```

- 工具声明最小能力，如 `order.read`，不为管理员、组长、操作人逐一重复绑定工具。
- 角色继承和有效能力闭包由 ToolPolicy 在可信后端上下文中计算。
- 用户 prompt 不得携带或决定角色、租户、Capability 等权限事实。

### Discover

在把工具 Schema 发给 LLM 前执行。输入包含账号、租户、角色/权限包、入口、会话、渠道、时间和请求目标；输出 `allow`、`deny`、`retrieval_plan` 与原因码。

`retrieval_plan` 输出少量稳定的 `audience_scope`，例如公共范围、当前租户范围、权限包范围和小规模用户 Overlay。它不能输出数百或数千个 `tool_id` 作为 Chroma 过滤条件。

### Execute

在 LLM 选择工具后重新执行。除身份上下文外，还必须检查真实参数、目标资源、数据归属、渠道、操作时间、风险等级和确认状态。Discover 允许不代表 Execute 必然允许。

策略结果至少包含：`allow`、`deny`、`require_confirmation`、`async_only` 和 `reason_code`。

## 7. 一期工具检索、能力覆盖度与 LLM 边界

### Resolver 流程

1. 判断请求是 `direct_answer`、`tool_optional` 还是 `tool_required`，并识别目标能力。
2. ToolPolicy 生成可信的 `retrieval_plan`。
3. 在允许的 Audience Scope 内进行关键词/BM25 与 Embedding 的混合召回、去重和重排。
4. 通过 `tool_id + version` 从 PostgreSQL 批量读取完整定义，再次做 Discover 校验。
5. 向调用方返回相关且可发现的外部候选 Schema、相关性/优先级和覆盖度；调用方可声明外部候选预算。

Chroma 的文档内容应包含名称、别名、能力、适用场景、参数语义和示例；metadata 至少包含工具定位、状态、类型、租户范围和 Audience Scope。Chroma 不负责复杂权限真值判断。

### 覆盖度结果

Resolver 必须输出能力覆盖度，避免把“没有召回到工具”错误地当成“用户没有权限”：

- `full_coverage`：当前可用工具足以完成目标。
- `partial_coverage`：可完成部分目标，需降级、补充信息或拆分执行。
- `permission_missing`：全局存在所需能力，但当前身份不具备权限；具体披露内容另由信息披露策略控制。
- `provider_unavailable`：存在且允许的工具目前不可执行。
- `unsupported`：平台没有该能力。
- `uncertain`：需要澄清目标或无法可靠判断。

无权限工具的完整 Schema 不得泄露给 LLM。LLM 只在候选工具内选择，不得指定未下发的 `tool_id` 或版本。

### 与 CountBot 本地工具的候选合并

工具平台 Resolver 只对平台管理的工具负责，不感知 CountBot 的计算、JSON、字符串等进程内工具，也不把它们写入自己的 Catalog 或 Chroma。CountBot 的 `ToolGateway` 必须在本地候选与平台候选之间做最终合并：

```text
CountBot LocalToolSelector → 少量本地候选及优先级 ─┐
                                                     ├→ 合并、去重、重排、总预算控制 → LLM Schema
工具平台 Resolver → 已授权外部候选及覆盖度 ────────┘
```

- 平台返回的 Top K 是**外部候选预算**，不是最终发给 LLM 的全部工具数量。
- 最终工具数量和 Schema Token 预算由 CountBot 控制；通常应保持在约 8～15 个，具体按模型上下文和 Schema 大小配置。
- CountBot 可先确定本地候选数量，再把剩余预算传给平台 Resolver；也可取两侧候选后按优先级合并。无论采用哪种方式，平台的 `full_coverage`、`permission_missing` 等结果不得被丢弃。
- 若外部工具是完成 `tool_required` 目标的唯一能力，CountBot 不得仅因本地工具占满预算而静默移除它；应优先保留关键外部候选或要求进一步澄清。

## 8. 一期 ToolExecutor 与安全执行

执行链固定为：

```text
LLM 工具调用
  → 根据 tool_id + version 读取 PostgreSQL 定义
  → ToolPolicy.Execute
  → JSON Schema 与参数级安全校验
  → Provider 路由与受控调用
  → 结果标准化、审计与返回 CountBot
```

- 对高风险写操作支持 `require_confirmation`；确认令牌必须绑定调用上下文、工具版本、已校验参数和有效期，不能只凭一句自然语言确认。
- 凭据从受控 Secret Store 按 `credential_ref` 注入；日志、Trace 和错误中统一脱敏。
- Provider 返回内容是不可信输入，应限制大小、类型、敏感信息和可回灌到 LLM 的内容。
- 对外请求必须有超时、错误映射、可控重试和幂等性规则；默认不对写操作盲目重试。

## 9. 一期 Trace 与可观测性

首期每个请求贯穿同一个 `trace_id`，至少记录：

- 调用方、入口、会话及认证上下文摘要；
- 请求分类、Retrieval Plan、候选工具 ID/版本/排名；
- Discover 和 Execute 的 Policy 决策及原因码；
- LLM 选择、参数校验结果、确认状态；
- Provider 名称、耗时、状态、错误码、重试次数和最终覆盖度。

敏感参数、密钥、授权令牌和业务结果按字段策略脱敏或只保存摘要。Trace 既要能由 CountBot 透传关联，也要能独立审计工具平台的决策。

## 10. 二期及后续待完成项

二期只在一期 HTTP 闭环稳定、权限与 Trace 验收通过后启动。下列能力均不应阻塞一期上线。

### MCP Provider、MCP Registry 与 MCP 网关

- 实现 `McpToolProvider`，连接已批准的 MCP Server，拉取 `tools` 并规范化为 Catalog 候选版本。
- MCP Server 是实际工具提供方；MCP Registry 只是发现候选 Server 的目录，不负责执行工具。
- Registry 中的 Server 必须经过发布者/来源校验、管理员审批、凭据配置和健康检查后，才能同步到 PostgreSQL 和 Chroma；禁止自动信任、自动安装或自动启用。
- `resources`、`prompts` 与可执行 `tools` 分开建模和审核，不能因为发现到它们就直接放进 LLM 上下文。
- 如需让其他 Agent 使用平台工具，再建设平台自身的 MCP Server 网关；它只暴露经过 ToolPolicy 允许的能力。

### gRPC 与其他 Provider

- 为内部高频、强类型或低延迟的 Java 服务增加 `GrpcToolProvider`。
- 将 Protobuf 转换为 Catalog 的统一输入输出 Schema、错误、审计和版本模型。
- 一个外部系统无需同时维护 HTTP、gRPC 和 MCP；确有跨 Agent 生态复用需求时，再在平台或业务系统增加 MCP 适配层。

### CountBot 宿主工具迁移

- 评审并实现受控的 `CountBotHostProvider` 或宿主 Agent，用于迁移文件、Shell、Wiki、记忆、渠道等依赖 CountBot 主机和进程上下文的工具。
- 明确网络可达性、调用/回调方向、服务身份、参数校验、审计归属、断连语义和工作空间隔离后，再迁移高风险宿主工具。
- 计算、JSON、字符串和简单规则等纯函数工具长期留在 CountBot，不属于此迁移范围。

### 规模化与治理增强

- 服务化或分布式向量数据库、专业搜索引擎、分片/多副本，以及多区域部署和跨区域灾备。
- 大规模任意账号—工具 ACL 的专用检索方案、分布式缓存和复杂热点目录优化。
- 长任务中心、取消/回调/死信处理、Provider 配额治理、熔断和高级限流。
- 工具版本灰度发布、自动回滚、离线召回评测、在线质量/成本指标和更精细的检索降级策略。

### 二期开始前需重新确认

1. MCP Server 的来源、信任模型、审批流与凭据隔离方案。
2. 哪些 Java 服务确实需要 gRPC，而非继续使用一期 HTTP Provider。
3. CountBot 宿主 Agent 的部署拓扑和高风险本地工具的最小授权模型。
4. 触发向量检索服务化、搜索引擎或复杂 ACL 专用方案的实际规模阈值。
